### Item 1: brms's fields, and `$`

`$` on a family object answers `link`, `linkfun`, `linkinv` and one
`link_<dpar>` per parameter other than the mean. They are NOT stored:
`$.frmtmb_family` computes them from `links`, `dpars`, `type` and
`ord_link` at the moment of the read (`family_link_view()`).

Round 0 stored them and re-derived them in `$<-` and `[[<-` methods.
The review showed that going stale through `[<-`, a numeric `[[<-` and
an unclass-and-rebuild, and a base-saved fit erroring on `$link`. Both
come from having a copy, so round 1 removed the copy and the
replacement methods with it. No assignment method is kept: nothing
needs one once there is nothing to re-derive. A stored element under a
link field name (`f["link"] <- "log"`, reachable by any write path) is
refused when `$` reads it, because `$` would otherwise have to choose
between the element and the links the fit applies; a read-time check is
the one place every write path passes through.

There is no `[[` method. `[[` is how the package itself reads a family
in every hot path, and brms-shaped consumers read these fields with `$`
(`dev/famlink-punch-insightscan.R`):

<<BLOCK:insightscan>>

**Why `links` stays.** Consumers of `links`, by grep over `R/` and
every `extensions/*/R` (generated by `dev/famlink-findings-build.R`):

<<BLOCK:consumers>>

Among them frmtmb.eam writes `fam[["links"]][["ndt"]]` in three
places inside `family_finalize()` and `ndt_bound_attach()`,
frmtmb.latent's `hmm()` copies component links, frmtmb.sample and
frmtmb.spline read the mean link. `links` holds link OBJECTS (a custom
link is a list of functions); brms's fields are strings. One cannot
replace the other, so the strings are computed from `links`.

**`$` partial matching.** `$.frmtmb_family` matches exactly. A name
that is a prefix of exactly one field is an error naming that field
(`beta_binomial()$link_p`, `$lpd`). A name that is a prefix of several
fields returns `NULL`, which is what base `$` returns, and so is not a
silent hit. A name matching nothing returns `NULL`, as brms's family
list does for `$link_zi` on a family without `zi`.

Joint-link families: `categorical` and `multinomial` report
`link = "logit"`, brms's value, and have no `link_<dpar>` for their
per-category predictors, whose `identity` in `links` is where the
softmax starts rather than their scale. A `mixture()` has no `mu` and
reports `"identity"`, brms's value; frmtmb adds `link_mu1`,
`link_sigma1` and so on, which brms keeps on its `mix` components
instead.

`print()` now opens with brms's two lines, so brms's
`expect_output(print(weibull()), "Family: weibull \nLink function: log")`
passes.

### Item 2: unquoted links

`link_arg_value()` follows brms's `.brmsfamily()` order: a bare name
that is a link the family allows is taken without evaluation (so
`student(identity)` never evaluates base R's `identity()`); otherwise
the argument is evaluated, and a string or a link list is used; `NULL`
or `NA` is the default; anything else comes back as its deparsed text
and is refused by name. Only the mean link is unquotable, as in brms,
where `student(link_sigma = identity)` errors (log line
"student(link_sigma = identity) unquoted secondary").

One deliberate difference, added in round 1. A bare name that is a
roster link the family does not take and that is bound to nothing,
`negbinomial(inverse)`, comes back as its name and is refused as that
link. brms evaluates it and fails with "object 'inverse' not found".
brms's own assertion `expect_error(negbinomial(inverse), "inverse")`
passes on that message in brms, and it did on the round 0 lane too;
the ledger's new check caught it (rows 6 and 28 below).

### NIT 3: `get_prior()` refused where brms does not. Fixed.

`assemble_frame()` gains `check_trials = TRUE`. `get_prior()` passes
`FALSE`, which skips `check_trials_given()` and the `valid_y` of a
family that reads trials (a component of a mixture included), because
no prior slot depends on the trials. A fit never passes it, so `frm()`

## Not fixed, and why

- **`mixture(nmix =, order =)`.** brms's arguments do not exist. They
  are refused by name, but brms's `family_names(mix)` and `order`
  assertions cannot pass without them.
- **`hurdle_negbinomial`, `zero_inflated_beta_binomial`,
  `hurdle_cumulative`, `xbeta`.** brms families frmtmb lacks; they are
  most of the ledger's "cannot transfer" rows.
- **The prose table in `?frmtmb-links`** ("Links for the mean") is
  still typed. The generated table is what the code enforces and what
  the test holds to brms; the prose was compared by eye.
- **`tweedie()` in a mixture** is allowed; see review finding 3.
- **`hmm(K, multinomial(K))`** in frmtmb.latent reads its emission
  trials from the row sums. hmm is not a brms family and the brief
  covered `multinomial` itself; extending the refusal into an
  extension's emission families is a separate decision.
- **`hmm(K, binomial())`** in frmtmb.latent fits 0/1 data without
  `trials()`, as one trial per row, in base and on the lane (NIT 4
  above). The reason is the one for the multinomial emission: the hmm
  family is not named `binomial` and does not list its emission family
  as a component, and brms has no hmm.
- **A custom density that is finite at its start and NaN elsewhere** no
  longer warns during optimization. Its trials are counted in
  `fit$opt$nonfinite_trials`, and `diagnose()` and `verbose = TRUE`
  print a nonzero count; there is still no warning.
- **Classed errors.** Out of scope (item 2.6e): every new refusal is a
  plain `simpleError`.
