## Verdict

**NOT MERGEABLE.** Two blocking defects, both small to fix.

- **B1. `add_criterion(overwrite = TRUE)` on draws does not recompute.**
  It returns the stored criterion. brms's `add_criterion.brmsfit()`
  runs `x$criteria[new_criteria] <- NULL` before it computes, so brms
  recomputes. frmtmb.sample's method calls `loo(x, ...)`, and the
  lane's own `use_stored` path in `loo.frmtmb_draws()` then returns the
  object it was asked to replace. `dev/surface-rev-addcrit.R`
  (`addcrit.txt`, sampler seed 3, 2 chains, 600 draws):

  ```text
  add_criterion(ds, 'loo', ndraws = 100): stored dims 100 x 60
  add_criterion(ds2, 'loo', overwrite = TRUE): stored dims 100 x 60 |
    identical to the old one (estimates): TRUE | fresh loo(ds) dims 600 x 60
  ```

  The test that claims to pin `overwrite`
  (`test-add-criterion.R`, `ds4`) checks only the `model_name`
  attribute, which the method sets after the call, so it passes on the
  stale object. Fix: clear `x$criteria[new]` before computing, and
  assert on `attr(, "dims")` or the estimates in the test.

- **B2. `pp_mixture()` on a fit: `Est.Error` understates the
  uncertainty brms reports, and the help page's figure is from a
  filtered subset.** Same construction as the lane
  (`dev/surface-ppmix-mc.R`: data seed 4, 300 rows; 4000 draws from
  N(estimate, V), seed 1), extended to all rows
  (`dev/surface-rev-ppmix.R`, `ppmix.txt`), and against brms 2.23.0's
  `pp_mixture()` on the same data (`dev/surface-rev-brms.R`, 4 chains
  of 1500 post-warmup draws, seed 1; `dev/surface-rev-ppbrms.R`,
  `ppbrms.txt`). Rows binned by `min(p, 1 - p)`:

  ```text
  bin               n  delta/MC SD  delta/brms SD  logit-normal SD/brms SD
  [0, 1e-4)        26     0.032        0.00837          4.75
  [1e-4, 1e-3)     35     0.161        0.0613           2.37
  [1e-3, 1e-2)     79     0.416        0.218            1.27
  [1e-2, 0.05)     60     0.675        0.434            1.03
  [0.05, 0.2)      57     0.859        0.723            0.843
  [0.2, 0.5]       43     1.07         1.04             0.914
  all rows        300     0.606        0.361            1.11
  ```

  The help page and the findings quote "a median 0.69" of the MC SD
  "over the rows where that SD exceeds 0.01": that filter removes the
  56 of 300 rows where the ratio is worst (0.0003 to 0.15). Against
  brms's own `Est.Error` the delta SE is a median 0.36 overall and 0.06
  to 0.22 within 0.01 of an edge, which is where `pp_mixture()` is read
  (how certain is this classification). The logit Wald interval is
  honest: width 1.04 of brms's interval (median), and every frmtmb
  `Estimate` lies inside brms's 95% interval (300 of 300, median
  |difference| 0.35 brms SDs). Shape, row names, statistic names and
  component names `P(K = k | Y)` are identical to brms's.

  Answer to the brief's question: the raw delta SE is not honest
  enough near 0 and 1, but NA throws away a number the interval already
  implies. The fix that matches brms best and agrees with the reported
  interval is `Est.Error` = the SD of `plogis(N(qlogis(p), lse^2))`,
  the law the interval is built from (40-point Gauss-Hermite, cheap):
  median 1.11 of brms's SD, 0.84 to 1.27 for p in [0.001, 0.999], and
  an overstatement only where the SD is itself below about 1e-4. If the
  lane keeps the delta SE (it is fitted()'s convention), the help page
  must give the unfiltered numbers and the brms comparison above, not
  the filtered 0.69. Either way, change the NEWS bullet to match.

### 4. frm_multiple()

- Estimates: max |frmtmb - mice| 4.11e-6, as claimed. But the claim

  1.15 times brms's width (t quantile on df near 11). Pooling a
  prediction at FIXED covariate values is valid whatever the
  imputations do to the covariate ranges: the estimand is defined by
  the grid, and each imputation's fit is evaluated at it. Here every
  imputation has the same `chl` range (113 to 284), so the range
  question did not arise in this data.
