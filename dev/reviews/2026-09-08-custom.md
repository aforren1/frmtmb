# Review: wt-custom (a family written in plain R is first class)

Independent verification of the `wt-custom` lane against `main` at
`c18253e`. Everything below was measured in this review, in a private
library, not taken from the lane's report. `main`'s package code is
identical to the branch point (`5b505f4` touches no package file), so
`main` is a valid "before".

**Verdict: PUNCH.** Two cheap defects, both in the new opt-in path, and
neither a correctness bug. The arithmetic, the refusals and the counts
hold up; I could not break the convention anywhere I tried.

## Ruling on the brms divergence: KEEP IT

This is the decision of the round, so I checked the premises rather than
accepting them.

**brms really does emit `P(Y > y)`.** Generated with brms 2.23.0,
`make_stancode(y | cens(cens, y2) ~ x, family = poisson())`:

```
if (cens[n] == 0)       target += poisson_lpmf(Y[n] | mu[n]);
else if (cens[n] == 1)  target += poisson_lccdf(Y[n] | mu[n]);      // P(Y > y)
else if (cens[n] == -1) target += poisson_lcdf(Y[n] | mu[n]);       // P(Y <= y)
else if (cens[n] == 2)  target += log_diff_exp(poisson_lcdf(rcens[n] | mu[n]),
                                               poisson_lcdf(Y[n] | mu[n])); // (y, y2]
```

So the divergence is **right and interval only**. Left censoring is
`P(Y <= y)` in both packages and agrees exactly. The lane's docs say
"differs for right and interval censoring", which is precise.

**frmtmb's `trunc(lb = )` really is inclusive**, so the
internal-consistency argument is real. Poisson, intercept only,
`y = 3,4,5,6`:

| | frmtmb | inclusive `P(Y >= lb)` | exclusive `P(Y > lb)` |
|---|---|---|---|
| `trunc(lb = 2)`, `b0 = log 4` | 6.9990718955 | **6.9990718955** | 6.2954805379 |
| `trunc(lb = 3)`, `b0 = log 4` | 6.2954805379 | **6.2954805379** | 5.1103559317 |

`trunc(ub = )` is inclusive too (`F(ub)`, not `F(ub - 1)`).

**And here is the fact that settles it: brms is internally inconsistent,
frmtmb is not.** brms's own discrete truncation emits

```
target += poisson_lpmf(Y[n] | mu[n]) - poisson_lccdf(lb[n] - 1 | mu[n]);
log_diff_exp(poisson_lcdf(ub[n] | mu[n]), poisson_lcdf(lb[n] - 1 | mu[n]))
```

that is `lb - 1`, an **inclusive** lower bound, `P(Y >= lb)`, identical
to frmtmb's. So in brms, `trunc(lb = 6)` means `Y >= 6` while a
right-censored row recorded at 6 means `Y > 6`: the same number, two
meanings, on the same response. frmtmb's `trunc` matches brms bit for
bit, so its `cens` had to choose between matching brms's `cens` and
matching its own `trunc`. It chose self-consistency, and that is the
right choice.

Four supporting reasons, all checked:

1. It is what a recorded count means. "5 or more" is `P(Y >= 5)`.
2. It is the only reading consistent with the **existing**
   `simulate(censored = TRUE)`, which caps draws with
   `pmin(pmax(y, lo), hi)` (`R/predict.R:2727`). That records the value
   `k` exactly when the latent draw is `>= k`. Measured on 4000 draws
   from a fit censored at 7: simulated mass at the point 0.13250,
   against inclusive `P(Y >= 7) = 0.12190` and exclusive
   `P(Y > 7) = 0.05763`. Adopting brms's reading would silently break
   the correspondence between the likelihood and the simulator that
   `dharma_residuals()` rests on.
3. The censoring arithmetic exists in exactly one place (`row_lpdf()`,
   `R/objective.R:86-146`). There is no second copy to drift.
4. The divergence is stated with its remedy ("subtract one from every
   right-censored and interval lower bound").

**The cost is real and should not be minimized:** a brms user who ports
a censored count model gets a different likelihood with no runtime
signal. Documentation is necessary but not sufficient. See punch item 3.

## Findings, by severity

### 1. MEDIUM - the new refusal points family authors at a function that does not exist

`R/frame.R:1451-1459`. The whole `se()` capability gate rests on this
message telling an author how to opt in. It says:

> ... and reads it as `aterms[["se"]]` (see **`resid_sd()`** in the
> gaussian family for the `sigma = TRUE` convention).

`resid_sd` is `@noRd` (`R/families.R:548-557`), absent from `NAMESPACE`,
and in no man page. Verified:

```r
"resid_sd" %in% getNamespaceExports("frmtmb")   # FALSE
help.search("resid_sd", package = "frmtmb")     # no match
```

I hit this for real while writing a conforming custom family: calling
`resid_sd()` from an `lpdf` dies with `could not find function
"resid_sd"`. An author who follows the message gets nothing.

Same message, second gap: it names `accepts_aterms` but **not**
`required_aterms`, although `required_aterms = "se"` alone opens the
gate. All five declaration forms, measured:

| declaration | result |
|---|---|
| `accepts = NULL`, no required | REFUSED |
| `accepts = c("weights","se")` | ACCEPTED |
| `required = "se"` only, `accepts = NULL` | **ACCEPTED** |
| `required = "se"` + `accepts` | ACCEPTED |
| `accepts = c("weights")` | REFUSED |

The `frm_compat()` note for the same rule *does* say "or
`required_aterms`". The runtime message a user actually hits omits it.

### 2. MEDIUM - opening se() to custom families opens a new route to the exact pathology mixture() is refused for

`R/parse.R:1582`. The other half of `se()`, mapping out the residual
scale, is keyed on the dpar being **literally named `sigma`**:

```r
if (!is.null(ri$aterms[["se"]]) && !isTRUE(ri$aterms[["se_sigma"]]) &&
    "sigma" %in% fam[["dpars"]] && ...) pfix$sigma <- 1
```

`mixture()` is refused by name because its dpars are `sigma1`/`sigma2`.
But a custom family that declares `"se"` and calls its scale dpar
anything else now gets the term with the scale **not** mapped out, the
identical half-capability. Reproduced:

```r
odd <- frmtmb_family("oddscale", accepts_aterms = c("weights", "se"),
  dpars = c("mu", "tau"), links = list(mu = "identity", tau = "log"),
  lpdf = function(y, dpars, aterms) {
    sd <- if (is.null(aterms[["se"]])) dpars[["tau"]] else aterms[["se"]]
    RTMB::dnorm(y, dpars[["mu"]], sd, log = TRUE) })
frm(y | se(sev) ~ x, data = d, family = odd, se = TRUE)
```

fits, `tau` sits at its start value, and **every standard error is
`NaN`**: "The likelihood is FLAT in 1 direction: `tau_(Intercept)`".

That is the same measurement the lane records for mixture, which I also
reproduced by restoring the union (adding `"se"` back to the mixture
object's `accepts_aterms`): both component sigmas frozen at their shared
start value 0.4902396 on my data, and **all 7 standard errors `NaN`**.
The lane's 0.9794869 is the same quantity on their data; it is a
function of `sd(y)`, so the number is data-dependent but the pathology
is exactly as described. The mixture refusal is justified.

This hole is **newly opened by this lane** (before it, no custom family
could get `se()` at all). Mitigating: it is loud, not silent. frmtmb
warns and names the flat direction, which is far better than the old
behavior in "a silent wrong answer this lane fixes" below.

### 3. LOW-MEDIUM - the new refusal is missing from the help page of the function that throws it

`R/predict.R:2291-2301` (rendered to `man/residuals.frmtmb_fit.Rd:44-54`)
enumerates precisely which `osa` + `cens()` combinations are refused:

> ... row-varying censoring times and interval censoring are refused.

It was not updated with the discrete refusal that `R/predict.R:2229` now

page for `residuals()` does not. `grep -n discrete

### 4. LOW - the published site still states the opposite

`docs/` is tracked (1088 files) and `docs/articles/compatibility.md:83`
(and the `.html`, and `docs/search.json`) still says `cens()`
"additionally refuses discrete responses". This project rebuilds the
site in its own commit (`028a862`), so this is a release-step follow-up

Smaller relative: the `frm_compat("trunc()", "poisson")` note says only

### 5. NIT - an unreproducible figure

`R/families.R:307` states the poisson upper tail is "`-2773.28` at

### The convention (b) - exact everywhere I could reach

All four codes against a hand-written likelihood, evaluating the
objective at fixed parameters through `dry_run = "objective"`. Agreement
to `< 1e-12` throughout.

**poisson**, interior bounds and the support edge, several `b0`:
observed, right, left, mixed, **right at 0**, **left at 0**, right at 1,

at 0 exercises `F(-1)` and correctly contributes `log P(Y >= 0) = 0`.

**A custom binomial (n = 8) with `lcdf`, and again with `lccdf`** - the
only way to reach the binomial's `n` edge, because `binomial()` carries
no `lcdf` and so cannot be censored at all (confirmed by sweeping all 39

family). Right at `n`, right at 0, left at `n`, left at 0, interior both
sides, interval `[2,6]`, full-range `[0,n]`, top interval `[6,8]`,
one-point `[4,4]`, all four codes at once. Every case matches, and the
`lccdf` branch matches the `lcdf` branch exactly.

Composition with truncation, against a hand-written windowed likelihood:
`lb` only, `ub` only, both, with intervals, and with all four codes. All
exact.

Two documented consequences confirmed: a one-point discrete interval is
**bit-identical** to the uncensored fit, and a full-range interval
contributes exactly 0. On a continuous response `y2 == y` is still
refused.

Refusals fire with accurate messages: `trunc(lb = 0)`, non-integer `y`
bound, non-integer `y2`, `y2 < y`; and `y2 == y` is accepted on discrete,
as documented.

Contrast measured: with four rows right-censored at `b0 = log 4`, frmtmb
scores `-6.267728` where the strict/brms reading gives `-8.913370`, a gap
of 2.65 log units on four rows.

Also checked, all consistent: `weights()` multiply censored rows
correctly (hand likelihood with weights 1,3,2,1,4);
`simulate(censored = TRUE)` matches the inclusive reading (above);
`dharma_residuals()` genuinely works on the fit whose `osa` is refused,
as the refusal message claims; `fitted()` and `predict()` work.

### The refusals (d) - both justified, and quantified

**The `osa` refusal is not merely cautious.** Type-I censoring at
`lo = 1`, `hi = 7`, poisson, lambda-hat 4.112021. The window the `osa`
code builds is `F(hi) - F(lo) = 0.8582072789`; the window the inclusive
convention implies is `F(hi-1) - F(lo) = 0.7936227016`. The discrepancy
is the point mass at `hi`, 8.14 percent of the window. The naive PIT
therefore tops out at **0.92474478 instead of 1** at the top of the real
support, and the residual it would produce is wrong by +0.043, +0.065,
+0.101, +0.174, **+0.398** across `y = 2..6`. Refusing is right.

Not over-broad: a **continuous** censored fit still gets `osa` (gaussian
plus cens, 120 rows, NA on exactly the 3 censored rows), and an
**uncensored** discrete fit still gets `osa`.

**The poisson `lccdf` really does not tape.** Both halves confirmed:
exact in plain R (`RTMB::ppois(700, 400, lower.tail = FALSE,
log.p = TRUE) = -95.64565`, where `log(1 - F)` is `-Inf`), and inside
`MakeADFun` it fails with **"Non-numeric argument to mathematical
function"** - directly, and again through a frmtmb family declaring it.
The `log(1 - ppois(...))` form tapes fine. The slot genuinely cannot be
filled, not merely awkwardly.

## Item 2 - the lane's third rule is correctly placed

The rule keys on what the core can actually map out: under plain `se()`,
a family carrying `sigma` gets it mapped out and is trusted about its
other dpars; a declaring family with no `sigma` is refused if any dpar
survives `setdiff(dpars, c(primaries, spoken_for))`, and passes if none
does. Tested on the cases the lane did not:

| case | result | right? |
|---|---|---|
| two free dpars, neither named `sigma` (`mu,tau,kappa`) | REFUSED, names both, correct plural "are" | yes |
| declares `se` through `required_aterms` only (`accepts` NULL) | REFUSED | yes, `family_declares_aterm()` covers both |
| `student()` + `se()` | ACCEPTED, `sigma` mapped out, `nu` still estimated | yes, unchanged |
| `dpars = "mu"` alone (the `bcm_gaussian_probit` shape) | ACCEPTED | yes, nothing to map out |
| no `se()` in the formula | ACCEPTED | yes, guard correctly silent |
| `se(x, sigma = TRUE)` | ACCEPTED | yes, guard correctly silent |
| undeclared family with a loose dpar | the DECLARATION refusal fires first | yes |

The three ways out all work, and the lane's figures are exact: with
`se(sev, sigma = TRUE)` on data carrying extra scale 0.9, **tau-hat =
0.905871**, and the tau-named and sigma-named fits are **bit-identical**
(logLik -587.471663112497 both, difference exactly 0).

**The boundary claim is true, not a convenient framing.** Re-run with
`extra = 0`, so the whole spread is the known se, the estimated scale
collapses to 4.6e-02 with a log-scale standard error of 2.19, a factor
of about nine either way, i.e. unidentified. There is genuinely no
variance left to estimate, so the third test needs `extra > 0` for a
statistical reason rather than to dodge the rule.

### Residual observation A - a narrow over-refusal (LOW, not blocking)

The guard assumes a non-primary free dpar in a `sigma`-less family is
unread. That is not always so. A robust meta-analysis whose scale IS the
known se, and whose `nu` the density genuinely reads, is refused:

```r
frmtmb_family("t_known_scale", accepts_aterms = c("weights", "se"),
  dpars = c("mu", "nu"), links = list(mu = "identity", nu = "logm1"),
  lpdf = function(y, dpars, aterms) {
    s <- aterms[["se"]]
    RTMB::dt((y - dpars[["mu"]]) / s, dpars[["nu"]], log = TRUE) - log(s) })
```

`nu` is not flat. Fitting the identical likelihood with the se captured
in the closure, so no `se()` term is needed, estimates it cleanly:
**nu-hat 4.1262 against a true 4, standard error 0.2108, z = 5.41,
p = 6.4e-08, no NaN anywhere.** The refusal's stated reason, "left free
and unused, which is a flat direction and a NaN standard error", is
false for this family.

None of the three offered ways out fits it: there is no scale dpar to
rename, pinning `nu` destroys the thing being estimated, and
`sigma = TRUE` is a different model. A fourth does work: declare a
`sigma` the density never reads, purely so the core has something to map
out. That reproduces the closure fit exactly - **nu-hat 4.1262,
logLik -407.55469693 against the closure's -407.55469693**.

Why it is not blocking: it is a refusal, not a wrong answer; it is **not
a regression**, because before this lane such a family could not use
`se()` at all; and it is recoverable by a one-line change the first
offered remedy already gestures at. Worth a clause in the message ("or
declare a `sigma` the density ignores, so the core has something to map
out") rather than a code change.

### Residual observation B - pre-existing, and not this lane's

`spoken_for` lumps `names(pforms)` with `names(pfix)`, so giving a dpar
its **own formula** takes it out of `loose`, even though a formula makes
it more free rather than less. `bf(y | se(sev) ~ x, tau ~ 1)` therefore
slips past the guard into the pathology: every standard error `NaN`,
`tau` at 0. (`tau ~ x` likewise; the pinned `tau = 1` the message
recommends is genuinely fine.)

But this is **not new and not the lane's**. Built-in `gaussian()` does
the same thing, identically on both trees:

```
bf(y | se(sev) ~ x, sigma ~ 1) + gaussian()
  BRANCH: SEs NaN, NaN, NaN     MAIN: SEs NaN, NaN, NaN
  both warn "the likelihood is FLAT in 1 direction: sigma_(Intercept)"
```

So it is a general, loud, pre-existing property of asking for a modelled
scale while `se()` replaces the scale. Out of scope here; a later lane
could tighten `loose` to subtract only genuinely pinned dpars.
