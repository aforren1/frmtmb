## B1. The tape-node bound in test-perf.R

The test asserts `nodes(n = 1e5) / nodes(n = 1e3) <= 100` and justifies
it as "a + b n with a >= 0". The lane's own number is 99.40 (seeds 71
and 72). `dev/ciharden-rev-perfseeds.R` runs the test's own
`perf_census()` on 30 other seed pairs of the same GLM
(`perf-glm-a.txt`, `perf-glm-b.txt`):

| Model | seed pairs | over the bound | min ratio | max ratio |
|---|---|---|---|---|
| Poisson GLM, bound 100 | 30 | 13 | 98.618 | 101.040 |
| Poisson GLMM, bound 100 | 10 | 0 | 76.944 | 79.256 |

The per-row node count depends on the response values, so `a + b n`
with a constant `b` is false. The ratio follows the share of zeros in
the SMALL sample: correlation 0.86 over the 30 pairs; seeds 1025/1026
have 29.0% zeros at n = 1e3 against 26.8% at n = 1e5 and give 101.04;
seeds 2017/2018 have 24.1% against 26.9% and give 98.89. That is what
CppAD does with a product by a constant 0 or 1 (it records nothing), so
a row with `y = 0` costs fewer operations. The comment's "operations
TMB shares between equal inputs" is not the mechanism.

The test is deterministic at its seeds, so it will not flake on CI
today. But it is exactly the pattern lane-rules.md names ("a spectral
assertion that passed only on a pinned seed"): any change to the data
draw, to RTMB's recording, or to the objective that shifts per-row
counts by 0.6% fails it with no regression present.

The node count also cannot catch the regression the canary exists for.
`dev/ciharden-rev-perfmut.R` puts `dev/rtmb-pitfalls.md` item 14's
elementwise sub-assignment loop INSIDE the objective that
`build_objective()` returns and runs the test's own `perf_census()`
(`perfmut.txt`):

| n | nodes ratio (bound) | bytes ratio (bound) |
|---|---|---|
| 1e3 to 1e4 | 9.92 (10) | 97.0 (20) |
| 1e3 to 1e5 | 99.43 (100) | 9676.5 (200) |

The bytes half catches it by a factor of 48; the node half passes it.
The lane's arithmetic is right (96.6 for a tenfold n is caught, since
the tenfold bound would be 20, and the hundredfold ratio is about
9700), but it was measured on a separate RTMB objective, not through
the test; the run above confirms it through the test, in 44 s. Posit's
Linux R builds use `--enable-memory-profiling` (rstudio/r-builds
`builder/build.sh`), so the bytes half runs on the Ubuntu runners.

Fix: bound the node ratio by `2 * fold`, the same as the bytes ratio,
with the reason stated: the per-row count moves with the response
values (observed 98.6 to 101.0 over 31 GLM seed pairs), and the
regressions it guards are superlinear, about `fold^2 = 10000` for a
quadratic, so a factor of 2 loses nothing. Correct the comment: the
bytes count is the item-14 canary; the node count guards the tape's
size only.

One more number, not blocking: the lane reports a GLM bytes ratio of
58.81; in my process order (one warm-up call, then the pair) it is
97.31 for every one of 31 seed pairs. The bytes count of the small
call depends on what ran earlier in the process (one-time allocations
land in whichever call comes first). The headroom against the bound of
200 is therefore 2.06x, not 3.4x.

## B2. The gp() key for unseen rows

The lane made `pos_rowkey()` exact (`%a`) for unseen rows and kept
brms's 15-digit rule only for fitted positions, after running
`brms::standata()` on FITTING data. brms applies the same `.data_gp()`
to NEW data: `match_rows(Xgp, Xgp)` groups the new rows and
`.predictor_gp_new()` kriges one value per group.
`dev/ciharden-rev-brmsgpnew.R` (an empty brmsfit, no compile;
`brmsgpnew.txt`), new rows `u, u (1 + 2^-52), u, 1/3, 1/3 (1 + 2^-52)`
with `u = 10/3`:

    distinct doubles in newdata x: 4
    Jgp_1 (new rows -> new positions): 1 1 1 2 2
    Nsubgp_1: 2  rows of Xgp_1: 2

So brms 2.23.0 makes `u` and `u (1 + 2^-52)` one unseen position.
rellib-r6 did the same; the lane makes them two. The NEWS bullet "Two
unseen gp() positions that differ only past the 15th significant digit
are two positions" presents brms's behavior as a bug, which the
project tiebreaker (match brms unless brms is clearly wrong) does not
allow without a decision. The effect is nugget-sized (the covariance
of the two rows differs by `gp_nugget * sd^2`), so brms is not clearly
wrong.

It is also inconsistent inside frmtmb. With the lane, a new row equal
to a FITTED position to 15 digits is read as that position (brms's
rule, `gp_fit_poskey()`), while two new rows equal to each other to 15
digits are two positions (exact rule). One rule for both is brms's.

Fix: revert `pos_rowkey()` to brms's rule (or make it an alias of
`gp_fit_poskey()`), drop the NEWS bullet and the tests "the kriging key
is exact" (first half) and "two unseen positions one bit apart are two
positions", or invert the latter to pin brms's grouping. Keep the
`gp_krig_cov()` change. If the user wants the exact key as a deliberate
departure from brms, it needs that decision on record and a NEWS entry
that says "differs from brms" rather than "bug fix".
