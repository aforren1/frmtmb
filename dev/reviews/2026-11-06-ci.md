## MAJOR 1. `cran-lag.R` fails open: unreachable CRAN gives "nothing lags", exit 0

`available.packages()` only WARNS when an index cannot be read, and returns an empty
matrix. Every package then reads "not in any repository", which the script does not
count as bad. Runs on the user library:

| run | closure | current | LAGS | MISSING | not in any repository | exit |
|---|---|---|---|---|---|---|
| CRAN reachable (`review-ci-cranlag.log`) | 285 | 280 | 4 | 1 | 0 | 1 |
| mirror `http://127.0.0.1:9` (`-badmirror.log`) | 78 | 4 | 0 | 0 | 74 | **0** |
| proxy to `127.0.0.1:9`, both repositories down (`-offline.log`) | 73 | 0 | 0 | 0 | 73 | **0** |

Both bad runs end with `nothing lags`. The only sign is the R warning "unable to access
index for repository" at the top of the output. This is a release check that passes
when it checked nothing, the same failure the skip gate exists to prevent for tests. The
lane's record says "The 'nothing lags' exit path was not exercised"; it is reachable,
and it fires falsely.

The same rule hides a real case: a Suggests package that is in no repository and not
installed (a GitHub-only Suggests, for example) reads "not in any repository" with
installed `<NA>`, and the exit is 0.

Fix: turn the index warning into an error (`withCallingHandlers(..., warning =
function(w) stop(w))` around each `available.packages()`), stop when `ap_cran` has no
rows, and count "not in any repository" toward exit 1 (or list allowed names
explicitly). Test the three rows above.

### Limits (brms-likelihood and stan-next)

- **brms-likelihood: justified.** The job is 180 minutes and the identity tier step is
  120. The slowest cold identity tier measured is 88.3 min (5296 s, 24.04, 11-02), so
  the step is 1.36 times that. The worst job: 41 min of setup (3cd2a0c8, slow mirror)
  plus 120 plus about 2 for the gp and methods tiers is about 163, under 180. This is
  the test-coverage pattern: the job limit is wide, and the step limit catches a wedged
  run (coverage: about 45 + 105 = 150).
- **Steps after a timeout still run.** In both jobs, the gp and methods tiers carry
  `if: !cancelled() && steps.deps.outcome == 'success'`, so they run after an identity
  step that times out (failure, not cancel). Neither job has a skip gate. That a step
  timeout counts as a failure and not a cancel is still CI only.

### MINOR 1 (fix round): stan-next does not follow the pattern

stan-next has a 150-minute job limit and the same 120-minute step limit. With the
3cd2a0c8 slow setup (41 min), a wedged identity tier reaches the job limit first
(41 + 120 = 161). The job is then cancelled, and `!cancelled()` skips the gp and
methods tiers: the outcome the step limit was added to avoid. Its comment, "Wider than
the push job's 90 minutes", is also stale, because the push job is now 180. Give
stan-next 180 as well, or say why 150 is enough. It is a weekly reporting job, so this
does not block.

### Record step

`ubuntu-next.yaml`'s "Record the numerical libraries" step cannot fail on a GitHub
Linux runner. The new lines are `readLines("/proc/cpuinfo")` (always present there),
`cat(cpu[1])` (NA if no match, no error) and two `system(..., intern = TRUE)` calls,
each ending `; true`, so their status is 0 even when grep matches nothing or apt-cache
complains. R only warns on a non-zero status with `intern = TRUE`. The older
`gcc --version` line is the same as before. NIT: if this step ever fails, the check is
skipped, and so is the gate. `continue-on-error: true` on this step would make that
impossible by construction.

### NIT: a cold identity tier that hits its limit saves no compiles

In brms-likelihood, an identity tier that hits its 120-minute limit fails the job.
`actions/cache@v4` saves only from a successful job, so the programs it compiled are
lost and the next run starts cold again. This is not new: the old 90-minute cancel
lost them too. A separate `actions/cache/save` step with `if: always()` would keep
them. On 24.04 the cold tier was 49, 64 and 88 minutes on three successive weeks, so
watch it.
