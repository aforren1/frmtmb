## Findings (all MINOR)

1. **MINOR: extension addition terms keep the wrong rows that this lane
   removed for core terms.** All eight extensions are loaded, and the
   lane build reads as follows for bhaz(), dec(), ndt_group(), reward(),
   payoff() and stage2(): "works" with thres() and cs_pred() (12 rows,
   from `kind:aterm x kind:aterm` and `kind:aterm x kind:special`), and
   "untested" with disc, equidistant and sum_to_zero (18 rows, the `*`
   default). Log: `review-compat-extrows.log`. frm() refuses them. On the
   lane build: "cumulative: the addition term `dec()` is not one this
   family reads ..." for dec(two) with thres(3) and with sratio + cs(z),
   and "Addition term `bhaz()` is not supported for family 'cumulative'"
   for bhaz() (`review-compat-frm.log`). This was so before the lane, and
   the lane makes it no worse. But the NEWS sentence "each addition term
   that no ordinal family takes (`trials()`, ...)" is false for the table
   that users see with extensions loaded. The new test also limits itself
   to `core_aterms` on purpose. Fix: derive the refusal for every
   registered addition term that the ordinal families do not declare, as
   `compat_aterm_rules()` does from `accepts_aterms`. Or let each
   extension add `r("<term>", "group:ordinal_only", "refused")`. Until
   then, NEWS should say "core addition term". A blanket
   `kind:aterm x group:ordinal_only` rule is not a drop-in fix: weights(),
   subset() and index() would need (3,2) exceptions, and one status per
   exception would move their untested disc, equidistant and sum_to_zero
   rows.
2. **MINOR: the flow still cannot score a conditional row's refused
   half. p154 was spelled again to avoid the flow, and the flow was not
   fixed.** With the live row, a spec that meets the refusing condition
   reads "compat row wrong" and gives a false "refused" proposal (the
   lane's own `compat-diff-edit-out/p154`). The next row that moves from
   refused to conditional will do the same. The new spelling also drops
   the survey's only check that frm() and brms both refuse cens() beside
   cosy() on gaussian. In the tests, that refusal is pinned for ar() with
   weights(), cens(), trunc() and se() (test-autocor.R:540-549) and in
   brms for weights() + ar() (test-brms-agreement.R:629-638), not for
   cosy(). Fix this at consolidation, in `dev/equiv-flow.R`, which lane
   translator owns this round: when both refuse and the live row is
   "conditional", the verdict is "refusal correct" (the condition's
   refused half), not "compat row wrong". Or keep a second spec for each
   half.
3. **MINOR: `dev/equiv-measure.R` reads the live row before it loads
   any extension.** The sample's frozen statuses come from the
   all-loaded frame (`dev/equiv-dump-compat.R` loads all eight). Today
   the core-only and all-loaded statuses agree on 172 of 172
   (`review-compat-live.log`), but a contributed rule can override a
   core pair, and a sampled pair that has an extension feature would
   `stop("no frm_compat() row")`. Load the same extension list before
   `frm_compat()`, or say in the header that the live row is core-only.
4. **MINOR: the generated summary does not say that strata and verdicts
   use different statuses.** After the change, "Verdicts by stratum" shows
   `| refused | 5 (5) | 14 (14) | 0 (0) | 0 (0) | 0 (0) | 1 (1) |`. That
   is, five pairs of the refused stratum read "equivalent", which reads
   as a refused row that fits. `dev/equiv-summary.R` writes no sentence
   on this, and section 2.6 of `dev/equiv-findings.md` defines "compat
   row wrong" against "the table's status" without saying which one. Add
   one generated line: "strata are the status at the draw; verdicts are
   scored against the build's own row; N of 172 pairs differ". The data
   is already in `live_status`.

### R/parse.R: registered_aterm_of() and aterm_spelling()

`review-compat-keys.R` (log `review-compat-keys.log`) compares the old
rule and the new rule on every key of the real registry, with all eight
extensions loaded:

- Every real key maps to its own term: dec, ndt_group, bhaz,
  reward1..2, payoff1..4, stage21..22. The spelling is right too, for
  example `stage2(..., <column>)` for stage22.
- The old rule gave NULL for stage21 and stage22. The new rule gives
  stage2.
- The old rule took out-of-range keys (reward3, payoff5) as reward and
  payoff. The new rule gives NULL. The parser cannot produce those keys,
  because it refuses a wrong number of arguments.
- No core key reaches the registry: vint<k>, vreal<k>, trunc_lb and
  cens_y2 resolve in `aterm_base()` and `aterm_spelling()` first. A
  name that is a prefix of another does not match (pay arity 2 against
  payoff2). Arity above 9 works (a10, a11 and a12 of an arity-12 a).

The coerce side effect: stage21 and stage22 now get the coercion that
frmtmb.learn registered for stage2. That coercion is the default,
`as.numeric`, so numeric values do not change. stage2 now also counts
as a custom data term for newdata, and as an integer variable for
`conditional_effects()`. reward() and payoff() were treated that way
before. The frmtmb.learn test files that use stage2 pass on the lane
core (`review-compat-learn-*.log`):

| file | pass | fail | err | skip |
|---|---|---|---|---|
| test-counterfactual.R | 69 | 0 | 0 | 0 |
| test-families.R | 45 | 0 | 0 | 0 |
| test-reference.R | 12 | 0 | 0 | 0 |
| test-surface.R | 146 | 0 | 0 | 0 |
| test-stan-identity.R | 0 | 0 | 0 | 11 (gated) |

**R1, MINOR, from before the change, follow-up only.** Two terms can
claim the same key, and neither registration nor the parser stops it.
The new rule does not cause this. I built three cases:

- `x` (arity 3) beside `x2` (arity 1). `y | x2(z) + x(u, v, w)` parses
  to the keys `x2, x1, x3`. x's second argument silently overwrites
  x2(z), and then it gets x2's coercion. In the other order the parser
  refuses, but with the wrong text: "Duplicated addition term `x2()`".
- `a` (arity 12) beside `a1` (arity 2). The keys a11 and a12 get
  overwritten in the same way.
- `frmtmb_register_aterm("reward1")` beside reward (arity 2) is
  accepted. So is `frmtmb_register_aterm("vint1")` beside core vint().

On a clash, the old and the new rule both give the exact-name term
first. After that, the old rule took the name with the digits removed,
and the new rule takes the first match in registry order. Either way the
data is already wrong. No real extension has a clash. Fix:
`frmtmb_register_aterm()` refuses a name if any of its keys (`name`,
or `name1..k`) equals a key of a registered term or a core key
(`vint<k>`, `vreal<k>`, `trunc_lb`, `trunc_ub`, `cens_y2`,
`se_sigma`, `mi_sd`, `thres_gr`).
