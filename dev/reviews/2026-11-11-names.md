## Findings

### MINOR 1. `pars =` (regex) selections keep the stored order

brms's `as.matrix(fit, pars = )` is `extract_pars(pars, variables(x))`,
which gives `variables()` order. frmtmb.sample's
`draws_accessor_args()` (draws-brms.R 630), `draws_select_variables()`
(methods-draws.R 2221) and so `as.matrix()`, `as.array()`,
`as.data.frame()`, `as.mcmc()`, `posterior_interval()`, `mcmc_plot()`,
`pairs()` and `plot()` with `pars =` match against
`colnames(x$draws)`, the template order. Reproducer:
`names-review-draws.log`, every shape:

    mv  as.matrix(pars = regex) in variables order  FAIL
      pars= order: b_y_Intercept b_y_x b_y2_Intercept b_y2_z r_g__y[...]
    (variables(): b_y_Intercept b_y2_Intercept b_y_x b_y2_z sd_... r_...)

Fix: match against `variables(x)` in those two helpers (one line each).
`ps_select()` already does it for `posterior_samples()`. This is a
deprecated argument, so the fix is small. The NEWS bullet ("list the
draws in brms's order") is not true of it.

### MINOR 2. A `||` block is shown two ways

`confint_varcorr()$block` now reads `1 + f || g`, and
`1 + x | gr(g, cor = FALSE)` for a `gr()` term. `frm_multiple()`'s
`pooled_varcorr$grp` and the `summary()` table labels still read
`varcorr_trans_rows()$block` (`1 + f | g`). Reproducer:
`names-review-misc-lane.log`:

    [1] "1 + f | g"    (frm_multiple pooled_varcorr$grp)
    [1] "1 + f || g"   (confint_varcorr(fits[[1]])$block)

The lane says that `VarCorr()` and `diagnose()` stay as they are, but
`pooled_varcorr` is the multiple-imputation form of the same table.
Pass it through `block_display_label()` too (R/multiple.R 161).

### MINOR 3. NEWS gaps

- The `confint_varcorr()` `block` change is a value change that a
  reader may match on. It is not marked BREAKING, and the `gr(g, cor =
  FALSE)` label change (`1 + x | gr(g, cor = FALSE)`, was `1 + x | g`)
  is not mentioned.
- `ranef()` of a model WITH group terms AND a smooth used to list the
  smooth's block (`$s(x)`) and now leaves it out. The BREAKING bullet
  covers only models without group terms.
- frmtmb.sample: `summary()` of draws now lists rows in brms's order
  (methods-draws.R 364). The bullet names `posterior_summary()` but not
  `summary()`. The `posterior_epred()` observation-margin change is not
  marked BREAKING.
- The `insight::get_parameters()` change (names and values of the rows)
  is not marked BREAKING. One could argue it is a fix.

### MINOR 7. An absolute tolerance in the new core test

`tests/testthat/test-brms-layout.R` 107:
`expect_equal(h$hypothesis$Estimate, 0, tolerance = 1e-12)`. The target
is 0, so `all.equal()` falls back to an absolute difference. The
round's rule is a ratio to something the run measures. Compare the sum
of the three weights to 1 instead, where the tolerance is relative.

### MINOR 8. K families: a `mu2` formula or prior now fails against named data

`categorical(K = 3)` with a factor response `a b c` now resolves to
`mub muc`. `prior = set_prior(..., dpar = "mu2")` and
`bf(y ~ x, mu2 ~ 1)` then stop ("names no distributional parameter of
this model. It has mub, muc" / "dpar(s) not available ... mu2"). The
same call worked on base. Reproducer: `names-review-cat-lane.log`, the
last two blocks. The failure is loud, and NEWS states the rename. The
`?categorical` text ("`categorical(K = 3)` for a response already coded
`1..K`, which names the dpars `mu2 ... muK`") is still the first thing
it says about K. Add one sentence that formulas and priors take the
data's names when the data name the categories. Numeric codes 2..4 under
`K = 3` now give `mu3 mu4` (base: `mu2 mu3`). This is consistent with
`categorical()` without K.

### MINOR 9. Line endings

In the working copy, R/brms-names.R, R/fit.R, R/methods-fit.R and
dev/test-backlog.md are LF. The other lanes' copies are CRLF. Git
normalizes these on commit. A per-file merge at consolidation that does
not normalize sees whole-file conflicts. My merges normalized
(`tr -d '\r'`) and were clean.

## The lane's three questions: facts for the decision

1. Should ML `ranef()` and `coef()` stay 2-D? brms returns
   `levels x 4 x coefs` arrays (Estimate, Est.Error, Q2.5, Q97.5).
   frmtmb.sample's draws methods already do. frmtmb's ML methods return
   lme4's `levels x coefs` (`condSD` attribute; `coef()` a data frame).
   If they move to 3-D, the following break: 86 test or vignette files
   that call `ranef()`, of which 20 index a 2-D entry (28 sites, e.g.
   `ranef(fit)$g[, "x"]`, test-mm, test-tre, test-sugar, frmtmb.spatial
   test-car, frmtmb.ode test-ode, `vignettes/spectral.Rmd`).
   `as.data.frame.ranef_frmtmb()` and `print()` also break, and so does
   every lme4-shaped reader (broom.mixed-style long form). The ported
   rows `brmsfit-methods:811`, `:814` and `:136` would move from
   divergence. One line: keep 2-D. brms's 4-slot layer has no ML content
   besides `Est.Error` from `condVar`.
2. Should frmtmb keep answering where brms stops? brms's
   `coef()` of a model without group terms stops ("The model does not
   contain group-level effects."), and so do `ranef()` and `coef()` of a
   gp-only or car-only model. frmtmb returns the coefficient vectors and
   the gp field. The same question covers frmtmb.spatial's CAR and SPDE
   fields: test-car.R (14 sites) and test-spde.R read `ranef(fit)[[1]]`
   as the field, and test-gp-noncentered.R reads the gp field. To stop
   would break those readers and leave no accessor for the field's
   conditional modes. One line: keep, as documented.
3. Should `x$draws` keep the stored order? brms stores draws in
   `variables()` order. frmtmb keeps the template order in `x$draws`
   and permutes in every accessor. On every shape above, the two orders
   hold the same columns with identical values by name. Readers of
   `x$draws` by position: `draws_outer_index()`,
   `draws_internal_matrix()`, the `laplace = TRUE` skip of `b` and
   `miss`, prior-draws.R, sample.R 1285 and 1301, and loo.R 20. They
   would all need a permutation map. A user who reads `x$draws`
   directly sees a different order from `variables()`. One line: keep
   it, and say in `?frm_sample` that `x$draws` is not in `variables()`
   order.
