## Findings, by severity

### 1. MEDIUM. `acat()` refuses non-logit links with a reason that is false

`R/families.R:2915` calls `ord_link(link, "acat", "logit")`, and
`ord_link()` at `R/families.R:2660` carries one message written for the
general ordinal case:

    acat(): link must be one of "logit". An ordinal link names the
    distribution function the thresholds are read through, so it has to
    map onto (0, 1); you gave character "probit". See ?`frmtmb-links`

`probit` does map onto (0, 1). So does `cloglog`, and `cauchit`, and
`softit`. brms accepts every one of them for `acat`. The stated reason
is the reason `cumulative()` refuses `log`, and it is not the reason
`acat()` refuses `probit`.

Reproduction:

    frmtmb::acat(link = "probit")     # the message above
    brms::acat("probit")              # accepted

The real reason is correct and is recorded, but not where the user
lands. `R/families.R:4861`, rendered into `man/frmtmb-families.Rd:327`,
and the NEWS bullet both say `acat()` takes `logit` alone because brms
defines its other links by a different density.

The justification itself is VERIFIED. `brms:::inv_link_acat()` branches
on the link. On the logit it forms `c(1, cumprod(exp(x)))` and
normalizes. Off the logit it forms
`c(1, cumprod(F(x))) * c(rev-cumprod(1 - F(x)), 1)` and normalizes,
which is a product of distribution functions times a reversed product of
survivals, exactly as the lane says. It is not the logit expression with
a distribution function substituted for the logistic, so routing it
through the registry would not reach it.

One correction to the lane's framing. That second branch reduces to the
first when `F` is logistic, so it is a coherent generalization of the
same model rather than an unrelated density. The honest statement is
that implementing it needs a new density path, not a registry lookup,
and the lane declined to write one. That is a fine scope call. The
message should say so.

## The two latent bugs

Both are real. Neither was LIVE on the base, because the argument that
triggers each did not exist there: `negbinomial()` was
`function(link = "log")` with `shape` pinned to `"log"`
(`R/families.R:1090` on the base), and `fam_cratio()` gated its robust
branch on `identical(link, "logit")`. Both are therefore latent bugs the
lane's own feature would have activated, which is what the lane claims.
I reproduced each against the base's code by making the construction the
new argument makes routine.

### Bug 1: `log_dpar()` and `gate_logs()` assumed the link

Base code returned the linear predictor AS the log of the dpar:

    log_dpar <- function(dpars, name) {
      e <- dpars[[paste0(".eta_", name)]]
      if (is.null(e)) log(dpars[[name]]) else e
    }

Reproduction against `rvl2-main-lib`. Take the base's own negbinomial
family object, put a softplus on `shape`, and evaluate its `lpdf` under
the objective's contract (`dpars[[d]] = linkinv(eta)`,
`dpars[[".eta_d"]] = eta`), at `eta_shape = 0.5`, so `shape = 0.974077`
and the true `log(shape) = -0.0262649`:

    y            0        1        2        3        4        5        6
    base lpdf   -1.70905 -1.64703 -1.80408 -2.04630 -2.33398 -2.64997 -2.98528
    dnbinom     -1.36961 -1.67705 -1.97128 -2.26114 -2.54882 -2.83520 -3.12071

Max error 0.339 nats at one point, 0.608 over the seven, no warning and
no error. The base answer is reproduced EXACTLY by
`dnbinom_robust(y, log(mu), 2*log(mu) - eta_shape)`, which is the
misread the lane describes.

Worktree, `negbinomial(link_shape = "softplus")`, same inputs: max
absolute error against `dnbinom()` is 8.88e-16, and the misread formula
no longer matches.

The `gate_logs()` sibling behaves the same way. Base `fam_zi_poisson()`
with an identity link on `zi = 0.3`, `mu = 2.5`, `y = 0:3`: base gives
`-0.4953 -2.4381 -2.2149 -2.3972` against the truth
`-1.0287 -1.9404 -1.7172 -1.8996`, an error of 0.533 nats, because it
reads the probability 0.3 as a log odds and uses `plogis(0.3) = 0.5744`.
Worktree with `zero_inflated_poisson(link_zi = "identity")` is exact to
2.2e-16.

Every call site is converted: 3 `log_dpar()` and 10 `gate_logs()` calls,
the same counts as the base, all now passing the dpar's own link object.

Generalized check, stronger than the two cases. For each of the 37
(family, dpar) pairs that gained a `link_<dpar>` argument, I fixed the
dpar at one NATURAL value and evaluated the family's `lpdf` once per
allowed link, feeding each link's own `linkfun` of that value as the
linear predictor. The density must not depend on which link produced the
same number. All 37 pairs agree, 34 with spread exactly 0 and the rest
at 1.8e-15. That covers every family the lane touched, not only the two
it names.

## Blocker 1, the acat message: FIXED

`fam_acat()` at `R/families.R:2947` now calls its own `acat_link()` at
`R/families.R:2704` instead of the generic ordinal resolver. Measured
message:

    acat() takes the 'logit' link only, and not because character "probit"
    is a bad link: brms accepts "probit", "probit_approx", "cloglog",
    "cauchit" and "softit" here, and they all map onto (0, 1). frmtmb
    refuses them because off the logit brms computes a category probability
    from a SECOND expression, a product of distribution functions times a
    reversed product of survivals. It agrees with acat's log-linear form
    when the distribution function is logistic, so it is the same model
    generalized, but it is a density frmtmb has not written, and
    substituting a distribution function into the log-linear form does not
    reach it. cumulative(), sratio() and cratio() do take these links.
    See ?`frmtmb-links`

Every complaint is answered: it says the link is not the problem, names
the five links brms takes, states the real reason, and points at the
three families that do take them. `acat()` still accepts `logit` and
nothing else.

restatement. I applied its three clauses to the OLD message text:

### The framing correction is right, and I verified it

The lane is correct and the sentence both the coordinator and I were
using was wrong. It is NOT that brms defines acat's other links by a
different density.

Measured. Taking brms's non-logit branch, hand-coded as
`c(1, cumprod(F(x))) * c(rev cumprod(1 - F(x)), 1)` normalized, and
evaluating it at `F = plogis`, against `brms:::inv_link_acat(x, "logit")`
on a 5 by 3 array of linear predictors:

    max absolute difference = 1.11e-16

So the second expression REDUCES to the log-linear form at the logistic.
It generalizes the same model rather than replacing it. The accurate
statement is the lane's: reaching it needs that second expression
written and taped, and substituting a distribution function into the
log-linear form does not get there. That is now what the error message,
the `frmtmb-links` topic at `R/links.R:88` and the NEWS bullet all say.
It is a better sentence than the one it replaced and it should stand.

I had already flagged this correction in the first round under finding
1; the lane has now made it the wording everywhere, which is the right
outcome.
