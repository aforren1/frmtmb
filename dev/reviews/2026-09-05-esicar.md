## 1. EQUIVALENCE

### 1a. On paper

Write `b` for the block's `Nloc` parameters, `s_j` for the indicator of
connected component `j` (`n_j` levels), `L = D - W`, and

    P0 = sum_j kappa_j s_j s_j',   kappa_j = 1 / (con_sd n_j)^2.

`null(L) = span{s_j}` and `range(P0) = span{s_j}`, and the `s_j` have
disjoint support, so `L` and `P0` are simultaneously block diagonal on
the orthogonal split `R^n = span{s_j} + span{s_j}^perp`. In an
orthonormal basis adapted to that split, with `u_j = s_j / sqrt(n_j)`,

    P0 u_j = kappa_j n_j u_j,   L u_j = 0,
    tau L + P0 = diag(P0_c, tau L_r),   L_r = L restricted to range(L).

Three consequences follow, and they are the whole design.

1.  `|tau L + P0| = |P0_c| tau^(n-c) |L_r| = tau^(n-c) |L + P0|`, so
    `log|Q| = (n - c) log tau + log|K|` with `K = L + P0` exactly the
    matrix `icar` already builds. No new factorization.
2.  Writing `b = f + sum_j m_j s_j` with `f = C b` the per-component
    centered part and `m_j = s_j'b / n_j`, the density factorizes as
    `p(b) = p_hard(f; tau) * prod_j N(m_j; 0, con_sd^2)`. The variance
    of `m_j` is `con_sd^2` whatever `n_j` is, because the eigenvalue is
    `kappa_j n_j = 1 / (con_sd^2 n_j)` and `var(m_j) = var(a_j) / n_j`.
    It carries no tau.
3.  The predictor sees `C b = f` alone, because `expand_b()` centers, so
    the `m` integral is exactly 1 and the marginal likelihood of the
    data is the hard-constrained one.

Laplace exactness. The joint negative log density in `(f, m)` is
`nll_data(f) + 0.5 sum_j kappa_j n_j a_j^2 + const`, with no cross term,
so the Hessian is block diagonal and `m* = 0` exactly: the block is
quadratic, so one Newton step lands on it. The `m` block's three Laplace
contributions cancel to exactly zero,

    -0.5 sum log(kappa_j n_j)          from nll(b*)
    +0.5 sum log(kappa_j n_j)          from 0.5 log|H|
    +0.5 c log(2pi) - 0.5 c log(2pi)   from the 2pi bookkeeping

so the marginal is the hard-constrained marginal with no residual
constant at all, and the inert coordinate cannot move the optimum: it
enters neither the data term nor any cross term, its gradient is
`kappa_j n_j a_j`, which vanishes only at `a_j = 0`, and its Hessian
block is positive and constant in every other parameter. For the whole
model the integrand is Gaussian in `b`, so the Laplace approximation is
exact for both parameterizations, not merely accurate.

The constant against brms. brms's target contribution for the field is
`0.5 ((Nloc-1) log tau - tau phi'L phi)`, and frmtmb's log density at
`b = phi`, already centered so that `b'P0 b = 0`, is
`0.5 ((n-c) log tau + log|K|) - 0.5 n log 2pi - 0.5 tau phi'L phi`. With
`c = 1` the tau terms cancel identically and

    brms - frmtmb = 0.5 Nloc log(2 pi) - 0.5 log|K|,

free of tau, beta, sigma and the data. Decomposed independently through
the pseudo-determinant, the same number is
`0.5 n log 2pi - 0.5 log|L|* + log(con_sd) + 0.5 log(n)`.

## 2. THE HARD-CONSTRAINED REFERENCE, MINE

I did not reuse the lane's. Mine is the marginal Gaussian

    y ~ N(X beta, sigma^2 I + sdcar^2 Z A (A'LA)^-1 A' Z')

with `A` an orthonormal basis of `null(L)^perp` from an eigendecom-
position, beta profiled by GLS, optimized over `(log sdcar, log sigma)`
and then Newton-polished with numDeriv to `|grad| = 2.8e-9`. I built the
drop-one-per-component version too, `B = rbind(I, -1')`:

    max |B(B'LB)^-1 B' - A(A'LA)^-1 A'| = 7.8e-16
    max |A(A'LA)^-1 A' - pinv(L)|       = 1.1e-15
    logLik(drop-one) - logLik(orthonormal) = 0 exactly

the paper argument requires.

The singleton is HANDLED, not refused, and handled correctly: with
`n_j = 1` the centering `b_i - b_i` is identically zero, so the

`escar` still refuses a zero-degree location by name; `icar` and
`esicar` do not need to. Over 300 draws from the disconnected fit the
singleton came back exactly 0 every time and the per-component draw
sums stayed at 1.1e-15.

The per-component design is a deliberate and correct divergence from
brms, which constrains the GLOBAL sum only (`rcar[Nloc] = -sum(zcar)`)
and so leaves a two-component intrinsic field improper. It is argued in
`R/covstruct.R` and in `dev/brms-likelihood-tests.md`. Note that the
same per-component choice is PRE-EXISTING in `icar` and `bym2`, whose
`K` uses `kappa_j = 1/(con_sd n_j)^2` per component where brms writes a
single `normal(sum(zcar) | 0, 0.001 Nloc)`.

Gap: there is no test for a singleton component anywhere in
`tests/testthat/test-car-spde.R`. The disconnected test uses two 2x3
lattices, both of size 6. The behavior is right; nothing pins it.

Three things are settled by that table. My reconstruction reproduces

is the inert coordinate's posterior variance and nothing else. And the
excess scales by exactly 100.0000 per decade of `con_sd`, which
confirms the diagnosis rather than merely being consistent with it.

`ranef(condVar = TRUE)` leaks the same way: condSD ranges
0.186381840..0.198433828 at con_sd 1e-2, 0.186116067..0.198184218 at
1e-3 (the lane's 0.186 to 0.198) and 0.186113407..0.198181720 at 1e-4,
the same `con_sd^2` scaling. `VarCorr()` is clean: `sd(car)` equals
`exp(theta[1])` to the last bit, uncontaminated.

### Is leaving the Jacobian for a sibling acceptable?

At the default con_sd, yes. 1.3e-5 relative in a standard error is five
orders below the quantity and far below any digit anyone reports; the
alternative was a cross-lane edit to `R/predict.R` for no measurable
gain, and the lane measured and documented it rather than hiding it.

But the accompanying documentation is what makes it dangerous, and that
is a real finding. NEWS says "`con_sd` has no effect on an `esicar`
term", the vignette says "`con_sd` on an `esicar` term is ignored", and
`R/compat.R:1190` says "con_sd, which esicar ignores". All three are
false as written: con_sd has no effect on the LIKELIHOOD, but it scales
the inert coordinate straight into every delta-method standard error
and every ranef condSD, as `con_sd^2` in the variance. A user who reads
"ignored" and sets `con_sd = 0.1` on an esicar term gets a prediction
standard error inflated by roughly 12 percent
(`0.01 / 0.04` in the variance) with no warning anywhere. The exact
Jacobian can wait; the word "ignored" cannot.

Cheapest durable fix, and it is in the lane's OWN file: since the
coordinate is inert, its scale is arbitrary, so pin esicar's `kappa_j`
to the default constant instead of the user's `con_sd`
(`R/covstruct.R:1283` feeding `car_esicar_prec()` at :1320). That makes
"con_sd is ignored" literally true for every reported quantity and caps
the delta-method leak at 1.3e-5 permanently. Second choice: qualify the
three sentences. Third: warn when `con_sd` is passed with `esicar`.

`bvec <- if (isTRUE(frame[["has_rr"]]))` line byte identical to base, so

Semantic overlap, which is the question that matters. The spline lane's
penalized block DOES go through `expand_b()`: `ps()` registers a
component with `covstruct = "smooth"` and a deliberately zero `Zlocal`
(`R/frame.R:1482ff` in that lane), so it becomes a real entry in
`frame$re_blocks` and `expand_b()`'s else branch copies
`b[b_idx] -> cvec[c_idx]`, the identity. The spline lane already relies
on this: its own comment says the ps closure reads "coefficient space,
not parameter space ... the closure reads the expanded vector", and
`objective.R` hands `ps_env()` the post-expansion `bvec`.

Would `has_expand` gate it wrongly? No, in both directions. A ps-only
model has `has_rr = FALSE` and `has_esicar = FALSE`, so `has_expand` is
FALSE, `bvec = bfull`, which is byte-for-byte the base behavior and
correct because b-space equals c-space when no rr block is present. A
ps + esicar model has `has_expand = TRUE`, so `expand_b()` runs, centers
the car block and passes the ps block through unchanged. The one way it
could have broken - a ps block whose `c_idx` positions are not covered
by `re_blocks`, which `expand_b()` would leave as zeros - does not
happen, because ps registers a component.

### The one defect in these three lines

`R/objective.R:253` gates strictly, `isTRUE(frame[["has_expand"]])`,
while `expand_b()` itself (`R/covstruct.R:1757`) carries a fallback,
`frame[["has_expand"]] %||% frame[["has_rr"]]`. The two disagree, and
the fallback is on the wrong one: `[[` does not partially match, so a
frame serialized under 0.51.0 or earlier returns NULL and
`build_objective()` silently stops expanding.

Three call sites rebuild the objective from a STORED frame:
`R/importance.R:1110` (`fr <- fit[["frame"]]`), `R/sandwich.R:317`
(`frame <- fit$frame`), and `R/fit.R:715` (fresh, safe).
`R/predict.R:40` and `:537` call `expand_b()` unconditionally and so
take the fallback and stay correct.

Measured, not argued. For an `rr` fit whose frame I stripped of
`has_expand`, `build_objective()` fails loudly with "non-conformable
arguments" (b-space and c-space have different lengths there). For an
ESICAR fit the lengths match, so nothing errors: at the stored estimates
the two objectives agree exactly (74.8856145292 both, because `m* = 0`),
but shifting the block by 0.37 gives 68524.8856145 with the flag and
68552.2990732 without. Off the mode they are different models, silently,
which is precisely the regime `imp_frozen_proposal()` and
`cluster_scores_at()` operate in.

Severity is low: `has_expand` is new, no released version wrote a frame
without it, and NEWS already tells esicar users to refit. The fix is one
token, `%||% frame[["has_rr"]]` at `R/objective.R:253`, making the gate
agree with the fallback that `expand_b()` already has.
