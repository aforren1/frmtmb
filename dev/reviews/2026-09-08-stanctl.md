and F5 must land before a second package registers a refused row, and

### Was the `control` / `fit_control` redirection the right call?

**Yes, and the reasoning holds up under checking rather than only
under reading.**

- `docs/SPEC.md:456` says "brms code ports mechanically, priors
  included" and then names `frm_sample()` as one of the three
  functions that spell an argument the brms way for that reason. The
  precedent the lane invoked is explicit, not inferred.
- `docs/SPEC.md:149` fixes core's Imports with "No Stan, no compiled
  code of our own, no brms", so putting `adapt_delta` into
  `frmtmb_control()` would have made core validate an option set it
  has no dependency on and would have let `frm()` accept an argument it
  ignores. Correctly rejected.
- `as_tmbstan(fit, ...)` has no `control` formal at all, so `control`
  already reached rstan there. `stan_control` would have made three
  conventions inside one package. Verified by reading
  `extensions/frmtmb.sample/R/sample.R:1878-1884`.
- The argument was not doing useful work under the old name on the
  route that matters. See "the silent ignore" below.
- The break is loud. Every old shape I could construct is refused by
  name with a message that names `fit_control`.

The redirection's one real cost is F2, and F2 is an eight-line fix,
not a reason to prefer `stan_control`. The lane should keep the
redirection.

## Findings

### F1 (must fix). `contro =` reaches rstan's `control` through the dots and bypasses `check_stan_control()` entirely

`extensions/frmtmb.sample/R/sample.R:1495-1496` says:

    # `control` is matched exactly (it follows `...` in the formals), so
    # it can never also be in `...`; nothing has to reconcile two of them

The premise is true and the conclusion does not follow. `control`
cannot bind twice, but a partial spelling lands in `...`, and `...`
goes to `tmbstan::tmbstan()` and then to `rstan::sampling()`, whose
S4 method takes `control` before its own `...`. So R partial-matches
it there. Measured (`.../scratchpad/rvsc-p2-dots.R`):

| call | `stan_args[[1]]$control` |
| --- | --- |
| `frm_sample(fit, control = list(adapt_delta = 0.97))` | `adapt_delta=0.97` |
| `frm_sample(fit, contro = list(adapt_delta = 0.97))` | `adapt_delta=0.97` |
| `frm_sample(fit, cont = list(adapt_delta = 0.97))` | `adapt_delta=0.97` |

The consequence is not cosmetic. The two refusals this lane built are
both bypassed by the same route, and the second lands on exactly the
mis-report the lane says it exists to prevent:

    frm_sample(fit, contro = list(nonsense = 1))
    # rstan prints: 'control' list contains unknown members of names: nonsense.
    # frm_sample(): the sampler returned no draws ... A known case: a tape
    #   that calls an external solver can fail inside tmbstan ...

    frm_sample(fit, contro = frmtmb_control())
    # rstan prints: 'control' list contains unknown members of names:
    #   optimizer, optCtrl, restarts, grad_tol, ...
    # frm_sample(): the sampler returned no draws ... external solver ...

So a user who mistypes the argument the lane just renamed is told the
model's tape called a failing external solver. Note that rstan already
rejects a genuinely unknown dots name (`fit_contro` gives "passing
unknown arguments: fit_contro."), so the hole is precisely the
partial-match set of rstan's own formals, and `control` is the one
member of that set the package now validates itself.

Fix: at `sample.R:1622`, where `args$control` is assembled, refuse any
dots name that `pmatch`es `"control"`, or simply run
`check_stan_control(args$control, ...)` on the assembled list rather
than on the formal alone. About four lines, and a test the current
file has no analogue of.

The lane recorded, and left, that `fit_control`, `start`, `data2`,
`na.action` and `REML` are silently ignored on the fit route while
`data` and `family` are refused by name. I confirmed all of it, and
found it is worse than "ignored": none of the five is validated
either, so complete nonsense is accepted in silence.
`.../scratchpad/rvsc-p1b-silentargs.R`, all on a fitted object, chains
= 1, iter = 60, seed = 3:

| argument | result |
| --- | --- |
| `fit_control = frmtmb_control(optimizer = "nlminb")` | no error, draws bit-identical to the plain call |
| `fit_control = "garbage"` | no error, draws identical |
| `fit_control = list(adapt_delta = 0.99)` | no error, draws identical |
| `start = list(beta = c(999, 999))` | no error, draws identical |
| `start = "nonsense"` | no error, draws identical |
| `data2 = "nonsense"` | no error, draws identical |
| `na.action = "nonsense"` | no error, draws identical |
| `REML = TRUE` | no error, draws identical |
| `REML = "nonsense"` | no error, draws identical |
| `data = dd` | refused by name |
| `family = gaussian()` | refused by name |

Four of these five predate the lane and "out of scope" is a fair call
for them. `fit_control` does not: it did not exist before this change.
The lane fixed "a sampler list bound to the fit-time argument is
discarded" and, in the same edit, created "a sampler list bound to the
new fit-time argument is discarded", with the extra sting that
`fit_control` is the name the refusal message points a confused user
at. `frm_sample(fit, fit_control = list(adapt_delta = 0.99))` samples
four chains with rstan's defaults and says nothing.

Fix: on the fit route, refuse any of the five when supplied, the way
`data` and `family` are refused, using `missing()` so a default is not
mistaken for a value. Eight lines and one test block. Closing all five
together is better than closing one, and is small enough to do here.

### F3 (fix before a second refused row). The pre-flight matches on `key`, and keys are not unique across display names

`sample_preflight()` (`sample.R:1201-1206`) resolves a row's display
name to `frm_compat_features()$key` and matches that against the
formula's call names. Three keys are shared by two display names each,
and core created that on purpose. `R/compat.R:867` says so:

    # The special vocabulary collides with the covariance vocabulary: gp,
    # cs and mi name both a bar-term structure and a predictor special.
    # Display names disambiguate; these keys map back to the parser.

The pre-flight throws that disambiguation away. Audit over all seven
extensions loaded (`.../scratchpad/rvsc-p4-audit.R`, 138 vocabulary
rows):

| name | key | kind |
| --- | --- | --- |
| `cs` | cs | covstruct |
| `gp` | gp | covstruct |
| `mi()` | mi | aterm |
| `mi_pred()` | mi | special |
| `gp_pred()` | gp | special |
| `cs_pred()` | cs | special |

Constructed, `.../scratchpad/rvsc-p4-collide.R`:

- a `refused` row on `mi_pred()` refuses `bf(y | mi() ~ x)`, which
  writes the ATERM;
- a `refused` row on `mi()` refuses `bf(y ~ mi(x))`, which writes the
  PREDICTOR SPECIAL.

Both are false refusals, and the lane rules say a check that fires on
a correct model is worse than no check. Latent today, because
`frm_ode()` is the only refused row and its key is unique. It stops
being latent the moment anyone registers `mi_pred() x frm_sample`.

Fix: match on `sub("[(][)]$", "", feature_b)` rather than on `key`, or
carry the row's `kind_b` into the lookup so the aterm row and the
special row do not resolve to the same string. The current fallback at
`sample.R:1204` already computes exactly the right thing and is used
only when the vocabulary does not carry the row.

### F4 (fix the claim). "The parentheses convention keeps a base R collision out" is false as written

The claim lives in the block comment above `formula_call_names()` in
`extensions/frmtmb.sample/R/sample.R` and in
`dev/stanctl-findings.md` section 2.4. Both argue that matching on the
display name's parentheses is what keeps a base R collision out, on
the grounds that `exp`, `diag` and `cs` have no parentheses so `exp(lka)`
in a nonlinear body cannot be mistaken for the `exp` covariance
structure. That narrow claim is true and I verified it: a `refused`
row on `exp` warns and samples rather than firing on `exp(lka)`.

The general claim is false. Four parenthesized display names are also
functions reachable at run time, and one of them is in base:

| name | key | kind | also a function |
| --- | --- | --- | --- |
| `trunc()` | trunc | aterm | `base::trunc` |
| `weights()` | weights | aterm | `stats::weights` |
| `ar()` | ar | autocor | `stats::ar` |
| `ps()` | ps | special | on the search path |

Constructed: a `refused` row on `trunc()` refuses
`bf(y ~ a * trunc(x), a ~ 1, nl = TRUE)`, whose `trunc` is base R
arithmetic. The convention that actually holds is narrower than the
one written down: it is that the three covstructs the lane happened to
test are spelled without parentheses. Fix the comment and the matching
sentence in `?frm_sample`; the code is unchanged by this finding.

The other direction of the same audit is worth recording: 24
covariance structures plus `hmm`, `lca`, `mixture` and `rescor` ARE
written as calls in a formula and have no parentheses in the
vocabulary, so a refusal registered on any of them warns and samples.
`hmm` and `lca` are the two the plan's own check names.

`?frm_sample` itself is not wrong here. It says only what the check
CAN see, not that the convention is airtight, so the fix is to the
comment and to the findings, not to the manual page.

### F5 (live gap). `as_tmbstan()` is unguarded and still poisons the session

The lane verified that `as_tmbstan()` needed no change for the
`control` collision, and that is correct: it has no `control` formal,
`...` goes to tmbstan, and the two entry points now agree in spelling
and in meaning. I confirm that half.

But `as_tmbstan()` gets no pre-flight, and it is the escape hatch
`vignette("posterior-diagnostics")` used to send divergence-hit users
to. On the same fixed-effect-only ODE fit
(`.../scratchpad/rvsc-p5-astmbstan.R`):

    as_tmbstan(ofit, chains = 1, iter = 30)
    # DLSODA / "Error : Wrong output length"
    # returned a stanfit with 0 chains
    # elapsed 1.79 s, NO ERROR RAISED

`as_tmbstan()` hands back an empty `stanfit` with no complaint at all;
`frm_sample()` at least catches `!length(sf@sim)`. And the session
damage is real. `.../scratchpad/rvsc-p4-poison.R` samples a plain
gaussian model, provokes the abort through `as_tmbstan()`, then
samples the same plain model again:

    BEFORE the ODE abort   OK, 30 draws, lp__ mean -62.553
    ... "Error : Wrong output length" ...
    AFTER the ODE abort    Error : empty_nested() must be true before
                           calling recover_memory()
    AFTER, second attempt  same

That is the registry note's own claim ("takes the R session's rstan
state with it") verified end to end, and it says the refusal covers
one of the two doors. `?frm_ode`'s new "Sampling an ODE fit" section
names only `frm_sample()`, so a reader is told the package protects
them and is not told which call is unprotected.

Fix, either: call `sample_preflight(fit)` from `as_tmbstan()` too, or
say in `?frm_ode` and in `?as_tmbstan` that the escape hatch is
deliberately unguarded and why. The first is three lines.

### F6 (small). The pre-flight is placed after the rstan and tmbstan namespace loads, so a refused model does not cost "one registry read"

`sample.R:1493-1511`: `refuse_retired_priors()`, then
`check_stan_control()`, then `as_priorlist()`, then
`requireNamespace("tmbstan")` and `requireNamespace("rstan")`, then
the `reparameterize` check, and only then `sample_preflight()`.
`check_tmbstan_build()` is not in the way (it is a static read of the
installed `model.hpp`, called at `sample.R:1658`, after the
pre-flight), so there is no Stan call; the cost is namespace loading.

Measured on a quiet machine, `.../scratchpad/rvsc-p4-warmtime.R`,
with an empty-closure control at 8 microseconds so the instrument is
visible:

| | seconds |
| --- | --- |
| first `frm_sample()` of a fresh session, ODE fit | 3.05 and 3.45 over two runs |
| the same, warm, 8 repeats | min 0.111, median 0.120, max 0.144 |
| `sample_preflight()` alone, warm, control arm 0.984 | 0.070 to 0.084 |
| the unguarded failure it replaces, reference build | 2.88 |

So the refusal is SLOWER on the first call of a session than the
failure it replaces (3.05 s against 2.88 s), and the difference is
namespace loading that the successful path would pay anyway. What the
refusal buys is not time, it is the session, which is the real
argument and which the lane states honestly. The lane's warm figures
(min 0.097, median 0.108) and mine agree within 15 percent; its 2.48 s
first call and my 3.05 s differ by machine load.

The pre-flight needs nothing from rstan. Moving it above the
`requireNamespace()` block would make the lane's own sentence ("so a
refused model costs one registry read") true, at the price of changing
which error a user without tmbstan installed sees. I did not make the
change because that precedence is a judgment call, but the sentence in
the code comment and in `?frm_sample` should either be earned or
softened.

### F7 (measured, not fixed). The warn-and-sample branch has a 100 percent false-alarm rate once any unmatched refused row exists

The lane proves the branch is not dead code with an injected `rows =`
argument. I proved it through the real registry

    frm_sample(): the registry refuses this sampler with 'zz_devmode',

### F8 (documentation). `?frmtmb_register_compat`'s new promise is stronger than what the code does

### F11 (small). `control = list()` is refused, with a message that does not fit

`control = list()` has no names, so it takes the "NAMED list" branch
and errors with "got an object of class list". An empty control list
is a legitimate no-op and the natural output of building one
programmatically:

    ctrl <- list()
    if (tight) ctrl$adapt_delta <- 0.99
    frm_sample(fit, control = ctrl)      # errors when tight is FALSE

The same branch also catches a partially named list
(`list(adapt_delta = 0.99, 12)`) and tells the user its class rather
than that an element has no name. Fix: treat a zero-length list as
`NULL`, and give the partially-named case its own sentence.

## What the plan's two checks actually show

**1.1, "divergence count on a centered funnel falls between 0.8 and
0.99; `nuts_params()` reads the tightened step size back."** Met, and
the construction is sound.

Reproduced exactly (`.../scratchpad/rvsc-p3-funnel.R`, rstan 2.32.7,
StanHeaders 2.39.1, tmbstan 1.2.0):

| seed | div @0.80 | div @0.99 | step @0.80 | step @0.99 |
| --- | --- | --- | --- | --- |
| 11 | 0 | 0 | 0.2641 | 0.0665 |
| 12 | 0 | 0 | 0.2081 | 0.0739 |
| 13 | 1 | 0 | 0.2258 | 0.1142 |
| 14 | 4 | 0 | 0.2711 | 0.0985 |
| 15 | 0 | 0 | 0.3134 | 0.1090 |
| 16 | 42 | 0 | 0.1781 | 0.0556 |
| 17 | 13 | 0 | 0.2885 | 0.0828 |
| 18 | 15 | 0 | 0.2645 | 0.0466 |
| total | 75 | 0 | mean 0.2517 | mean 0.0809 |

Three things I checked that the lane did not.

*Is it seed-deterministic, or does it ride on the session's RNG?* The
default `init_jitter` draws from the session RNG, so I expected the
two arms to differ in their starting points and the answer to depend
on what ran earlier in the file. It does not: `mode_inits()` jitters
only chains 2 and up (`sample.R:283`), and the test uses `chains = 1`,
so the init is the maximum-likelihood mode exactly. Re-running seed 16
at 0.80 after 1000 intervening `rnorm()` draws returned div = 42 and
step = 0.178087, identical to six figures. Suspicion disproved; the
"two arms of the same runs" claim is exact.

*Is the construction tuned to seeds 11:18?* No.
`.../scratchpad/rvsc-p3-holdout.R`:

| seed set | div @0.80 | div @0.99 | step @0.80 | step @0.99 | monotone |
| --- | --- | --- | --- | --- | --- |
| 11:18 (shipped) | 75 | 0 | 0.2517 | 0.0809 | yes |
| 21:28 (held out) | 28 | 2 | 0.2369 | 0.0722 | yes |
| 101:108 (held out) | 194 | 0 | 0.2349 | 0.0769 | yes |

The held-out set 21:28 gives 2 divergences in the high arm, which is
why `expect_lt(n_hi, n_lo)` rather than `expect_equal(n_hi, 0)` is the
right assertion shape and the lane wrote it that way. The three
alternative constructions reproduce the recorded table to three
digits (5/1 at 0.296/0.068, 3/0 at 0.124/0.0015, 4/0 at
0.101/0.0009), so the search in section 1.7 is verifiable, not
asserted.

*What does it cost, and where does it run?* The 16 runs took 21 s on a
contended machine; `test-stan-control.R` as a whole is 26.6 s, so the
funnel is essentially the whole file. It never runs on CI:
`.github/workflows/check-frmtmb-sample.yaml:47` sets
`FRMTMB_SAMPLER_GATES: "false"`, and `sampler_gates_on()` is the gate.
That answers the CI-fragility question by removing it, and it is the
right gate for the right reason (a seeded Stan chain is not
platform-deterministic; the step-size half of the assertion is
mechanism and would survive a platform change, the `expect_gt(n_lo,
0)` half would not). I could not test an rstan version bump: 2.32.7 is
the only build here, and I will not install another into a shared
library. The honest statement is that the assertion is robust to seed
choice and to session state, is not robust to a platform or rstan
change, and is gated off wherever that matters.

`expect_gt(n_lo, 0)` is the single absolute number in the three new
files. It is not a tolerance, it is a precondition on the
construction, the lane says so in a comment, and it is gated. I do not
count it as a lane-rules violation.

**1.2, "an ODE fit refuses in under a second with no Stan call; the
eam and latent rows stay conditional."** Met on the second half,
qualified on the first.

## The re-registration defect, and whether `load_all()` can give a wrong answer

Confirmed, with a sharper answer than the lane's.
`.../scratchpad/rvsc-p5-reload2.R`:

| step | rules | `frmtmb_compat_validate()` rows | resolved status |
| --- | --- | --- | --- |
| normal load | 447 | 0 | refused |
| second `.onLoad()`, identical rule | 448 | 0 | refused |
| re-register the SAME pair with a DIFFERENT status | 449 | 1 | works |

So:

- For identical rules the lane's claim holds exactly. The table grows,
  the resolved answer does not move, and core's own validator stays
  clean. No wrong answer.
- For an EDITED rule, which is the case that actually happens under
  `pkgload::load_all()` (you change a status, reload, the old closure
  is still registered), `frm_compat()` gives the NEW status, because
  `compat_hand_rules_tbl()`'s documented tie-break is later-wins. So
  the answer a developer reads is right.
- The wrong answer arrives somewhere else. The stale and fresh rules
  tie on precedence and disagree on status, which is exactly the
  registry defect `frmtmb_compat_validate()` exists to report, and it
  reports it: one row, `frm_sample x frm_ode()`. Core's
  `test-compat.R` asserts that table is empty. So a developer who
  edits a rule's status and reloads gets a `test-compat.R` failure
  describing a defect that is not in the sources.

That is the answer to the question: yes, a dev session can produce a
wrong answer, not from `frm_compat()` but from the validator that
polices it, and the wrongness is a false positive rather than a
missed refusal. It strengthens the lane's case for deduplicating by
registrant. Still core's defect, still out of this lane's scope, and
`frmtmb.ode`'s new `test-compat.R` block that exercises it is a good
thing to have.

One small consequence of that block: it leaves a duplicate rule in the
registry for the rest of the R process. Under `R CMD check`, where
testthat runs all six frmtmb.ode files in one process, `test-compat.R`
sorts before every `test-ode*.R`, none of which reads the registry, so
nothing is affected. Worth a comment in the test so the next person
does not have to work that out.
