## Findings

### 1. HIGH: `step()` moves through the workspace data, not the fit's

`stats::step()` does not call `update(fit, ...)`. It calls
`update(fit, change, evaluate = FALSE)`, then `eval.parent()`, and
`update(evaluate = FALSE)` still returns `data = d`, the symbol. So
`step()` takes its decision from `drop1()` on the stored data but
makes its move by evaluating the workspace object
(`dev/drop1raw-rev-step2.R`, `step2-lane.txt`, seed 21, n = 300):

```
update(fit, '~ . - x4', evaluate = FALSE) data arg: d
step, data in place: z ~ x + log(x2) | logLik -413.02051460
step, data gone: ERROR object 'd_gone' not found
drop1, data gone: 837.6717 905.7380 1012.3194 835.7650 835.9619
step after d$x2 changed: z ~ x + log(x2) + x4 | logLik -435.26018233
```

So, with the data changed, `step()` silently returns a different model
that was fitted to other data. With the data gone, it fails although
`drop1()` on the same fit works. With NA rows it stops with lm's
"number of rows in use has changed", because the move gains rows that
`drop1()` did not use (`step-lane.txt`). The findings say that
`step()` is fixed; it is fixed only while `d` is unchanged.

Fix: make the call that `update(evaluate = FALSE)` returns evaluate
to the same refit as `update()`. On the stored-data route, put the
refit data in the call by value and attach the original spelling to
it (for example `attr(rd, "data_name") <- spelled`, which
`summary_data_name()` already reads). Then make `frm()` record that
spelling in its `call` when the attribute is present. Remove the
`out[["call"]][["data"]] <- spelled` fix-up after `eval()`. Add a test
for `step()` with the data removed and with `d$x2` changed.

### 2. MEDIUM: `update()` without data does not reproduce a fit with a spline when `na.action` dropped rows

The fit computes `ns()`, `poly()` and `scale()` on every row before
`na.action`. The stored data hold only the rows after `na.action`, so
the refit computes the basis again on fewer rows
(`dev/drop1raw-rev-probe.R`, seed 5, n = 200, 3 NA in `x3`,
`probe-lane.txt` section 2):

```
z ~ splines::ns(x2, 3) + x3        fit -361.02064484 | update(fit) -361.00574735 | diff 1.49e-02
                                   drop1 AIC(-x3) 733.73080917 | AIC(update(fit, ~ . - x3)) 733.69788456
z ~ splines::ns(x2, 3) * g + x3    fit -321.37180462 | update(fit) -321.36528092 | diff 6.52e-03
z ~ poly(x2, 2) + x3               coef 2 fit 11.956459 update 11.909387 (logLik equal)
z ~ scale(x) + x3                  coef 2 fit 1.000344 update 1.002649 (logLik equal)
```

Also, `update(fit, family = student())` gives -361.00574738, while
`frm(..., family = student())` gives -361.02064489. `drop1()` freezes
the bases and `update()` does not, so the two disagree on the same
submodel (733.73080917 against 733.69788456). `step()` will show both
numbers. brms has the same defect: its fit's `poly()` column is
`poly()` on all 40 rows, and its update computes it again on the 38
stored rows ("fit column == update column: FALSE", `brms2.txt`). This
is a case where brms is clearly wrong, because a refit with no change
must reproduce the fit. NEWS says "It now reproduces the fit in each
case", which is false here.

Fix: on the stored-data route (`update()` without `data`/`newdata`,
and `drop1()`), give the refit's `assemble_frame()` the fit's
`predvar_map`, as `influence()` already does. Use an internal channel
through `frm()`, for example an attribute on the refit data that
`frm()` passes as `assemble_frame(predvar_map = )`. Then remove
`freeze_bases()`. This keeps the coefficient names (finding 4), makes
`update(fit)` reproduce the fit, and makes the `drop1()` AIC equal
`AIC(update(fit, ~ . - x3))`. With `newdata`, keep evaluating again,
as now. Add the ns() + NA case to the `update()` test.

### 3. MEDIUM: a new variable in `update()` silently switches every variable to the workspace object

`update(fit, ~ . + w)`, where `w` is not in the fit, evaluates the
call's `data` for ALL variables. After `d` changed (`x2` times 10, 10
rows deleted), `update(fit)` gives the fit (nobs 197, logLik
-300.3602251078), but `update(fit, ~ . + w)` gives nobs 188 and logLik
-284.1072416771. That is exactly `frm()` on the changed `d`
(-284.1072416771), so `log(x2)` is read from the changed `x2`. A
global vector gives "`wv` is not a column of `data`; the object R finds
from the formula has 200 rows and `data` has 190", which describes
neither cause (`probe-lane.txt` section 1). The lane's test pins the
switch: `expect_identical(nobs(u4), nrow(d))` after `d` changed. brms
refuses (`brms2.txt`).

Fix: when the new formula reads a variable that the fit does not hold,
evaluate the call's data, and use it only if it still holds the fit's
data: after the fit's `na.action` and subset, the same rows and
identical values for every variable in `fit_refit_data()`. Otherwise
refuse, with brms's advice: name the variables, say that the data
object changed or is gone, and tell the user to give it with
`newdata =`. A plain brms-style refusal would also break `add1()`,
which cannot pass `newdata`, so check, do not always refuse. Change
the test to expect the refusal after `d` changes, and to expect a
refit when `d` is unchanged.

## Item 5: recommendation for `drop1()` on MAP fits

**Measured.** `logLik()` of a fit with a prior is `-opt$objective`, and
that objective includes the negative log prior (`R/fit.R`: `nll <-
function(pars) nll0(pars) + nlp(pars)`). The `frm()` documentation
says so. `dev/drop1raw-rev-map.R` (seed 5, n = 200,
`normal(0, 1)` on class `b`, `map-lane.txt`):

```
logLik(fit) -294.5289625064 | data log density -290.8528061920 | + log prior -294.5289625064
logLik - (data + prior) = 5.684e-14
drop1 LRT(x3) 2.485802 = 2 (lp0 - lp3) -1.904880 + 2 (lik0 - lik3) 4.390682
ML LRT(x3) 4.391157
bound-only prior logLik -290.8469579503 | no prior -290.8469579503
summary marks MAP: TRUE
```

So the drop1 "LRT" is the likelihood term plus twice a difference of
log prior densities at two different estimates. Its sign is not fixed:
on the probe data it is -1.562, with p = 1. A bound-only prior adds no
density (logLik equal to the no-prior fit), but `summary()` still
marks it "(MAP)".

**Others.** glmmTMB 1.1.15.2 does what the lane does: `logLik()`
includes the prior (logLik - data = -3.676157 = the log prior of the
fixed effects), and `drop1()` and `anova()` print the same 2.486 with
p = 0.1149 and no warning. lme4 has no priors. brms has no `drop1()`
and compares models with `loo()` and `bayes_factor()`. So no
reference implementation gives this statistic a meaning, and the
project's tiebreaker (brms) gives no table at all.

**Options.**

- (a) Keep the lane's behavior (the glmmTMB route). This prints a
  chi-square p-value for a quantity that is not chi-square distributed
  and can be negative. Reject this option.
- (b) Use the likelihood alone at the MAP estimates (4.390682 here).
  Neither estimate maximizes that likelihood, so this is still not an
  LRT, and it is not guaranteed to be nonnegative. Reject this option.
- (c) Refit both models without the prior (ML). This tests a model
  the user did not fit. Users often set the prior because the ML fit
  does not exist (separation, a singular variance). Reject this
  option.
- (d) Refuse.

**Recommendation: (d).** `drop1()`, and through it `step()`, refuse a
fit whose prior adds a density to the objective. The message says
that the fit maximizes log-likelihood plus log prior, so the
difference is not a likelihood ratio, and names the alternatives:
refit without the prior for ML tests, or use frmtmb.sample's `loo()` /
`bayes_factor()`. Decide from the resolved prior entries, not from
`!is.null(object$prior)`. A bound-only prior (`set_prior("", lb = 0)`)
leaves logLik unchanged and must not be refused. Apply the same
refusal to `anova()`'s LRT between MAP fits, in this lane or as a filed
follow-up, because it has the same defect today and is not in this
diff. `AIC()` can stay as documented ("penalized quantities"). With
(d), the lane's `drop_who = "drop1()"` message path and finding 4's
symptom go away for MAP fits.

### New findings

**N1. MEDIUM: the channel outlives the call it was made for.**
`frm()` trusts any `frmtmb_refit` attribute on `data`. Two paths reach
it with the wrong call:

- The standard `stats::update()` idiom: edit the call that
  `update(evaluate = FALSE)` returns, then evaluate it
  (`r1e-lane.txt`):

  ```
  edited call: fitted formula z ~ x | recorded call frm(formula = bf(z ~ splines::ns(x2, 3) + x + x3), data = d)
  ```

  The new fit's call names a model it is not.
- A data frame taken out of such a call and given to `frm()`
  (`r1-lane.txt` section A). `frm(bf(z ~ x), data = dd)` records the
  update's call, `formula = z ~ x + log(x2)`. It also takes the old
  fit's `na_action` (rows 3, 17 and 40, which were not removed from
  `dd`) and its `predvar_map`, so a `poly()` or `ns()` term in the new
  formula would get the old fit's basis.

Fix: make the channel name what it was made for, and make `frm()` use
it only for that. Store the formula value that `update()` and
`drop1()` put in the call, and `nrow(data)`. `frm()` uses the channel
only when `identical(formula, channel$formula)` and the row count
agrees. Otherwise it removes the attribute and records its own
`match.call()`. Add tests for the edited-call idiom and for
`frm(data = update(fit, evaluate = FALSE)$data)`.

**N2. MEDIUM: `refit_data_matches()` does not check a variable that
the candidate data lack.** The loop compares only
`intersect(names(rd), names(data))`. A `d` in the caller's frame that
lacks `x2` passes the check, and the refit then reads `x2` from
wherever R finds it (`r1-lane.txt` section B):

```
reference frm(... + w) on the global d                   logLik -380.7151487902
local d: x2 column missing                               ERROR The model uses `x2`, which is not a column of `data` ...
local d: x2 column missing, global x2 vector             nobs 197 logLik -406.3372068809
```

The second line refuses for the wrong reason. The third is a silent
wrong model. Every other shadowing case is caught: changed `x2`,
reordered rows, other row names, an NA moved to another row, and a
different global `dl` for a fit whose local `dl` is gone. A changed
value on a row the fit dropped is accepted, which is correct, because
the refit drops that row again. A local `d` with the fit's variables
and a different `w` is read, which is the documented lookup order.

Fix: in `refit_data_matches()`, return FALSE when a variable the fit
holds by name is not in `data`. A variable held by name is in
`intersect(names(rd), formula_vars(fit$bform))`, so that transformed
model-frame columns such as `log(x2)` are not required. Add the
missing-column case to the test.

**N3. LOW, not a regression: `getCall()` after a delta update holds a
deparsed `bf()` object.** `getCall(update(fit, ~ . - x3))` is
`frm(formula = structure(list(formula = z ~ x + (1 | g), ...` with
2474 characters, on rellib-r9 and on the lane alike (`r1d-<arm>.txt`).
A `family =` update records a readable call on both builds. The
recorded call still names the user's data (`data = d`). `update()` of
an updated fit reproduces it (`r1-lane.txt` section A: `update(u1)`
gives -381.7662502150, the same as `u1`, in this session and in a new
session after `readRDS()`, and drop1 AIC agrees to 6 decimals).
`eval(getCall(u1))` reads the workspace `d` and gains the 3 NA rows
(nobs 200, -387.35), as `lm()` does. Optional: record the delta
through `bform_call()` as the complete-formula branch already does.
File it if not done here.
