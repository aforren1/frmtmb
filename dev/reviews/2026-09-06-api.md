## Defect 2: two spellings of one coefficient name

### The census, re-measured on five model shapes

`fixef(flatten = TRUE)` against `rownames(vcov())`:

| shape | setequal | same order |
| --- | --- | --- |
| A `y ~ x + (1\|g)` gaussian | TRUE | TRUE |
| B `bf(y ~ x, sigma ~ z)` | TRUE | TRUE |
| C multivariate `bf(y ~ x) + bf(y2 ~ z) + set_rescor(FALSE)` | TRUE | **FALSE** |
| D smooth `y ~ s(x)` | TRUE | TRUE |
| E the nonlinear reference fit | TRUE | TRUE |

The order difference on C is real (`vcov()` puts both `betad` blocks
last, `flatten` interleaves them per response) and is documented in the
new `@param flatten` ("index by name"). Set equality holds everywhere,
so the claim survives on a multivariate model and on a smooth, which the
lane's own tests do not cover: `tests/testthat/test-api-spellings.R`
exercises `sp_case()` and one distributional fit, so "three model
shapes" in `dev/api-findings.md` is really two, and neither is the one
that fails on ordering.

The location dpar really is unprefixed:

```
names(fixef(flatten=TRUE)):  (Intercept) | x | sigma_(Intercept)
rownames(vcov):              (Intercept) | x | sigma_(Intercept)
names(unlist(fixef)):        mu.(Intercept) | mu.x | sigma.(Intercept)
```

`unlist()` does dispatch: an `unlist.<class>` method registered on a
classed list is called. So the lane's technical premise is right and the
refusal rests on blast radius alone.

### Blast radius, measured independently

My grep, not the lane's. Files carrying BOTH `unlist(fixef(` and a
literal `[["a.b"]]` index, excluding `dev/`:

```
19 files, 151 dot-index sites
```

The lane reported 19 files and about 134 sites. Identical file count,
site count within 13 percent (my regex also catches `[["s(x).fx1"]]`).
Monorepo-wide literal dot-name `[[ ]]` sites: I count 296, the lane 240.
Same order of magnitude throughout. Across the whole monorepo,
`unlist(fixef(` appears **114 times in 48 files**, six extensions
included.

### Judgment on the refusal: CORRECT

Reconciling `unlist()` is technically possible and would still break all
19 files and 151 sites, because those sites index the composite name
literally. An `unlist.fixef_frmtmb` method is smaller in code and
identical in blast radius, so it is not the smaller change the brief
asks about. The alternative I checked and reject: naming the list
ELEMENTS canonically while keeping the dpar keys yields
`sigma.sigma_(Intercept)` under `unlist()`, which is worse. The lane
found no smaller reconciling change because there is none. Adding
`flatten = TRUE`, correcting the docs, and pinning `unlist()` with a
test is the right shape of fix.

### Finding 2.1 (MEDIUM): the replacement doc claim is also false, for `hypothesis()`

The lane removed a false `?fixef` claim and installed a narrower one that
is still false. `R/methods-fit.R:534-538` now says `flatten = TRUE` is

> named the way every parameter-addressing surface of the package names
> its rows - `vcov()`, `confint()`, `hypothesis()`, `par_template()`,
> `start` and `newparams`

`hypothesis()` is not one of those. Its bare namespace strips
parentheses:

```r
f <- frm(y ~ x + (1 | g), data = dd)
names(fixef(f, flatten = TRUE))
#> "(Intercept)" "x" "sigma_(Intercept)"
hypothesis(f, "sigma_(Intercept) = 0")
#> Error: could not find function "sigma_"
#> Available names: Intercept, x, sigma_Intercept, sd_g__Intercept, sigma
hypothesis(f, "`sigma_(Intercept)` = 0")   # OK, backquoted
hypothesis(f, "sigma_Intercept = 0")       # OK, hypothesis's own spelling
```

Feeding every `flatten = TRUE` name to `hypothesis()` verbatim: two of
three work, `sigma_(Intercept)` is REFUSED. `(Intercept)` survives only
because R parses a parenthesized symbol; it is an accident, not
agreement. So there are three namespaces, not two, and the third is the
one the lane's census table (`dev/api-findings.md`, row
"`hypothesis(fit, "chi_group = 0")` | underscore") folds into the
canonical one.

This matters because Defect 2 was "the package points the user at a name
mismatch and emits it". The same overstatement is repeated in three
places: `R/methods-fit.R:534-538`, the generated `man/fixef.Rd`, and
`NEWS.md` ("the `vcov()` / `confint()` / `hypothesis()` /
`par_template()` spelling"). Drop `hypothesis()` from all three, or say
it takes the name backquoted.

### Finding 2.2 (LOW): the `?fixef` example returns `NA` on a constant dpar

The new example is

```r
cf <- fixef(fit, flatten = TRUE)
cf / sqrt(diag(vcov(fit))[names(cf)])
```

On `bf(y ~ x, sigma = 1)` the flattened vector carries
`sigma_(Intercept)` for a dpar held at a constant, `vcov()` has no such
row, and the ratio is `NA`. The `@param` does warn that constants are
included and absent from `vcov()`, so this is documented rather than
wrong, but the headline example and the "named the way `vcov()` names its
rows" sentence read as a guarantee that this case breaks. The Rd example
itself fits a model with an estimated sigma, so `R CMD check` never sees
it. Worth one clause in `@param flatten`.

### Finding 2.3 (INFORMATIONAL): `R/allfit.R:122` still calls `unlist(fixef())`

`dev/api-findings.md` lists `frm_bootstrap()` as the only in-package
default worth moving. There is a second in-package call,
`R/allfit.R:122-123`, which the report never mentions. I checked it: it
feeds a `vapply()` that is reduced to a scalar spread, so no name ever
reaches the user and nothing needs to change. Recording it so the next
lane does not have to rediscover it. `R/influence.R:57` already uses
`get_coef()` and says why.

### `frm_bootstrap()`: the behavior change is real and NEWS says so

```r
set.seed(7); frm_bootstrap(f, nsim = 12)$t0
#>  new: (Intercept) | x | sigma_(Intercept)
#>  old: mu.(Intercept) | mu.x | sigma.(Intercept)
```

Values identical (`all.equal` on the unnamed vectors is TRUE), only the
names move, `confint(bs)` row names move with them, and the new names are

## Defect 3: ranef() block addressability

This is a behavior change on a method other packages call, so I ran the
same script under both libraries and diffed the captured output.
Fixtures: the three-block nonlinear fit (`(1 | id)` on `apo`, `chi`,
`pk`), a single-block `y ~ x + (1 | g)`, and a model with no random
effects.

The complete diff, main to branch, is FIVE hunks and nothing else:

| probe | main | branch |
| --- | --- | --- |
| `ranef(m)[["id"]]`, 3 blocks | the `apo` block, silently | ERROR naming all three labels |
| `ranef(m)$id`, 3 blocks | the `apo` block, silently | same ERROR |
| `ranef(m)[["chi: 1 or id"]]` | `NULL` | the 40x1 block |
| `attributes(...)` on that block, `condVar = TRUE` | `NULL` | `dim, dimnames, condSD, term`; `condSD` is 40x1 |
| `ranef(s)[["1 or g"]]`, 1 block | `NULL` | the 12x1 block |

(The label spelling is `chi: 1 | id`; the pipe is written out here to
keep the table readable.)

Everything else is byte-identical between the two libraries: `print()`,
`as.data.frame()` (dim, names and head), `str()`, positional `[[1]]` and
its `"term"` attribute, single-block `[["g"]]` and `$g`, partial matching
(`$gg` gives `NULL`), a missing name (`[["nope"]]` and `$nope` both give
`NULL`), an empty `ranef()` on a model with no random effects, and
`VarCorr()`'s keys.

The error message names all three labels:

```
ranef() has 3 random-effect blocks on grouping factor 'id', so 'id' does
not name one of them. Address a block by its term label -
[["apo: 1 | id"]], [["chi: 1 | id"]], [["pk: 1 | id"]] - or by position.
The label is also each block's "term" attribute, VarCorr()'s key and the
`grp` column of as.data.frame()
```

`condVar` attributes survive the new `[[`, because `ranef_pick()` returns
the stored matrix unchanged rather than rebuilding it. Confirmed above:
`condSD` comes back at the right dimension through a label lookup.

The lane's comment at `R/methods-fit.R:723` ("whatever base does with a
name this list does not carry, which on a list is NULL rather than an
error") is correct. I checked it on both libraries rather than from
memory: `[[` on a list with an unmatched character name returns `NULL`.

## Defect 4: flat directions

### Reproduced, before and after

The lane's data generator (seed 11, `mu_i ~ N(10, 1.1)`, `group` numeric)
is needed. My own generator drives the bump to a shallow but non-zero
optimum where nothing underflows, and no flat direction exists there. On
the lane's data the pathology is exact.

Gradient at the reported optimum, my measurement:

```
apo_(Intercept)  -5.18e-04     pk_(Intercept)    1.38e-32
chi_(Intercept)   1.14e-03     lamp_(Intercept)  1.98e-34
chi_group         7.09e-04     lsig_(Intercept)  3.33e-32
theta_1          -9.90e-04     theta_3          -1.51e-68
theta_2          -1.28e-04
```

`fit$obj$he()` really is unavailable: "Hessian not yet implemented for
models with random effects." The gradient-perturbation route is forced,
not chosen for convenience.

MAIN, `vcov()`:

> ... the covariance could not be recovered from the Hessian **and the
> model is probably overparameterized**. diagnose() names the offending
> parameters ...

and `diagnose()` lists all nine parameters under "Non-finite standard
errors", identifying none.

BRANCH, same fit, `vcov()`:

> ... The likelihood is FLAT in 4 directions: pk_(Intercept),
> lamp_(Intercept), lsig_(Intercept), theta_3 - zero gradient and an
> empty Hessian row ...

and `diagnose()` gains a "Flat directions" block. `$flat` is a strict
subset of `$bad_se`.

### Are those the right four? An independent argument

Yes, for a reason that does not require trusting the code. The bump is
`exp(lamp) * exp(-0.5 * ((w - pk) / exp(lsig))^2)` and it underflows to
exactly zero on every row. Its three parameters are `lamp` (amplitude),
`pk` (centre) and `lsig` (width); `theta_3` is the standard deviation of
the `(1 | id)` block ON `pk`, whose conditional modes then also do
nothing. That is four. The other five (`apo`, two `chi`, `theta_1`,
`theta_2`) act through `apo - chi * logw`, which is untouched.

Measured independently of `diagnose_flat()`, by my own finite-difference
Hessian column norms:

```
apo_(Intercept)   2.82e+02      pk_(Intercept)    2.30e-30
chi_(Intercept)   7.35e+02      lamp_(Intercept)  3.33e-32
chi_group         3.68e+02      lsig_(Intercept)  5.61e-30
theta_1           1.93e+01      theta_3           2.84e-10
theta_2           6.67e+01
```

Eight to thirty orders of magnitude of separation, the same split the
lane reports. Nine gradient evaluations in **0.11 s** against the lane's
0.08 s; same order, and the difference is machine noise.

### Cannot false-positive on an ill-conditioned but identified parameter

Constructed: `y ~ x1 + x2 + (1 | g)` with `x2 = x1 + N(0, 1e-5)`, so
`cor(x1, x2)` prints as 1, `kappa(vcov)` is 3.2e10 and both slopes carry
a standard error of 2409. Grossly ill-conditioned, fully identified.

* Normal route: `pdHess` is TRUE and no standard error is `NaN`, so the
  gate never opens and `$flat` is empty.
* Gate forced: `frmtmb:::diagnose_flat(fit, gtol = Inf)`, every parameter
  a candidate, returns `character(0)`.
* Why it structurally cannot misfire: the test measures a Hessian COLUMN
  norm, and two parameters that trade off against each other have a LARGE
  one. Measured here as 1.59e+03 for each of the collinear pair, eleven
  orders above the 1e-8 threshold.

Exact collinearity never reaches the check: `y ~ x1 + 2*x1` is caught
upstream by the rank-deficiency drop ("Fixed-effect design ... is rank
deficient; dropping column(s): x3").

### A healthy fit pays nothing

`yy ~ xx + zz + (1 | gg)`, binomial, 2000 rows, 100 groups. Median of
five: `vcov()` 0 s and `diagnose()` 0 s on BOTH libraries, and
`fit$cache$flat_pars` is never populated. On a 33-parameter gaussian GLMM
over 4000 rows, `diagnose()` is also 0 s and the cache stays empty.

### Finding 4.1 (LOW): the worst case is linear in the parameter count

With the gate forced open on that 33-parameter model,
`diagnose_flat(gtol = Inf)` costs **0.28 s**, 8.5 ms per gradient
evaluation. That is the shape of the real worst case: a model whose
covariance failed but whose gradient is tiny everywhere makes every
parameter a candidate, and the check then costs `n + 1` gradient
evaluations before any warning prints. Bounded, and the caller has
already failed, so this is a note rather than an objection. A cap on the
candidate count would remove the tail.

### Finding 4.2 (LOW): `theta_3` is named but not explained

The printed block names `pk_(Intercept), lamp_(Intercept),
lsig_(Intercept), theta_3` and then explains three things: "a bump whose
centre starts far from the data is flat in its centre, amplitude and
width at once". The fourth, `theta_3`, is the group standard deviation OF
the flat parameter, and the reader is left to work that out from a bare
index. `R/confint.R` already carries `log_sd_theta_index()`, so a label
is available. One clause closes it.

### Finding 4.3 (INFORMATIONAL): the flatness threshold is absolute

`diagnose_flat(tol = 1e-8)` compares a Hessian column norm against a
fixed 1e-8 with no scaling by the likelihood. On this fit the tightest
margin is `theta_3` at 2.84e-10, two orders inside the threshold, and
every identified parameter sits at 19 or above, so the gap is enormous
here. A differently scaled likelihood could in principle put a genuine
curvature near 1e-8, but such a parameter carries a standard error near
1e4 and is not usefully identified anyway. Recorded, not objected to.

### The lane's correction to the brief is right

The brief said the flat fit stays at the start point. It does not: at
`w = 1` with `pk = 0, lsig = 0` the bump is `exp(-0.5) = 0.6065`, so
there is a gradient at the start. The optimizer walks `lsig` down until
the bump underflows and the model goes flat DURING the optimization.
Verified arithmetically and against the fitted values.

## Finding 4.0 (HIGH): the flat-direction message asserts a nonlinear cause on models that have none

Found by running `fixef(flatten = TRUE)` across more model shapes than
the lane tested, which put a MONOTONIC model through the new warning
path. This is the most serious finding in the review.

`flat_par_note()` (`R/confint.R:840-853`) and `diagnose()`'s printed
block (`R/confint.R:1093-1108`) both close with an UNCONDITIONAL causal
claim and an unconditional remedy:

```
A nonlinear term that has left its own support does this; give it a
starting value that puts it back (see par_template())
```

```
A nonlinear term evaluated outside its own support does this - a bump
whose centre starts far from the data is flat in its centre, amplitude
and width at once. Give those parameters a starting value that puts the
term back on the data
```

Neither is gated on the model having a nonlinear term. `flat_pars()` is
not either: it names any outer parameter with a vanishing gradient and an
empty Hessian column, whatever produced it.

### Reproduction

```r
set.seed(6); n <- 300
dd <- data.frame(x = rnorm(n), g = factor(rep(1:15, 20)),
                 mo = factor(sample(0:3, n, TRUE), ordered = TRUE))
dd$y <- 1 + 0.6 * dd$x + rnorm(n, 0, 0.5)
f <- frm(y ~ mo(mo) + x, data = dd)
vcov(f)
```

All four `mo` levels are well populated (70, 75, 67, 88). The model has
no nonlinear anything: `f$frame$spec$responses[[1]]$nlpars` is
`character(0)`. `pdHess` is TRUE and the maximum gradient is 6.2e-06.

BRANCH:

> Some standard errors are not finite ... The likelihood is FLAT in 1
> direction: zeta1_2 ... **A nonlinear term that has left its own support
> does this; give it a starting value that puts it back (see
> par_template())**

and `diagnose()` prints the whole "a bump whose centre starts far from
the data" paragraph.

MAIN, same fit:

> ... the covariance could not be recovered from the Hessian **and the
> model is probably overparameterized**. diagnose() names the offending
> parameters ...

`zeta1_2` is a monotonic-effect SIMPLEX component. The branch sends the
user looking for a bump that does not exist and tells them to give it a
starting value through `par_template()`, which will not help. Main's
message is vague; the branch's is a false lead, which is worse. That is
the exact failure mode Defect 4 set out to remove, reintroduced on a
different model class.

The lane measured this change on one fit. Nothing in
`tests/testthat/test-diagnostics-ux.R` exercises a flat direction outside
a nonlinear model, so it ships silently: `grep -rn "overparameteriz"
tests/` finds only the nonlinear assertions at
`test-diagnostics-ux.R:367-417`.

### Fix

Small, and it does not touch the diagnosis, only the explanation.

1. Gate the nonlinear sentence on the model actually carrying nonlinear
   parameters. `flat_par_note()` already receives `fit`, so
   `length(unlist(lapply(fit$frame$spec$responses, function(r) r$nlpars)))`
   is available with no new plumbing, and `diagnose()`'s print block has
   the fit too.
2. With no nonlinear parameter, say what is true for every case: the
   likelihood does not depend on these parameters AT THIS POINT, name
   them, and point at `par_template()`/`start` without asserting a bump.
3. Add a regression test on a non-nonlinear flat direction. The `mo()`
   model above is a two-line fixture.

## Finding 3.1 (MEDIUM): the ranef() break reaches `||` and distributional random effects, and the docs name neither

The lane, `NEWS.md` and `?ranef` all illustrate the multi-block case with
ONE example: a nonlinear model with `(1 | id)` on three nonlinear
parameters. A reader who does not fit nonlinear models concludes the
change cannot reach them. It does. Measured, branch against main:

| model | blocks on `g` | `ranef(fit)$g` on main | on branch |
| --- | --- | --- | --- |
| `y ~ x + (1 + x \|\| g)` | 2 (`1 \| g`, `0 + x \| g`) | the intercept block | ERROR |
| `y ~ x + (1 \| g) + (0 + x \| g)` | 2, same labels | the intercept block | ERROR |
| `bf(y ~ x + (1 \| g), sigma ~ (1 \| g))` | 2 (`1 \| g`, `sigma: 1 \| g`) | the mu block | ERROR |
| `y ~ x + (1 + x \| g)` | 1 (`1 + x \| g`) | the block | the block, unchanged |

The uncorrelated random slope `(1 + x || g)` is a bread-and-butter
lme4/brms spelling, and a random effect on a distributional parameter is
the ordinary way to write a heteroscedastic mixed model. Both now refuse
`ranef(fit)$g`. The correlated `(1 + x | g)`, which is one block, is
correctly untouched.

The package's own test helper already knew this. `helper-stan.R:158-166`,
pre-existing:

> That label is the only unambiguous key. ranef() names every block after
> its GROUPING FACTOR, so a model with a random intercept on two
> distributional parameters has two blocks both called "id" ...; `||`
> splits one term into several blocks with the same name again.

### Judgment

The change is still RIGHT. Returning the intercept block when the caller
asked for `g` on a `||` model is a wrong answer, and a wrong answer is
worse than an error; the package had already built `frm_block_index()` to
route around it internally. Keep the error.

What must change is the description of its reach. `NEWS.md` says only

> **What breaks is `ranef(fit)$g` on a factor carrying more than one
> block**

which is true and uninformative about WHICH models those are. Name the
three common shapes: `||`, two bars on one factor, and a random effect on
more than one distributional or nonlinear parameter. Do the same in
`?ranef`, whose new paragraph currently gives only the nonlinear example.

If a softer landing is wanted, a `warning()` plus the first block for one
release would preserve every existing script while telling users to move.
I do not recommend it: the wrong answer is the defect.

### Test gap

`tests/testthat/test-methods.R`'s new tests use the nonlinear fixture
only. Neither `||` nor a distributional random effect is covered, so the
two most common ways to hit the new error are untested. Two fixtures,
four lines each.

### Finding 4.0, addendum: the DETECTOR is right, only the message is wrong

I checked whether `zeta1_2` is a false positive. It is not. On the `mo()`
fit:

```
                     |grad|      Hessian column norm
(Intercept)          6.22e-06    1.83e+03
x                    1.95e-06    1.13e+03
momo                 2.79e-06    5.49e+03
sigma_(Intercept)    2.06e-06    6.00e+02
zeta1_1              3.05e-08    3.89e-06
zeta1_2              2.60e-13    2.75e-11   <- flagged
```

and the objective does not move at all when `zeta1_2` does:

```
nll(p)      = 220.205072942557
nll(p + 1)  = 220.205072942558
nll(p - 5)  = 220.205072942557
```

The monotonic simplex has saturated (`zeta1_1 = 14.68`,
`zeta1_2 = -12.91`), so the softmax sits in a corner and further movement
changes nothing. That is a flat direction by exactly the definition the
lane implemented.

Note also that `zeta1_1`, in the same simplex, has a column norm of
3.89e-06 and is correctly NOT flagged. The threshold discriminates within
one parameter block.

This makes the finding sharper, not softer. The DETECTOR generalizes
correctly past the nonlinear case the lane built it for, which is a good
result. The message does not generalize with it, and asserts a cause the
detector never measured. Fixing the message keeps the generalization and
removes the false lead.

# Verdict: PUNCH

The engineering is good and the reasoning is nearly all sound. Every
headline claim I could check independently held up: both original Defect 1
failures, the brms silent-discard (verified with `make_stancode()`), the
Defect 2 refusal and its blast radius (19 files, my count 151 sites
against the lane's 134), the Defect 3 diff being five hunks and nothing
else, the Defect 4 separation of four flat directions from five identified
ones, the gated tier at 1634, roxygen idempotence, and a clean tree.

It is a PUNCH because of 4.0. Defect 4's whole purpose was to stop the
package asserting a cause it had not measured. The lane measures the flat
SET correctly and then attaches an unmeasured causal claim to it ("a
nonlinear term that has left its own support does this") with no gate on
the model having a nonlinear term. On `y ~ mo(mo) + x` that ships a false
lead where main shipped only a vague one. That is the original defect
relocated, and it is four lines to fix.

3.1 and 2.1 are documentation, but both are the kind that sends users to
the wrong place: one hides which models a breaking change breaks, the
other tells users a name works in `hypothesis()` when it does not.

Nothing here needs redesign. The punch list is small and none of it
touches the parts that were measured well.
