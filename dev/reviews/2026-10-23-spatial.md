# Review: lane spatial (2026-10-23)

Reviewer's adversarial pass over `frmtmb-wt-spatial` (base 19b162b9,
frmtmb 0.73.1, uncommitted). Every number below comes from a run made
for this review. Scripts are `dev/review-spatial-*.R` and
`dev/review-spatial-par.sh`; logs are in `dev/review-spatial-log/`
(gitignored). "Lane" means the libraries `wt-spatial-lib` then
`rellib-r11`; "base" means `rellib-r11` alone (frmtmb 0.73.0). Each log
starts with a `lib:` line that names the frmtmb build it loaded. The
scratch trees (the AB copy, the merge copy, a core-only library copy,
the base test copy) were deleted after the runs.

## Findings

### A1 (major). The seam accepts entries that are wrong in shape, and `cs_check_entry()` is never run outside a test

The help page says the call "checks every slot before it commits
anything". In practice it checks only that each slot is a function with
enough arguments. `cs_check_entry()` checks that slots are present and
are functions, and only test-covstruct-seam.R calls it. Nothing checks
an entry against a block. `dev/review-spatial-strict.R`
(`strict.txt`; seed 1; 100 rows, 20 groups; reference
`(1 | g)` logLik -156.8200751):

    register badstart -> ok
      [warning] number of items to replace is not a multiple of replacement length
    fit badstart (start length 3, npar 1) -> FIT logLik -156.8200751
    fit badsd (sd_idx 4, npar 1) -> FIT logLik -156.8200751
    fit badvc (vcov 3 x 3 for dim 1) -> FIT logLik -156.8200751
      VarCorr: sd Estimate 1, Est.Error 0      <- fabricated
    fit signflip (lpdf returns the NEGATIVE log density)
      -> FIT logLik 1.284229581e+15 (two convergence warnings, no refusal)
    fit np_fun_bad (npar(blk) = -1) -> ERROR: argument must be coercible to non-negative integer

A `vcov` of the wrong dimension gives a `VarCorr()` of sd 1 with no
error. An `sd_idx` out of range is ignored without a message. That is
the failure the extension-api page warns about: "a registration that is
accepted and then does nothing is indistinguishable from one that
worked."

Required fix: call `cs_check_entry()` from `frmtmb_register_covstruct()`.
At frame assembly, check every block once against its entry:
`length(start(blk)) == npar(blk)`, `sd_idx(blk)` within
`seq_len(npar(blk))`, `vcov(start, blk)` a `dim x dim` matrix with the
coefficient names as dimnames, and `lpdf` a finite scalar at the start.
Refuse with a message that names the structure and the slot. Add a test
for each of the slips above.

### A2 (major). The OLRE check still names structures, and warns falsely on car() with one row per area

`R/fit.R:2459` is `structured <- bk[["covstruct"]] %in% c("gr_cov",
"gr_prec", "equalto")`. It is a property, "a fixed matrix correlates
the levels", which is `cs_levels_coupled()`. The lane converted six
such lists but missed this one. As a result, the standard areal model,
one row per area under a gaussian response, warns that "only their sum
is identified". That is false: the levels are correlated through the
adjacency, as in `gr(cov = A)`, which the check already exempts.
`dev/review-spatial-reload.R fit` (`reload-fit.txt`, seed 42, 6 x 6
lattice, 36 rows):

    [warning] escar `car(W6, gr = loc, type = ty)` gives every observation its own random effect, and for a gaussian response that variance is confounded with the residual sd: only their sum is identified ...
    one row per area, type escar -> FIT logLik -42.4022199
    (the same warning for icar and bym2)
    one row per level, gr(cov = A) -> FIT logLik -42.52094795   (no warning)

The defect is in base too (`olre-base.txt`, rellib-r11: the same warning
and logLik -42.4022199). It also applies to any registered structure
with `levels_coupled = TRUE`.

Required fix: `structured <- cs_levels_coupled(bk) ||
identical(bk[["covstruct"]], "equalto")`. Add a test in frmtmb.spatial
that fails on rellib-r11: a car() fit with one row per area raises no
OLRE warning.

### A3 (major, blocks C). A saved fit with a registered structure, read back where the package is absent

`dev/review-spatial-reload.R`: an escar fit saved with frmtmb.spatial
loaded, then read in a fresh process that loads frmtmb only.

- frmtmb.spatial installed but not loaded (`reload-installed.txt`):
  `readRDS()` loads the namespace (its closures are in the fit), and its
  `.onLoad()` registers car. Every method passes. Good.
- frmtmb.spatial not installed (`reload-absent.txt`, a library that
  held only the lane's frmtmb):

      print            ERR could not find function "car_rho"
      summary          ERR could not find function "car_rho"
      logLik           ok
      VarCorr          ERR The car() structure is in the extension package frmtmb.spatial, which is not loaded. Install it and run library(frmtmb.spatial)
      vcov             ERR could not find function "car_rho"
      fitted           ok
      predict_new      ERR could not find function "car_rho"
      simulate         ok
      ranef            ERR The car() structure is in the extension package frmtmb.spatial, ...
      confint_varcorr  ERR could not find function "car_rho"
      update           ERR The car() special is in the extension package frmtmb.spatial, ...

Half of the methods give a "could not find function" error from a
frmtmb.spatial internal. This is the defect that splitsurv fixes for
families ("family from an absent package"). Structures need the same
fix. A third-party structure is worse off: core's home table does not
list it, so `cs_entry()` says "internal: no covariance structure 'x' is
registered". Also, the entry's `package` slot is `NULL` for a
registration made outside a namespace.

Required fix: record the registering package in each block of the
frame when the fit is built, from the entry's `package` slot. At the
first method that reads a block's entry, refuse with a message that
names that package and says whether it is installed. Use splitsurv's
mechanism, so that families and structures give one message. Test it
in a child process with a library that lacks the package, as
test-guardrail.R does.

### A4 (minor). Reserved names miss names that another part of frmtmb owns

`strict.txt` and `dev/review-spatial-poly.R` (`poly` on base and lane):

    poly(x, 2) unregistered -> -155.6212825          (base and lane)
    poly(x, 2) after registering poly -> ERROR: object '.frm_poly' not found
    register car -> ok;  y ~ x + car(1 | g) -> FIT (as the caller's bar structure)
    register dec -> ok;  register wiener -> ok     (their extensions not loaded)
    register cox / weibull -> refused (kind conflict with a family)

Any caller can take `car` or `spde`, because the reserved list removes
`names(extension_special_homes)` for frmtmb.spatial's sake. A
structure named `dec`, registered before frmtmb.eam loads, holds the
vocabulary name as kind `"covstruct"`. frmtmb.eam's `dec()`
registration should then fail on the kind conflict. This was read from
the code and not run. Registering `poly` breaks `poly()` in every
formula.

Required fix: let only the home package register a name in
`extension_special_homes`. Reserve `names(extension_aterm_homes)`,
`names(extension_family_homes)`, the whole `brms_vocabulary`, and every
call the parser rewrites (`poly`, and the others like it).

### A5 (minor). Replacement is unconditional

The `name` parameter says "Registering a name the same package
registered before replaces it". The code replaces any non-core entry
for any caller. In `strict.txt`, `ok1` was re-registered with a `vcov`
of 99, and `VarCorr()` then reported 9.949874, with no message. Either
refuse a name another package registered (compare `package`), or
document that the last registration wins.

### A6 (minor). frm_compat() says "untested" where frm() refuses

`dev/review-spatial-toy2.R` (`toy2.txt`) for a registered `myar`:
`myar x quadrature` and `myar x importance` are `untested`, but
`frm()` refuses both by name (`toy.txt`). test-importance.R states the
invariant for core's structures ("every structure the objective
refuses by name has to read 'refused' there"). A registered structure
breaks it by construction. Required fix: when a name is not on the
allow-lists of quadrature, importance and `gr(by =)`, and not under
`|ID|`, `mm()` or `dist = "student"`, the seam adds the matching
refused rules, or the resolver derives them.

### A7 (minor). Two wrapper paths the fix does not reach

`dev/review-spatial-wrap.R` (`wrap-base.txt`, `wrap-lane.txt`):

### B1 (major). The `gr` probe hides a brms gap; NEWS overstates

`dev/review-spatial-gr.R` and `dev/review-spatial-plain.R`:

    brms (1 | gr(g)) standata identical to (1 | g): TRUE  N_1 = 10
    y ~ x + (1 | gr(g)) -> frmtmb: ERR gr() supports (x | gr(g, cov = A)), (1 | gr(g, prec = Q)), (x | gr(g, by = f)) and (x | gr(g, dist = "student"))
    (1 | gr(g, cor = TRUE)), (1 + x | gr(g, cor = FALSE)), (1 | gr(g, id = 'a')) -> fit

The refusal is on base too. test-guardrail1.R probes `gr` as
`(1 | gr(g, by = f))`, which works. With brms's plainest spelling, the
classifier would call the outcome "refused" (the message names `gr`),
and the "refused equals declared" check would fail. That check would
catch the gap, but the probe was chosen to pass. NEWS says "Every
family, addition term and formula special of brms 2.23.0 now resolves
in core, resolves in a named extension, or has such a refusal". That is
not true for `gr`. The other specials in their plainest forms (`ar()`,
`ma()`, `arma()`, `cosy()`, `mm(g1, g2)`) do resolve (`plain.txt`).

Required fix: make bare `gr(g)` fit as `g`, as brms does. Probe each
special in its plainest brms spelling (several spellings per name
where brms has them). Reword the NEWS bullet until both are done.

### B2 (major at merge). bhaz after splitsurv moves cox()

splitsurv puts `cox = "frmtmb.survival"` in `extension_family_homes`
(its `R/families.R:8470`). Two things break at the merge:

1. The probe is `sp("y | bhaz(df = 5) ~ x", "cox()")`. Without
   frmtmb.survival, `cox()` is "could not find function", which the
   classifier calls generic, so the test fails. The bhaz refusal fires
   under `gaussian()` too (`dev/review-spatial-bhaz.R`: the same
   message under `gaussian()`, `'cox'`, `brmsfamily('cox')` and
   `cox()`). So probe with `gaussian()`, and the family plays no part.
2. The message sends the user to `family = cox(...)`, which does not
   exist in core after the merge. The merged text must say:

   > Addition term `bhaz()` is not supported: it sets brms's M-spline
   > basis for the baseline hazard of a cox() model, and frmtmb sets
   > the same basis in the family. cox() is in the extension package
   > frmtmb.survival: install it, run library(frmtmb.survival), then use
   > family = cox(df = 5, degree = 3, intercept = TRUE), which is
   > brms's bhaz() default. A group-specific baseline, bhaz(gr = ), has
   > no frmtmb equivalent.

   brms's default is right: `resp_bhaz(gr = NA, df = 5, ...)` with
   `args$intercept %||% TRUE` (dev/brms-suite `formula-ad.R:166`). The
   last sentence is new (B3).

### B3 (minor). bhaz(gr = ) is not mentioned

brms's `bhaz(gr = g)` gives a separate baseline for each group. The
refusal sends such a user to `cox(df =)`, which has no `gr`, and does
not say that the stratification is lost. Add the sentence above.

### B4 (minor). The extension arm skips without a word

When an extension that a refusal names is not installed, the arm
`next`s without calling `skip()`. In core alone, the test passes with
fewer expectations and reports `skip=0`:

    lane core alone (a library with only the lane's frmtmb): pass=20 skip=0
    AB core alone (rev-spatial-lib):                          pass=19 skip=0
    lane, extensions installed (lane1):                       pass=24 skip=0

Call `skip()` with the package name, so that a core-only CI run shows
that the absent-condition arm did not run.

### C2 (minor). The 16 tie notes, and load order

I reran `dev/spatial-compat-dump.R` and `dev/spatial-compat-compare.R`
(`compat-compare.txt`):

    pairs 11350 -> 11350 ; features 164 -> 164
    features identical (name, key, kind): TRUE
    pairs only before: 0  only after: 0  status differs: 0  note differs: 16

The lane's result is reproduced. With frmtmb.spatial loaded FIRST
instead of last, 2 notes change (`car x frm_sample`,
`frm_sample x spde`; `compat-after-first.rds`). So `frm_compat()`
depends on the order of the `library()` calls. In each of the 16 pairs,
two blanket notes tie, one per feature
(`dev/review-spatial-notes.R`). Neither note is wrong, but neither
describes the pair better.

My judgment: "a contributed rule wins a tie" is not a sound rule. It is
an accident of position. Once two extensions contribute, the answer
depends on load order. The lane did not change the resolver, which was
right for this lane. Accept the 16 note changes, because every status
is unchanged. As a separate change, make the tie deterministic: show
both blanket notes for a pair that ties, or break the tie by feature
name.

### C3 (minor). frmtmb.latent's floor

floor must be the release that carries the seam. The lane says so, but
latent's DESCRIPTION is not changed. Set it at consolidation, together
with mvnlatent's floor.

### F1 (major). The lpdf heuristic refuses correct models

`cs_check_block()` refuses a registered structure when
`lpdf(1000 * 1) >= lpdf(0)`. An intrinsic (improper) density is flat
along its null space, and the constant vector is in that null space
for an RW1, an RW2 or an ICAR without a constraint. So the check
refuses a correct model. `f1.txt` (seed 7, 30 time points): the
local-level model `y ~ 0 + x + rwone(Q1, gr = t)`, with
`Q1 = crossprod(diff(diag(30)))` (rank 29). The data identify the
level through the field, and the gaussian joint Hessian
`Q / s^2 + I / sigma^2` is positive definite.

    fit y ~ 0 + x + rwone(Q1, gr = t), improper RW1 -> ERROR: The 'rwone' structure's lpdf slot is no smaller at b = 1000 than at b = 0 (-26.65 against -26.65); it has to be the LOG DENSITY of b, not its negative
    fit proper RW1 (Q + 1e-6 I) through the seam -> FIT logLik -31.2795175

A density with a nonzero fixed mean is refused too, once the mean is
past 500. This case is contrived, but the density is valid:

    fit shift100(1 | g) -> FIT logLik -156.8200751   (= the (1 | g) logLik: the mean goes into the intercept)
    fit shift600(1 | g) -> ERROR: ... no smaller at b = 1000 than at b = 0 (-1600018 against -3600018)

A heavy-tailed (Cauchy) structure passes (logLik -160.9814213).
frmtmb.spatial's own car types pass, because the soft constraint of
icar penalizes the constant vector at any finite `con_sd`.

Required fix: test the sign of the curvature, not the level far from
zero. With `u` a small random vector, scaled to the sd from `vcov` at
the start, refuse only when
`lpdf(u) + lpdf(-u) - 2 * lpdf(0) > 0` beyond rounding. That second
difference is negative for a negated proper density. It is zero along
the null space of an improper density. It is negative for a gaussian
with any mean, and for a Cauchy near zero. If that is not acceptable,
drop the level comparison and keep the finiteness check. Add the RW1
case above as a test of the absent condition.

### F2 (minor). Reserved names: too broad, and registration loads mgcv

`covstruct_formula_function()` reserves every function in base, stats,
splines, utils, methods and mgcv. So `toeplitz`, `spline`, `kernel`,
`cov`, `cor`, `dist`, `filter`, `kronecker` and `power` are refused
"because ... is a function of stats that formulas call". Formulas do
not call these. The conflict this guards against is a FIELD special
that would capture a whole-term call such as `poly(x, 2)` or `log(x)`.
A bar structure conflicts only if the function is written around a
bar.

Fix: apply the base/stats rule to field structures only, or limit it to
a list of functions that formulas call as terms. The cost of the
current rule is a renamed structure, not a wrong fit, so this is minor.

Also, the lookup calls `asNamespace("mgcv")`, so `library(frmtmb.spatial)`
loads mgcv: false after `library(frmtmb)`, true after
`library(frmtmb.spatial)`. Check only namespaces that are already
loaded, or use a fixed list.
