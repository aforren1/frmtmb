## Findings, ranked

### 1. MINOR: derived fields can go stale, and `family(fit)` then lies

The findings say "Why the derived fields cannot go stale". They can,
through every write path that does not dispatch to `$<-` or `[[<-` with a
character name. `dev/famlink-rev-mutate.R` (deterministic; the fit at the
end uses seed 20260916, n = 80) tries 20 mutation paths on
`brmsfamily("gaussian")`:

| Path | Derived fields after |
|---|---|
| `f$links$mu <- ...`, `f[["links"]][["sigma"]] <- ...` | fresh |
| `utils::modifyList(f, list(links = ...))` | fresh |
| `f$dpars <- ...`, `f$links <- NULL`, `f$ord_link <- ...` | fresh |
| `f["links"] <- list(lk)` | `link`, `link_sigma`, `linkinv` stale |
| `f[c("links", "dpars")] <- ...` | `link`, `linkinv` stale |
| `f[[6]] <- lk` (numeric index) | `link`, `linkinv` stale |
| `unclass`, edit, `class<-` or `structure(class =)` | `link`, `linkinv` stale |
| `f["link"] <- "log"` | accepted: the refusal is bypassed |

Through a fit: after `f["links"] <- list(lk)` with `lk$mu` set to `log`,
`frm(y ~ x, family = f)` fits on the log link
(`fit$frame$linpreds[[1]]$link$name` is `"log"`) while
`family(fit)$link` is `"identity"`. That is the silent wrong answer this
item exists to remove, reached by a user rather than by the package.

Base comparison: base has no `link` field, so this exact disagreement
cannot occur there; base's `$link` returned the links list instead.

Reach inside the repository is zero, measured two ways. A grep of `R/`
and `extensions/*/R` finds no `[<-`, `attr<-`, numeric `[[<-` or
unclass rebuild of a family object. `dev/famlink-rev-invariant.R` traces
`fit_assembled()` and, for every fit a test file makes, compares each
derived field with a fresh `family_link_fields()` and with the link
object the objective actually applies (`frame$linpreds`), and compares
`linkinv` numerically. Over 43 test files across core and all seven
extensions (list in `dev/famlink-rev-invariant-jobs.txt`), 856 fits,
5,684 comparisons: 0 stale, 0 disagreeing with the fit, 0 `linkinv`
differences, and every file green. The 79 "absent" rows in
`dev/famlink-rev-invariant-log.tsv` are non-linear parameters (`lka`,
`omega`, `thr` and so on), which have no `link_<nlpar>` in brms either;
they are an artifact of my tracer, not a finding. The rlddm, eam
`ndt_bound_attach()` and `family_finalize()` paths, hmm, lca, mixture,
mvbf, frailty and Royston-Parmar fits are all in that count.

Fix, cheapest first: re-derive with `family_link_fields()` once in
`as_frmtmb_family()` (or at frame assembly), so `family(fit)` is right
whatever the user did to the object before `frm()`; or derive `link`,
`linkfun`, `linkinv` and `link_<dpar>` on READ inside `$.frmtmb_family`
instead of storing them, which also removes finding 2. Correct the
sentence in the findings either way.
