## Findings

### 1. HIGH: a Student-t `gr(g, by = f)` term is now refused

`student_share_sets()` puts every Student-t block of one `group_name`
in one set and refuses a set whose blocks do not have the same levels.
frmtmb splits `gr(g, by = f)` into one block per by-level, and each
block has only the levels of `g` in its by-level. So the lane refuses
a single Student-t by-term, which `R/compat.R` lists as `works`
(`r("gr_by", "group:student_blocks", "works", ...)`, line 2044).

`dev/prilabel-rev-tby.R`, data seed 21 (`tby-base.txt`,
`tby-lane.txt`):

```
y ~ x + (1 | gr(g, by = hg, dist = "student"))
  rellib-r9: fits, logLik -361.6239067, 2 blocks
  lane:      ERROR: The Student-t terms of grouping factor 'g'
             (1 | g [hg = u]; 1 | g [hg = v]) share one latent scale per
             level, as in brms, but do not see the same levels of 'g' ...
y ~ x + (1 + x | gr(g, by = hg, dist = "student"))
  rellib-r9: fits, logLik -364.5278394
  lane:      ERROR (same message)
```

No test covers the combination, so the suite stays green. brms fits
it, and it also shares one `dfm_1` between a by-term and a plain
Student-t term on the same factor
(`(1 | gr(g, by = hg, dist = "student")) + (0 + z | gr(g, dist =
"student"))`: `r_1_1 = dfm_1 .* (transpose(sd_1[1, Jby_1]) .* ...)`,
`r_2_1 = dfm_1 .* (sd_2[1] * ...)`, `dev/prilabel-rev-log/misc.txt`).
The lane refuses that too, with a message that says the terms do not
see the same levels. That is not the user's problem to fix.

Fix: share the latent scale per LEVEL of the factor, not per block.
In `student_share_sets()`, take the union of the set's levels and store
on each block `t_level = match(bk$levels, union)`. In
`student_shared_lpdf()`, add each block's `q` and its per-level share of
`ldet` into union-level vectors, and take `D_j` per union level as the
sum of the dims of the blocks that hold level `j`. Then call
`student_lpdf_core()` per union level with that `D_j` (vectorize its
`lgamma_shift_diff(nu / 2, D / 2)` and `D / 2 * log(nu pi)` terms over
`D_j`). In `draw_b()`, draw one `w` per union level and give each block
`w[t_level]`. A partition (one by-term) then reduces exactly to the
0.71.0 model. Keep the refusal only for what is still not defined, if
anything. Tests: the two formulas above give the rellib-r9 logLik
(-361.6239067, -364.5278394); the by-term plus plain term equals a
closed-form reference at the mode and at perturbed points on
`obj$env$f()`.

### 2. MEDIUM: the shared-sd refusal ignores the prefix

`sd_coef_shared()` checks the group and the column name, and not the
response, dpar or nlpar. A per-coefficient prior on a block whose
columns have their own standard deviations is refused when a
shared-sd block of the same group in ANOTHER prefix has a column of
that name. brms accepts the same specification and puts it on the
location block alone (`dev/prilabel-rev-probe.R`, section 5,
`probe.txt`):

```
bf(y ~ x + (1 + x | g), sigma ~ homdiag(1 + x | g))
set_prior("normal(0, 0.5)", class = "sd", group = "g", coef = "x")
  lane: ERROR: class = "sd", coef = "x" names a column of sigma: 1 + x | g,
        whose homdiag() structure gives its columns one shared standard
        deviation ...
  brms, on (1 + x | g) with sigma ~ (1 + x | g):
        normal_lpdf(sd_1[2] | 0, 0.5) on mu's block only
bf(y ~ x + homdiag(1 + x | g), sigma ~ (1 + x | g)), same prior with
dpar = "sigma"
  lane: ERROR (names the mu block)
```

The absent cases work: `homdiag(1 + z | g) + (0 + x | g)`,
`(1 + x | g) + homdiag(1 + x | h)` and `ar1(0 + f | g) + (0 + x | g)`
put the prior on the right theta, and a `diag()` or `cs()` block takes
it (the lane's test).

Fix: give `sd_coef_shared()` the spec and refuse only when the
specification's `(resp, dpar, nlpar)` EQUALS a prefix of the shared
block that holds the named column, by the rule of the coef branch of
`sd_spec_reach()` (use `block_sd_prefix()`). Test: the first formula
above puts the prior on theta 2 (mu's `x`); with `dpar = "sigma"` it
is refused by name.

### 3. MEDIUM-LOW: `variables()` now lists `sds_` before `cor_`

`hyp_env_vals()` now writes every `cor_` after the loop over blocks.
The loop still writes a smooth's `sds_` inside it, so `sds_` now comes
before `cor_`. brms lists classes in the order `sd`, `cor`, `df`,
`sds`, `sdgp`, `lscale` (`reorder_pars()`). rellib-r9 had this case
right (`dev/prilabel-rev-order.R`, `order-base.txt`, `order-lane.txt`,
`order-brms.txt`):

```
y ~ s(x) + (1 + x | g)
  rellib-r9: bs_sx_1 sd_g__Intercept sd_g__x cor_g__Intercept__x sds_sx_1 sigma
  lane:      bs_sx_1 sd_g__Intercept sd_g__x sds_sx_1 cor_g__Intercept__x sigma
  brms (y ~ (1 | h) + s(x) + (1 + x | g) + (0 + x | h)):
             sd_g__Intercept sd_g__x sd_h__Intercept sd_h__x
             cor_g__Intercept__x sds_sx_1 sigma
```

Fix: in `hyp_env_vals()`, collect the smooth `sds_` (and any `sdgp_`
or `lscale_` written in the loop) as `cor_` is collected now, and put
them after the `cor_` flush. Add `y ~ s(x) + (1 + x | g)` to the
order test.

### 4. LOW: group order is not brms's, so the NEWS claim overreaches

brms sorts the group-level terms of each predictor by group name
(`terms_re()`: `out <- out[order(out$group), ]`, `R/brmsterms.R`
line 408 of the 2.23.0 tarball). It then numbers them in that order,
so `variables()`, `ranef()`, `VarCorr()`, `ngrps()` and `summary()` list
groups sorted per dpar. frmtmb lists them in formula order. This is
not new in this lane, but the NEWS bullet says `variables()` now lists
the standard deviations "in brms's order". `dev/prilabel-rev-brmsfit.R`,
fit A, `brmsfit.txt`:

```
y ~ x + (1 + x | g1/g2/g3) + (1 + f || g) + (1 | mm(m1, m2, weights =
  cbind(w1, w2))) + (1 | k1/k2)
  brms ranef/VarCorr/ngrps: g g1 g1:g2 g1:g2:g3 k1 k1:k2 mmm1m2
  frmtmb:                   g1 g1:g2 g1:g2:g3 g mmm1m2 k1 k1:k2
y ~ (1 + x | h) + (1 + x | g): frmtmb sd_h... sd_g...; brms sorts g first
```

The names and the coefficients per group are the same. Fix: order
the brms-facing outputs by brms's id order (response, dpar in brms's
order, nlpar, then `order()` of the group). If that is out of scope,
change the NEWS bullet to "every standard deviation before every
correlation" and file the group order in `dev/test-backlog.md`.

### 5. LOW: a level that contains `:` is not spelled as brms spells it

`brms_levels()` and the new-level message use `gsub(":", "_", lev)` on
reformulas's `a:b` level. brms pastes the parts with `_`
(`combine_groups()`), so a part that contains `:` keeps it
(`brmsfit.txt`, fit A):

```
k1 levels "c:d", "e"; k2 levels "f", "h"; group k1:k2
  brms:   c:d_f c:d_h e_f e_h
  frmtmb: c_d_f c_d_h e_f e_h
```

The `_` collision guard that was there before (`The levels 'a:b_c' and
'a_b:c' of group 'k1:k2' are one level in brms ...`) works on both
arms (`model-base.txt`, `model-lane.txt`). Fix: build the level names
from the component factors, as brms does: paste the parts of each
row with `_`. Keep the parts on the block at frame time (`levels`
come from reformulas's interaction, which cannot be split back
safely when a part contains `:`). Use the same names in `ranef()`,
`coef()` and `pred_design()`'s message.

### 6. LOW: `re_formula` still accepts the old order of an interaction

`re_group_key()` (`R/re-formula.R`) sorts the parts of an interaction,
so `re_formula = ~ (1 + x | g2:g1)` on a `g1/g2` fit selects `g1:g2`.
brms selects no term there: its fitted values equal `re_formula = NA`
(`brmsfit.txt`):

```
re_formula        brms (posterior mean)        frmtmb
NA                0.947 1.484 0.777 0.176      0.931 1.474 0.758 0.151
~(1 + x | g1:g2)  1.386 1.297 0.264 0.696      1.379 1.344 0.264 0.729
~(1 + x | g2:g1)  0.947 1.484 0.777 0.176      1.379 1.344 0.264 0.729
```

Now that blocks carry brms's group names, this alias is the one place
where the old label still works silently. It contradicts "old labels
refused". It also selects both blocks of `(1 | g1:g2) + (1 | g2:g1)`,
which brms and the lane keep as two groups. Fix: match the group
string exactly, as brms writes it. Refuse a term whose group the fit
does not have, and name the groups it does have. Do not drop the
term silently as brms does.

### 7. LOW: frmtmb.sample NEWS misses one effect of the new rule

With "a default steps aside only for its own slot", a CLASS-WIDE user
prior no longer replaces a default written per coefficient. On a
`gp(x)` model, `set_prior("inv_gamma(2, 1)", class = "lscale")`
replaced the sub-GP default on rellib-r9. On the lane the default
`inv_gamma(1.494197, 0.056607)` is kept on theta 3, and the user's
prior reaches nothing. brms does the same: its Stan code keeps
`inv_gamma_lpdf(lscale_1[1][1] | 1.494197, 0.056607)`
(`dev/prilabel-rev-lscale.R`, data seed 51, `lscale-base.txt`,
`lscale-lane.txt`). So the behavior is brms's. But NEWS describes only
the sd case, and the user's prior now has no effect without a message.
Fix: add the lscale case to the frmtmb.sample BREAKING bullet. Add a
disclosure line, as `default_prior_notes()` already writes for slots
left flat, when every slot that a user specification reaches keeps a
more specific default.

### The lane's "fails before the fix" evidence

`dev/prilabel-prefix-run.R` swaps one function for its round-0 form
with `assignInNamespace()` and runs one test file. I judge that sound
here, with two qualifications.

- It shows the new test detects the defect only if the mutant behaves
  as round 0 did. I measured round 0 myself for each defect (the
  refusal, the prefix refusals, the `sds_` order, `c_d_f`, the
  `g2:g1` alias, the missing note). Mutants 2, 4 and 6 are the round-0
  code. Mutant 1 reproduces the round-0 refusal, with a shorter
  message and the new `t_level`/`t_n` fields so that the new consumers
  run. Mutant 3 is a text substitution into the current function.
- A namespace swap does not reach a copy of the function that was
  captured earlier, for example in a registry or a closure. So a
  mutant can fail to take effect without any sign. Each mutant made
  its test fail, which shows that it took effect.

Mutant 7 stubs the new function to return nothing. That is the weak
"missing feature" form, but round 0 had no note at all, so it is the
round-0 behavior. Building the round-0 tree would be stronger, but it
no longer exists. rellib-r9 is no use for fixes 1 to 3, because those
were defects this lane introduced.
