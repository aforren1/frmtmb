# Review of lane loglik (2026-10-27)

Reviewer of `wt-loglik` (base 70476dc3, uncommitted diff). Lane library
`wt-loglik-lib` read only; no build of my own was needed. Scripts are
`dev/review-loglik-*.R` and `dev/review-loglik-bin2.sh`; logs are in

The values are right. Every case I added agrees with brms 2.23.0. The

## Findings

### 1. major: the Jacobian check runs only at sigma = 1 and the start theta, so it passes wrong slots

`autocor_seam_check_map()` compares `K (y - m)` with `whiten(y)$u` at
`sg <- autocor_seam_sigma(e, 1, n)` and `st <- start(aux)`. For
`sar()`, `sar_start()` is rho = 0, so the check of sar's own slot
verifies only `K = I`. For `fcor()` it verifies `Linv` and not the
division by sigma.

Evidence: `dev/review-loglik-seam.R`, seed 81, n = 40,
`dev/review-loglik-log/seam.txt`. Each slot below was registered,
accepted by `frm()`, and gave this relative error against the dense
conditional:

    rvnosig sigma ~ x        ACCEPTED, rel err vs dense = 1.047e-01   (K = Linv, no / sigma)
    rvnosig constant 1.7     ACCEPTED, rel err vs dense = 3.040e-01
    rvrows sigma ~ x         ACCEPTED, rel err vs dense = 4.357e-01   (Linv / sigma: rows, not columns)
    rvrows constant 1.7      ACCEPTED, rel err vs dense = 2.544e-16
    rvnorho rho = tanh(0.8)  ACCEPTED, rel err vs dense = 2.322e-01   (ignores rho; start rho = 0)
    rvtrans rho = tanh(0.8)  ACCEPTED, rel err vs dense = 8.844e-02   (K', asymmetric W)
    rvright rho = tanh(0.8)  ACCEPTED, rel err vs dense = 1.391e-15   (guard absent)

`rvrows` is the help-page example `aux$Linv / sigma`, used with
`sigma_varies = TRUE`. NEWS and `?frmtmb_register_autocor` say "a wrong
one is refused by the term's name". For these slips that is false, and
`log_lik()` is then wrong with no message. The lane's own refusal test
uses the transpose of a lower-triangular `Linv`, which also differs at
sigma = 1.

Fix: also check at a second, generic point. Use a non-unit sigma (row
varying when `sigma_varies`, for example `exp(0.3 * sin(seq_len(n)))`,
or 1.37 when constant) and `theta = start + 0.4 * seq_along(start)`. A
logit-mapped bounded parameter stays inside its interval. The check is
one `K %*% v`, so it is cheap. Add the four slips above as refusal
tests, and keep `rvright` and fcor/sar as the absent cases. State the
evaluation points in "The Jacobian". In the example, add a comment that
`Linv / sigma` holds only for a scalar sigma.

### 2. major: the 8 SAR rows will be recorded as plain "pass" although brms's input was replaced

On the lane build and on rellib-r13 I reran both generated files
(`dev/review-loglik-bin2.sh`, sequential, own staging directory). Logs
are `dev/review-loglik-log/run-{lane,base}-*.txt` and
`rec-{lane,base}-*.tsv`.

    lane  log_lik           pass=97 fail=0 err=0 skip=0 blocks=15
    lane  posterior_predict pass=61 fail=0 err=0 skip=0 blocks=14
    base  log_lik           pass=97 ...   (record: 7 rows held=FALSE, "STALE: ... 'autocor_row_loglik' is not an exported object")
    base  posterior_predict pass=61 ...   (record: 6 rows held=TRUE)

This confirms the lane's arms: 13 rows hold on the lane, the 7 log_lik
rows fail on base, and the 6 posterior_predict rows hold on base. The
adapters reach the real code: `autocor_row_loglik()` is the function
that frmtmb.sample's `log_lik()` calls per draw, and
`sim_context()`/`sim_draw()` are the simulator. The value checks hold
against brms's own `log_lik_*()` on the substituted prep (lane record,
max rel 3.12e-16).

The path graph is a fair substitute for what the rows assert. brms's
rows check only `dim(ll)` and `dim(pred)`, and the path graph also
exercises a nonzero rho. But `dev/brmsport-bin2-ledger.R` gives a
held row with no manual verdict `verdict = "pass", reason = ""`. At
consolidation the 4 SAR `log_lik` rows and the 4 SAR `posterior_predict`
rows would therefore be indistinguishable from literal passes. On
brms's literal input (`Msar = diag(10)`) frmtmb refuses, by design.
`dev/round-20261024.md` expected exactly this: "a literal port gives 4
divergence rows; with a path-graph W ... they pass", and "the pass
count would rise by 2 to 6". The lane counts 13.

Fix (consolidation decides): record the 8 rows with a reason that
names the input substitution. That means a manual-verdict class that
keeps "pass" but carries the reason (`held_classes` would make them
"hollow", which is also wrong, so the ledger script needs one more
class). Or emit the literal row as "divergence by design" beside the
adapted assertion. Report the pass delta as 5 literal (the fcor rows)
plus 8 adapted, not 13.

### 3. minor: the dense fallback has no size limit

Without a slot, each draw calls `unwhiten(diag(n))` and then
`solve(B)`. Evidence: `dev/review-loglik-seam.R`,
`dev/review-loglik-log/seam.txt`, one `autocor_row_loglik()` call on a
registered lag SAR without a slot:

    n =   250  call 0.020 s  peak Mb 7
    n =   500  call 0.080 s  peak Mb 29
    n =  1000  call 0.640 s  peak Mb 77
    n =  2000  call 4.330 s  peak Mb 306

The time grows as n^3. At n = 2000 a 4000-draw `log_lik()` takes about
4.8 h. At n = 5000 the extrapolation is about 70 s and 2 GB per draw.
Fix: above a documented size (n > 2000, for example), refuse with a
message that names `jacobian =`, or message the cost once per
`log_lik()` call. Put the measured cost in "The Jacobian".

### 4. minor: no test shows that sar() uses its slot

The fallback agrees with the slot to 6.96e-15 (lane cost log; my rerun
`dev/review-loglik-log/cost.txt`: "sarfb vs sar 6.960e-15"), and every

1440 ms against sar 1.816 ms per draw). I did not run this. Fix: assert

sparse `Matrix`, in test-sar.R.

### 5. minor: the gap divergence is not stated where a log_lik() user reads

I verified the claim. `dev/review-loglik-brms.R`, seed 71,

    ar interior gap (expected to differ)     3 x 22  rel = 1.721e-01

for an interior gap under `ar()`/`ma()`/`arma()`, so a ported brms
script silently fits another model.

  - a model with the term in two responses raises it 2 times, once per
    block.

  So it fires once per frame build, not per draw.
- **Correct terms never raise it.** I checked fcor (constant sigma and
  `sigma ~ x`) and sar lag and error over a row-standardized path graph,
  a symmetric normalized path graph, a star graph, an unnormalized
  adjacency (rho on (-0.501, 0.501)), a W scaled so that rho is on
  (-0.025, 0.025), and an 8 x 8 lattice. Each ran both as
  `dry_run = "objective"` and as a full ML fit: 0 unchecked warnings
  and no other warning in all 32 runs.
- **Why no correct sar can raise it.** sar's rho is logit-mapped
  inside its eigenvalue interval, so a step of plus or minus 0.4 on the
  internal scale cannot leave the interval, whatever W is. The narrow
  interval (+/- 0.025) shows this.

### Item 2: `frmtmb:::autocor_loo_dense_max` in frmtmb.spatial's test-sar.R (acceptable)

`dev/core-boundary.md`, "Interface before move", forbids `frmtmb:::`
in an extension's `R/` code: "no code in their `R/` reads a core
internal. Some of their tests do." The lane-env rule "Interface before
move" is about "the new home", which is the package code.

There is precedent. test-sar.R already used
`frmtmb:::autocor_natural` at base 70476dc3. frmtmb.spatial's tests

If core renames the constant, the test fails loudly ("object not
found"). It cannot pass silently, because the block asserts
`expect_gt(s$n, lim)`.

free of `:::`, add a documented option. For example,
`getOption("frmtmb.autocor_dense_max", 1000L)` read by core and named
in "The Jacobian". This also lets a user tune the warning. The test
would then set the option, instead of reading the constant.
