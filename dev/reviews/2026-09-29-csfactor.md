### Finding 1, minor and silent: an NA from `cooks.distance()`

Deleting row 120 removes the only row of level `c`. The refit's
`drop.unused.levels = TRUE` then builds ONE cs column instead of two, so
that refit's coefficient names are a strict subset of the full fit's.
`influence()` fills by name (`fe[i, names(fe_i)] <- fe_i`,
`R/influence.R:94`), so the `fcc[1]`, `fcc[2]` cells of row 120 stay
`NA` and `cooks.distance()` gives NA for that unit. Measured: 1 NA of
120 on the worker's build, 0 of 120 on the reference build, same data
and seed. The refit did NOT fail, so nothing is counted or warned.

This is a behavior change (a number became an NA), it is arguably the
honest answer, and it is silent. It is a nit and not a blocker, because
the NA is visible in the output and a coefficient that the deleted
subset cannot estimate has no defensible value.

**Where it meets lane wt-thresrefit.** That lane adds `thres_pin` to
`assemble_frame()` so a deletion refit keeps the FITTED threshold count,
and counts failed refits so a partly NA table warns and an all-NA table
errors (`frmtmb-wt-thresrefit`, `R/influence.R`). Neither mechanism
reaches this case: the cs refit does not fail, so the new counter never
sees it, and `thres_pin` pins thresholds, not `xlevels`. After both
lanes merge, an ordinal threshold that a deletion would have dropped is
pinned and an outright failure is reported, while a `cs()` factor level
that a deletion drops still produces a quiet NA. The matching fix would
be to pin the fit's `xlevels` into the deletion refit's frame the way
`thres_pin` pins the thresholds. Both lanes also edit `R/frame.R`'s
`assemble_frame()`, `NEWS.md` (both add a
`# frmtmb (development version)` heading) and `man/frm.Rd`; expect
textual conflicts there at consolidation.

`influence(groups = )` could not be measured for this question: the
grouping variable has to be in the model, and a `(1 | g)` term changes
the construction. Recorded as not settled; the observation-wise path is
the same code.

    Write 'x + cs(x)' as 'cs(x)' alone

### Finding 3, BLOCKING as a record defect: the `mo()` hole

`dev/csfactor-rev-gap.R`, seed 1907, n = 300, `m` an ordered factor with
4 levels, worker's build:

    X columns: mom
    X column sums of squares: 0
    cs labels: csm.L, csm.Q, csm.C
    rank(cbind(1, X)) = 1   ncol = 2
      j=1 rank(cbind(M, Z[,1:1])) = 2  needs >= 2
      j=2 rank(cbind(M, Z[,1:2])) = 3  needs >= 3
      j=3 rank(cbind(M, Z[,1:3])) = 4  needs >= 4
    qr() default tol = 1e-07

    logLik(mo(m) + cs(m)) = -327.579435714   df = 11
    logLik(cs(m))         = -327.579435720   df = 8
    difference            = 6.425751e-09
    vcov eigenvalues: 1.197e+04 0.0725 0.07128 0.06997 0.04112 0.01772
                      0.003413 -1.473e+04 -2.713e+05
    NaN standard errors: 9 of 9

Three extra degrees of freedom buy 6.4e-09 of log likelihood. That is
not a measurement of a small effect, it is the optimizer's noise on an
exactly flat subspace: `cs(m)` on an ordered factor with 4 levels spans
every function of `m`, and `mo(m)` is a monotone function of `m`, so
`mo(m)`'s contribution lies inside the cs span and the substitution that
the refusal exists to catch applies verbatim. The fit is reported with
two negative covariance eigenvalues and NaN on every standard error,
which is the exact symptom the lane set out to remove.

The reason the check misses it is the design decision the findings state
and do not follow through: `X`'s `mo()` column is an all-zero
placeholder that the objective fills later, the test compares against
`rank(cbind(1, X))` rather than its column count, and so the placeholder
contributes nothing to `base`. Every `cs()` column then raises the rank
and the loop passes.

Pre-existing, not a regression: the reference build fits
`mo(m) + cs(m)` too, with 5 NaN standard errors. So this is not a
blocker on the code. It is a blocker on the write-up: `?frm`, `NEWS.md`
and the findings all present the refusal as covering "a column written
on BOTH sides", with `y ~ I(x) + cs(x)` and `y ~ x1 + x2 + cs(x1 + x2)`
named as proof that it is a rank test rather than a name test. A reader
concludes that an unidentified `cs()` model is now impossible. It is
one `mo()` away. The gap needs a sentence in the findings and one in
`?frm`, and `me()`/`mi()` need the same sentence for the same reason.
`me(x, sdx) + cs(x)` fits with 0 NaN standard errors on both builds, so
that one may be genuinely identified; it was not settled here.

### 1a the span, checked numerically at a non-uniform simplex

`dev/csfactor-rev2-mo.R`, seed 3151, n = 600, `m` an ordered factor of 4

`c(0, 0.15, 0.30, 1.30)` so the fitted simplex is far from uniform.

    zeta = 0.000000 0.178665 0.821335      (uniform would be 0.333333)
    max/min zeta ratio = 42916719.686

The relation is an IDENTITY, not a measurement: `D * cz0[codes + 1]` is
by construction a function of `codes` that vanishes at code 0, and the
treatment dummies of the codes are a basis for exactly that space, so
the residual is zero algebraically. The two figures above are the
numerical check at full precision, relative residual 8.7e-15. The ten
random simplices are there because the refusal must hold for EVERY
simplex, not for the fitted one.

The worker's argument is therefore right, and the refusal condition is
the right one for a second reason worth stating: a `cs()` column carries
one coefficient per BOUNDARY, so shifting all of a column's boundary
coefficients by the same amount reproduces a population-level effect of
that column. That makes `span(1, X, Z)` exactly the set of
common-to-every-boundary directions available, which is the space the
test compares `Dmo` against. And because the test requires the WHOLE of
`span(Dmo)` to be inside it, no accident of the fitted simplex can turn
the verdict either way.

### Finding R2 (nit): the fallback advice pastes the poly example in

`cs_alias_advice()`'s third branch is a fixed string. On
`x + z + cs(I(x + z))` the message reads, after correctly naming
`('x', 'z')`:

    No population-level term spells 'I(x + z)' on its own, so drop the
    cs(), or respell the term above so that column is gone: 'I(x^2) +
    cs(x)' in place of 'poly(x, 2) + cs(x)' reaches the same maximum
    with one parameter fewer.

"the term above" refers to nothing in that formula, and the worked
example is about a different formula. The correct advice is to drop one
of `x`, `z` or the `cs()`. This is round 1's nit 5 narrowed rather than
closed: the poly case was fixed and the poly example then became the
generic fallback. It is a nit and not a blocker, because the message
still names the aliased columns correctly and still offers "drop the
cs()", which is a correct escape. `y ~ x1 + x2 + cs(x1 + x2)` is one of
the shapes the `NEWS.md` bullet advertises, and the new test block pins
only the `('x', 'z')` half of that message, so nothing caught it.

A second, smaller one: the `mo()` message says "Keep one of the two",
which for `mo(m) * z + cs(m)` is not the only option.
`z + mo(m):z + cs(m)` keeps the interaction and fits (df 12, logLik
-327.001146171, 0 non-finite standard errors).
