### 2. MINOR: `prior_summary()` of the merged R1 pair prints one class row and drops the class row the user wrote

Release fix R1 replaces both specifications with the merged one. The
sampled prior is correct, but the summary no longer shows what the
user wrote. Evidence: `dev/review-rel078-b-run/r1b.R`, `r1b-r16.txt`
and `r1b-r15.txt`, data seed 2, sampler seed 7.

The case: `a ~ 1`, with `frm(prior = pA)` and then
`frm_sample(fit, prior = pB2)`. Here pA is `set_prior("normal(5, 0.1)",
class = "Intercept", nlpar = "a")`, and pB2 is
`set_prior("normal(10, 1)", class = "b", nlpar = "a", lb = 2)`.

| library | `prior_summary()` rows for `a` | `b_a_Intercept` mean |
|---|---|---|
| rellib-r15 | `normal(5, 0.1)` b coef `Intercept`; `normal(10, 1)` b, lb 2 | 4.856 |
| rellib-r16 | `normal(5, 0.1)` b, lb 2 (one class row) | 4.856 |

The draws are the same in both libraries. brms keeps both rows (the
coefficient row and the class row with its bound). On rellib-r16, the
class row reads `normal(5, 0.1)`, which the user did not write on the
class, and the user's `normal(10, 1)` is gone from the summary.
`update(fitA, prior = pB)` prints the same single row
(`x8-r16.txt`). The summary round-trips, because it holds the effective
prior.

Required fix: keep both rows in the printed record, for example by
merging into a private slot and printing the inputs. Or say in
`?frm_sample` and in the R1 NEWS bullet that the summary shows the
merged row. Otherwise file it.

### 4. NIT: the dry run's "no git write" is not strictly true, so I did not run it

`dev/rel078-commit.sh --dry-run` runs `git add -A -n` in each of the
four trees, twice: once for the reviewer-scratch check and once for the
path lists. `GIT_OPTIONAL_LOCKS=0` covers only optional locks, such as
the refresh that `git status` makes. `git add` takes the index lock
`index.lock` unconditionally, before it reads the index, and with
nothing changed it rolls the lock back. This is from git's
`builtin/add.c`. I read it and did not run it.

So the dry run creates and removes one lock file per tree, and it fails
if another git process holds the lock. It does not change the index's
content.

I did not run `--dry-run`, because by reading I could not confirm that
it makes no git write. I reproduced its counts read-only instead
(section 8).

Required fix: in the script's header and the record, say that the dry
run takes and releases each tree's index lock. Or list the paths with
`git status --porcelain --untracked-files=all` and a pathspec filter,
which needs no lock.

### 3. Release fix R1

Evidence: `b-run/r1.R`, `r1b.R` and `x8.R` on both libraries, data
seed 2, sampler seed 7. Each case compares the resolver
`frmtmb.sample:::sample_resolve_priors()` with core's
`resolve_prior_input()` in both orders. Then it compares `frm()`,
`frm_sample()` and brms 2.23.0's `stancode()`.

Notation:
- pA: class `Intercept`, nlpar `a`;
- pB: class `b`, nlpar `a`;
- pC: brms's `class = "b", coef = "Intercept"`.

Results:
- **Both orders.** Densities only, both orders: pA's density stands.
  brms writes pC's density on `b_a[1]`.
- **One-sided bounds.**
  - pA lb 1 with pB ub 10 gives lb 1, ub 10.
  - pA ub 10 with pB lb 1 gives the same.
  - pA `""` ub 10 with pB's density and lb 1 gives pB's density with
    lb 1, ub 10. brms writes `normal_lpdf(b_a | 0, 0.1)` with
    `<lower=1>`.
- **Both bounded differently.**
  - pA lb 1 ub 10 with pB lb 2 ub 8 gives lb 1, ub 10 (pA wins on each
    side).
  - pA lb 2 with pB lb 1 ub 10 gives lb 2, ub 10.
  - pA `""` lb 1 with pB `""` ub 9 gives flat, lb 1, ub 9.
  - Each is the same in both orders, and the same as `frm()`.
- **nlpar with `(1 | g)`.** The rewrite fires. The `sd` row is not
  touched: `theta_1` keeps student_t, or takes an explicit `sd nlpar a`
  row.
- **nlpar with a slope** (`a ~ 1 + w`). No rewrite: pA stays a
  coefficient row. With a bound, `frm_sample()` refuses it, as brms
  refuses a coefficient bound. `frm()` keeps the box, the documented
  exemption.
- **Several nlpars.** pA on `a` with pB on `b` does not merge. pA(a) +
  pB(a) + pB(b) in three orders gives identical results. The only
  difference is the name order of the `lower` vector.
- **Multivariate nonlinear.** With `resp = "y2"` on both, the pair
  merges. pA on y with pB on y2 does not merge.
- **The fit's prior and the call's prior.**
  - `frm(prior = pA)` with `frm_sample(prior = pB2)` gives pA's

  - Finding 2 is the printed summary.
- **Duplicates in one call.** These are refused by both `frm()` and

  - pA + pC;
  - pA + pA2 + pB;
  - pB + pB2 + pA;
  - `c(table, pA)`.

  So the merge's `length(rw) != 1 || length(cl) != 1` exit cannot be
