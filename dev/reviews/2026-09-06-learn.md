## (b) The engine

`R/engine.R` and `R/family.R` read end to end.

**The trial loop is right.** `ln_recurse()` (engine.R:167) loops over
`ncol(idx)`, the trial count, and every quantity inside is a vector over
subjects. There is no loop over observations anywhere on the likelihood
path. The only per-option loops are over 2 or 4.

**RTMB pitfalls: clean, and by construction rather than by care.** There
is no `ADoverload()` call in the package and none is needed, because no
advector is ever sub-assigned. The value store is a named list and the
engine advances it with whole-vector arithmetic in `ln_blend()`
(engine.R:71); list `[[<-` is not advector `[<-`. Every `[<-` in the
package writes a plain double off the tape: `pm[, k]` (engine.R:181,
simulate only), `ysim` (:186), `sc` (:203), `tr` (:213), `out[hit]`
(:91), and the payoff columns in `task.R`. Base `matrix()` appears three
times (engine.R:179, family.R:71 and :73, task.R:60) and every one is on
plain integers or doubles, never an advector. No `rowSums()`, `colSums()`
or `apply()` on an advector; `rep(each =)` appears once, in `task.R:60`,
on doubles. Broadcasting is done by multiplication against `rep(1, ns)`
(bandit4arm2-kalman.R:84), which is the recommended form.

**Tape safety: clean.** Every `if` in the recursion branches on `mode`,
on `j`, or on a family constant fixed at construction, never on a
parameter. Every comparison that reaches a numeric is on DATA:
`as.numeric(v == k)` on the response (engine.R:151), `m == 1` on the
mask, `d[["stage21"]] == 1` on an addition term (ts-par7.R:109, :115),
and `x >= 0` / `w > 0` in igt-pvl-delta.R:98-103 where `x` is
`sum(indicator * payoff)` and both factors are data. The softmax goes
through `RTMB::logspace_add()` (`ln_lse()`, engine.R:111) and the
two-step maximum through the `abs` identity (`ln_max2()`, engine.R:106).

The one parameter-dependent selection is `sign(pec)` in
bandit2arm-dual.R:74. I checked that RTMB 1.9 implements `sign()` as a
real AD operation rather than freezing it at the tape point: taping
`sum(sign(x) * x^2)` at `x = -2` and evaluating at `x = +2` returns
4.25 and gradient 4, both correct. So `split = "pe"` is sound and the
family's comment about it is accurate.

**The by-name blending bug: reproduced.** The mechanism is real.
`bandit4arm2_kalman_filter()`'s `init` returns `mu1..mu4, s1..s4`
(bandit4arm2-kalman.R:86) while its `update` fills `out` inside a loop
over arms and so returns `mu1, s1, mu2, s2, ...` (:108-110). I reverted
`ln_blend()` to positional matching in a scratch copy, installed it to a
separate library and refitted the identity tier's own Kalman fixture
(10 subjects, 500 rows, seed 104). Both variants converge. Numbers:

| | joint at own estimates | logLik |
|---|---|---|
| name-blended (shipped) | -141.7830 | -447.6321 |
| position-blended (reverted) | -607.2948 | -611.9547 |

The shipped joint of -141.7830 matches `dev/learn-findings.md:304` to
all printed digits, so this is the same fixture the lane used. Evaluating
the CORRECT engine at the buggy fit's own parameter vector gives
-536.7140 against the buggy engine's -607.2948, a gap of 70.6 units;
refit against refit the logLik gap is 164.3 units. Neither is the 206
the findings document claims (see finding L4).

`ln_blend()`'s refusal on mismatched names works and is checked; the
guard compares `setequal(names(old), names(new))`, so it catches a
renamed or dropped slot but would not catch a duplicated name. Not worth
a punch item.

**The identity constant is zero, and the reason is stated and correct.**
There is no per-family constant: `ln_lp_check()` (helper-stan.R:155)
asserts `abs(lp - ours) < 1e-6 * max(1, |ours|)` and it passes at 1e-13.
The three reasons in helper-stan.R:12-19 are each real. The programs
declare exactly frmtmb's parameters on frmtmb's scales, so there is no
Jacobian; `target +=` with `_lpdf`/`_lpmf` keeps normalizing constants
that a `~` statement would drop; and `sd_u` is passed as DATA
(helper-stan.R:105), so no constrained parameter reaches `log_prob()`
and `adjust_transform = FALSE` has nothing to discard.

**The Stan programs are the lane's own code.** I read all seven against
hBayesDM 2.0.0's published `inst/stan_files/*.stan`, downloaded from
CRAN for this review. They are not a port. hBayesDM parameterizes
hierarchically with `mu_pr`, `sigma` and `*_pr` through `Phi_approx`
bounded transforms and loops `for (i in 1:N)` over subject-indexed
arrays; the lane's programs take a design matrix `X`, an `idx`/`mask`
block, a fixed `sd_u` as data, and plain `log`/`logit` links, and
increment `target` directly. No variable name, block structure or
comment is shared beyond the unavoidable (`ev`/`q`, `PE`/`pe`). This is
a clean-room implementation from the published equations and the
licensing claim holds.

**The gradient assertion covers the subject effects only.** `gin` is
asserted below `1e-4`; `gall` is computed and logged but never asserted
(helper-stan.R:164-166). The stated reason is correct: maximum
likelihood makes the MARGINAL likelihood stationary, not the joint one,
so the joint gradient with respect to the fixed effects is not zero at
that point and cannot be asserted against zero. But that is an argument
against comparing it TO ZERO, not against comparing it to frmtmb's own
gradient, which is available as `fit$obj$env$gr(par)` and would catch a
wrong fixed-effect map that the single-point value identity can miss.
See finding L7.

**One identity row asserts nothing the row above it does not.**
`bandit2arm_dual (pe)` and `(outcome)` return identical numbers, because
the fixture uses binary payoffs where the two splits are provably the
same model (the package says so itself, NEWS and `?bandit2arm_dual`).
So the `outcome` branch of `ln_stan_code_dual()` is never exercised
where it differs from the `pe` branch. The ungated `test-families.R:77-87`
does separate them on graded payoffs, so the R side is covered; no Stan
identity is. Finding L8.

## Findings, ranked

### L1. `prl_fictitious`'s `bias` is not hBayesDM's `alpha` up to sign

**Severity: high.** The documentation asserts a specific relationship
that is wrong.

`R/prl-fictitious.R:20-31` says of `bias`: "hBayesDM's `alpha` is the
same quantity and is subtracted rather than added there, so the two
differ in sign." `R/trace.R:127` maps `alpha, bias, tau` to
`eta, alpha, beta` as a plain rename.

hBayesDM 2.0.0 `inst/stan_files/prl_fictitious.stan` computes

    prob[1] = 1 / (1 + exp(beta[i] * (alpha[i] - (ev[1] - ev[2]))));

which is `inv_logit(beta * (ev1 - ev2) - beta * alpha)`. This family
(`R/prl-fictitious.R:62-63`) computes `inv_logit(tau * (ev1 - ev2) + bias)`.
So the true relation is

    bias = -tau * alpha_hBayesDM

not `-alpha_hBayesDM`. The two differ by a factor of `tau`, which is
itself an estimated parameter, so no fixed transform relates them and
the sentence is wrong rather than imprecise. At `tau = 3`, the value the
package's own examples use, a ported indecision point is off by 3x.

Reproduction: read the two expressions side by side. Source:
`https://cran.r-project.org/src/contrib/hBayesDM_2.0.0.tar.gz`,
`inst/stan_files/prl_fictitious.stan`.

### L2. `ts_par7`'s `pers` is not hBayesDM's `pi`, and the trace differs

**Severity: medium-high.**

`R/ts-par7.R:25-27` and `R/trace.R:129` present the seven parameters as a
rename of hBayesDM's `a1, beta1, a2, beta2, lambda, w, pi`. Two
deviations, neither documented.

**(a) Perseveration is inside the temperature here, outside it there.**
hBayesDM `ts_par7.stan`:

    level1_prob_choice2 = inv_logit(beta1[i] * (v_hybrid[2] - v_hybrid[1])
                                    + pi[i] * (2 * level1_choice[i, t-1] - 3));

`pi` is added OUTSIDE `beta1`. This family (`R/ts-par7.R:105-107`) puts
`pers * rep_k` INSIDE the bracket that `tau1` multiplies, so its
contribution to the same logit is `tau1 * pers * (rep2 - rep1)`. Hence

    pers = pi_hBayesDM / tau1

**(b) The eligibility trace uses a different `delta2`.** hBayesDM updates
`v_mf[2 + level2_choice] += a2 * (reward - v_mf[2 + level2_choice])`
BEFORE computing the trace term
`v_mf[level1_choice] += lambda * a1 * (reward - v_mf[2 + level2_choice])`,
so its effective trace is `lambda * a1 * (1 - a2) * delta2`. This family
(`R/ts-par7.R:130-134`) forms `delta2` from the pre-update value, which
is Daw and others (2011)'s own equation. **The family is right and
hBayesDM's code is the outlier here**, but the help presents the
relationship as a rename, so a user comparing fits meets a discrepancy
with no documented cause.

### L9. `?frmtmb.learn` misattributes the `loo()` and `waic()` refusal

**Severity: medium.**

`R/frmtmb.learn-package.R:67` says the missing per-group loglik slot
"costs `loo()`, `waic()` and deviance residuals". Deviance residuals,
yes. `loo()` and `waic()`, no: they refuse for every frmtmb fit, because
`frm()` is maximum likelihood. Measured on an ordinary gaussian fit and
on a learn fit, the message is identical:

    loo() is a posterior quantity and this is a maximum-likelihood fit:
    an elpd averages the likelihood over draws. Sample first, with
    frmtmb.sample::loo(...)

The refusal is core-wide and unrelated to this package's seam. As
