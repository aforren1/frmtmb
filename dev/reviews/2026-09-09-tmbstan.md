### N1: the examples are not covered, and they are the same disease

15 `.Rd` files in `frmtmb.sample/man` carry 18 sampler calls inside
`\examples{\donttest{...}}`, every one guarded by
`requireNamespace("tmbstan") && requireNamespace("rstan")` and nothing
else. That is the exact installed-only guard this lane spent its effort
removing from the tests.

They do run. `00check.log`:

    * checking examples with --run-donttest ... [15s] OK

and `frmtmb.sample-Ex.Rout` carries 16 `frm_sample(): default priors`
banners over 15 executed topics, so they sampled.

(Both figures are corrected in round two below. The first pass said 19
calls and 20 banners; both were mine and both were wrong.)

From R's own check code
(`tools:::.check_packages`), `test_donttest <- !run_donttest && (if (x
== "NA") as_cran else config_val_to_logical(x))`, so `\donttest`
examples run whenever `--as-cran` is passed and
`_R_CHECK_DONTTEST_EXAMPLES_` is unset.

Why CI does not hit it today: `check-frmtmb-sample.yaml` passes
`args: 'c("--no-manual")'`, dropping the `--as-cran` that
`r-lib/actions/check-r-package@v2` puts in by default
(`args` default `c("--no-manual", "--as-cran")`, confirmed from the
action's `action.yaml`). So the exposure is a developer running the
command the lane rules themselves prescribe, and any future restoration
of the action's default args.

The consequence is not a wrong answer: on a broken build these ERROR on
the refusal. But it does falsify the record's stated property that a
broken build leaves "the job red for one legible reason instead of green
or drowned in 108 errors". Under `--as-cran` it is one legible reason
plus up to 20 example errors. The fix is one line per Rd source: add
`!frmtmb.sample:::tmbstan_build_broken()` to the `if`, or wrap the
examples' sampler calls in a helper that already asks.

### The construction does exercise the real detector

`with_tmbstan_hpp()` takes `environment(frmtmb.sample:::tmbstan_build_
broken)`, which is the `local()` frame of the installed function, and
binds `system.file` there. That frame's child is the function body
itself, so the shadow is seen by exactly the one call the detector
makes and by nothing else in the namespace. The function object under
test is the installed one, not a copy. Empirically: if the assignment
did not take, block 2's `expect_true()` would fail. It passes, and the
whole file passes 14 expectations in the clean arm.

`on.exit()` is registered BEFORE both assignments, so an error inside
`code` still restores. The memo is reset to `NULL` rather than to its
prior value, and block 2's trailing `expect_false()` re-reads the real
`model.hpp` to prove the borrow was handed back. That is the right
shape.

### The synthesized model.hpp is faithful in shape, and the real marker is real

I downloaded the artifacts myself and read them (see Claim 4). The
broken article has TWO `log_prob_impl` definitions:

    line 242  stan::require_st_var<VecR>       UNPATCHED at 273

and line 273 is

**N3:** the fixture's PATCHED arm writes two overloads both patched and

Nothing in the suite asserts that the marker string matches a genuine

### A positive result the record does not claim

The detector cannot produce a false NEGATIVE against the current
upstream. From tmbstan 1.2.0's own `tools/autogen.R`:

    pattern <- "lp_accum__.add(stan::math::std_normal_lpdf<propto__>(y));"
    i <- grep(pattern, mod, fixed = TRUE)
    stopifnot( length(i) >= 1 )
    if (length(i) > 1) warning("More than one match; Using first")

frmtmb's marker `std_normal_lpdf<propto__>(y)` is a strict substring of
that literal, and `configure` runs autogen at install time, so any
tmbstan that installed at all had at least one match and patched exactly
one. If two matched, one survives and carries frmtmb's substring. So
"detected" and "defective" coincide for as long as autogen's own pattern
is this literal. That bounds the brittleness, and it is worth recording
because "it is a string match, therefore fragile" was the obvious
objection and it is wrong in this direction.

The residual risk is upstream changing the emission and autogen's
pattern together. Measured, `dev/rev-tmbstan-absent.R` row 3: a defect
written as `std_normal_lpdf<propto__, false>(y)` gives
`detector=FALSE refuses=FALSE skip_sampler=ran`. Nothing in the suite
would notice, because the only assertions that would are the
chain-agreement ones this workflow turns off. See "The gates question".

## Claim 3, the CI pin. FALSIFIED

### B1: the substitution is applied to the wrong repository, so the job aborts

The step reads

    repo <- getOption("repos")[["CRAN"]]
    pin  <- sub("/latest/?$", "/2026-09-01", repo)
    if (identical(pin, repo)) stop("could not derive a dated snapshot ...")

On a runner configured by `r-lib/actions/setup-r@v2` with
`use-public-rspm: true`, the CRAN entry is not the RSPM URL. The action
writes an `.Rprofile` containing

    repos <- c(
      RSPM = 'https://packagemanager.posit.co/cran/__linux__/noble/latest',
      CRAN = 'https://cran.rstudio.com'
    )

`setup-r/src/installer.ts` builds `rspm` from the codename and the
snapshot, then separately
`const cran = '${cran_input || "https://cran.rstudio.com"}'`, and
`setup-r/action.yml` gives the `cran` input NO default. This workflow
sets neither the `cran` input nor the `CRAN` or `RSPM` environment
variables, so `cran_input` is empty and the mirror is the literal
default.

This is not an inference. The runner prints the table itself. Run
34329755305 (2026-09-09, the red run), step
`Run r-lib/actions/setup-r-dependencies@v2`, group `Repo status`:

    1  RSPM  https://packagemanager.posit.co/cran/__linux__/noble/latest
    2  CRAN  https://cran.rstudio.com

Replaying the step's arithmetic, `dev/rev-tmbstan-pin-derivation.R`:

    CRAN   in : https://cran.rstudio.com
    CRAN   out: https://cran.rstudio.com
    CRAN   no-op (step calls stop()): TRUE

    RSPM   in : .../__linux__/noble/latest
    RSPM   out: .../__linux__/noble/2026-09-01
    RSPM   no-op (step calls stop()): FALSE

So on the first push the step reaches its `stop()`, `Rscript` exits 1
(measured: `Rscript -e 'stop("x")'` gives exit 1), the step has no
`continue-on-error` and the job has none, so the job FAILS with
"could not derive a dated snapshot from https://cran.rstudio.com" and
`check-r-package` never runs. No clean tmbstan is installed, the tier
never runs, and the failure message points at the RSPM layout, which is
present and correct. That is the confusing failure the guard was written
to prevent, arriving because the guard is reading the wrong string.

The `sub()` itself is right, including the trailing-slash case. Only its
input is wrong. Fix: `repo <- Sys.getenv("RSPM")` (the action exports
it, visible at line 1606 of the red run's log) or
`getOption("repos")[["RSPM"]]`, and keep the no-op `stop()`, which is
the part of the design that turned this from a silent no-op into a loud
one.

The same wrong `repo` reaches the obsolescence probe, and there it is
worse than a stop. `available.packages(repos = repo)` and
`download.file(paste0(repo, "/src/contrib/tmbstan_", ver, ".tar.gz"))`
would fetch the CRAN SOURCE tarball. I downloaded it: the source ships
`tmbstan/inst/model.hpp` and `tmbstan/src/include/model.hpp`, identical
(md5 `20a43fac...`), 516 lines, 0 markers, and `configure` regenerates
both at install time. So:

- at the probed path `tmbstan/model.hpp` there is no file, so
  `file.exists()` is FALSE and the probe stays silent, which is the
  failure the record already predicted; and
- **a maintainer who "fixes" that by pointing the probe at
  `inst/model.hpp` would get a warning that is ALWAYS true**, because
  the shipped copy is the stale clean one no matter what the build
  produces. Write that trap down beside the probe.

Both go away with the RSPM URL, where `X-Package-Type: binary` is served
and `tmbstan/model.hpp` is the built one.

### B2: the workflow's own detector fails open, and then asserts the opposite

    unpatched <- function(path) {
      nzchar(path) && any(grepl(marker, readLines(path), fixed = TRUE))
    }
    hpp <- system.file("model.hpp", package = "tmbstan")
    bad <- unpatched(hpp)
    say("- model.hpp patched: **", !bad, "**")

If `system.file()` answers `""`, `bad` is FALSE and the step PRINTS
`model.hpp patched: TRUE` into `$GITHUB_STEP_SUMMARY` and passes. That
is a printed truth from an unmeasured state, which is precisely what the
lane rules forbid. The package's `tmbstan_build_broken()` shares the
`nzchar()` and is only a skip decision; here the same expression becomes
a positive claim in the report the whole design leans on.

Make the empty path a third state and stop on it:

    if (!nzchar(hpp)) stop("tmbstan installed no model.hpp; this check ",
                           "cannot tell whether the build is patched")

### What else the dated snapshot pins, and whether it conflicts

`install.packages(c("StanHeaders","rstan","tmbstan"), repos = pin)` uses
`dependencies = NA`, so it installs the three named packages plus any
Depends, Imports or LinkingTo that are MISSING or too old. By that point
the earlier step has installed the whole Suggests set from `latest`, and
the snapshot's requirements are a week older than what is installed, so
nothing else should come from the snapshot. The three that do come from
it are the three that must move together.

The question that matters is which INSTALLED package was compiled
against the StanHeaders being downgraded. Checked by reading
`LinkingTo:` in the installed DESCRIPTIONs: of `rstan`, `brms`,
`bayesplot`, `rstantools`, `QuickJSR`, `loo`, `bridgesampling` and
`RcppParallel`, only `rstan` links to StanHeaders. `rstan` is replaced
in the same call, and `tmbstan` links to it too and is also replaced.
`brms` and `bayesplot` use rstan only at the R level. So the trio stays
self-consistent and nothing else in the graph carries stale headers.
That is the strongest form of the record's "unlikely", and it is now
measured rather than assumed.

Two residual risks that a run settles and I cannot:

- `install.packages()` reporting a failure as a WARNING and continuing.
  The design already covers this well: the step re-reads `model.hpp`
  AFTER installing, so a silently failed pin leaves the old broken file
  and `bad` is TRUE and the step stops. Credit where due.
- the snapshot's binary for noble R-4.6 being pruned or rebuilt. Also
  covered, same way.

### Does the date pin expire, and would anyone notice

The record's answer, the obsolescence probe, is the right idea and is
the part of the step I would keep hardest. It reads the ARTIFACT, not
the version, which is correct: tmbstan stayed 1.2.0 through the whole
episode and only the build date moved. But as written it is aimed at the
wrong repository (B1) and would never fire. After the fix it fires on
every run once upstream is clean, which is the right cadence.

One case it does not cover: P3M rebuilding `latest` with the SAME defect
again. Then the probe stays silent and the pin stays, which is correct
behavior, so no change needed. The thing that would go unnoticed is the
opposite of the record's worry.

### Does the fail-the-job step actually fail the job

Yes. `shell: Rscript {0}`, an uncaught `stop()` exits 1, no
`continue-on-error` on the step or the job, `if:` absent, so subsequent
steps including `check-r-package` are skipped. The obsolescence probe's
own errors are inside `try(silent = TRUE)` and cannot reach it. The
`say()` calls run before the `stop()`, so the summary is written even on
the failing path. All correct.

## The two loose ends

### May a guard against a silent wrong answer fail open? Here, yes, but say so

`dev/rev-tmbstan-absent.R`, four constructions through the same seam:

| construction | detector | refuses | `skip_sampler()` |
| --- | --- | --- | --- |
| 1 no model.hpp at all | FALSE | FALSE | ran |
| 2 model.hpp present but EMPTY | FALSE | FALSE | ran |
| 3 the defect under a renamed marker | FALSE | FALSE | ran |
| 4 the defect as it ships today | TRUE | TRUE | skipped |

Row 2 is new; the record measured row 1 only.

Is "absent" reachable? Read upstream to find out. `configure` is
`Rscript -e 'source("tools/autogen.R")'`; autogen writes
`src/include/model.hpp`, then `file.copy()`s it to `inst/model.hpp`; and
`stopifnot(length(i) >= 1)` aborts the build if the placeholder is gone,
so a failing autogen fails the install rather than shipping a package
without the file. The source tarball also ships both copies, so
`--no-configure` gives a consistent stale pair, not an absent one.

So the reachable absences are: a corrupted library (this machine has had
two, and the lane rules exist because of them), a future tmbstan that
stops shipping the file, and `file.copy()` returning FALSE unchecked
inside autogen, which would leave the CLEAN shipped `inst/model.hpp`
beside a BROKEN compiled `src/include/model.hpp`. The last is the only
one that produces a genuinely silent wrong answer, it is upstream's to
fix, and frmtmb cannot see it.

Judgment. In the PACKAGE, fail-open is the right call: refusing every
installation whose `model.hpp` cannot be read would break correct
machines, and each reachable absence also breaks tmbstan itself, so the
user gets a loud runtime error rather than plausible draws. It must be
named in the `@noRd` block, which is N5 and is the record's own
recommendation. In the WORKFLOW it is not defensible, because there the
same expression is turned into a printed assertion. That is B2.

### Core's test-lkj.R: what should happen, and when

Confirmed by reading. `tmbstan_samples_the_model()` at
`tests/testthat/test-lkj.R:157` reimplements the detector and writes the
marker string a second time, and it fails open on an absent file in
exactly the same way (`!(nzchar(hpp) && ...)` gives TRUE). The block at
:376 has four skips in this order:

    skip_if_not(sampler_gates_on(), "chain-agreement gates are off")
    skip_if_not_installed("tmbstan")
    skip_if_not_installed("rstan")
    skip_if_not(tmbstan_samples_the_model(), ...)

`prior_rho()` is called from that block and nowhere else, so this is one
block, not a tier.

Where it bites: `R-CMD-check.yaml` sets no `FRMTMB_SAMPLER_GATES` and

## 1. The gradient assertion

### Attack A: is 0 ulp portable? Yes, and not by luck

The assertion as written is

    expect_lt(max(abs(g_stan - g_obj)) / scale,
              max(abs(g_bad - g_obj)) / scale / 1e6)

so it demands a relative discrepancy below about 1e-6. The question is
whether two independent gradient computations can be relied on to agree
that closely on a runner with a different compiler and BLAS.

They are not two independent computations. Traced through source, all
of it on this machine:

1. `tmbstan/model.stan` declares
   `vector<lower=make_bounds(lower_bound, N, 0),
   upper=make_bounds(upper_bound, N, 1)>[N] y`, and `as_tmbstan()`
   passes no bounds, so `have_bounds` is 0 and `make_bounds` returns
   plus and minus infinity.
2. `StanHeaders/include/stan/math/prim/constraint/lub_constrain.hpp`,
   the `lp` overload: `if (unlikely(is_ub_inf && is_lb_inf)) return
   identity_constrain(x, ub, lb);`. `lp` is NOT touched. So `lp__`
   stays 0.0 and the accumulator holds one term.
3. `tmbstan/src/include/custom_func.hpp`,
   `custom_func_vector_vari::chain()` calls
   `gradient_custom_func_as_double`, which either evaluates `R_gcall`
   (which is `obj$gr` in R) or calls `tmb_reverse` on the same ADFun
   pointer, then negates. It then does
   `vis_[i]->adj_ += adj_ * g(i)`.
4. `StanHeaders/.../rev/fun/sum.hpp`, the `std::vector<var>` overload:
   `arena_m.adj() += vi.adj()`, unscaled, so the accumulator transports
   the top adjoint unchanged.
5. `grad_log_prob` seeds the top adjoint at exactly 1.0.

So `vis_[i]->adj_` is `0.0 + 1.0 * (-obj$gr(u)[i])`, which is
`-obj$gr(u)[i]` bitwise. `rstan::grad_log_prob(sf, u)` does not compute
a gradient that happens to match TMB's; it transports TMB's own
doubles. The left side of the assertion is structurally 0 on every
platform, so it cannot false-alarm on a healthy build. Compiler, BLAS
and optimization level have nothing to act on.

Measured here anyway, `dev/rev-tmbstan-round2.R`, the block's own model
and seeds (`set.seed(4021)` for the data, `set.seed(4030)` for the
points, sampler seed 11):

| point | lhs | rhs | passes |
| --- | --- | --- | --- |
| `rep(0, np)` | 0.000e+00 | 1.000e-06 | TRUE |
| `par + 0.3` | 0.000e+00 | 9.888e-07 | TRUE |
| `par - 0.7` | 0.000e+00 | 9.992e-07 | TRUE |
| `rnorm(np)` | 0.000e+00 | 9.998e-07 | TRUE |

and `identical(grad_log_prob(sf, par + 0.3), -obj$gr(par + 0.3))` is
TRUE.

One consequence worth naming: because the left side is structurally 0,
the "separation factor of 1e6" is decoration. Any positive right side
passes. The property the assertion really has is stronger and simpler:
it fails the moment the Stan entry point stops delegating to TMB. That
is the right property and it should be described that way.

**N8**, filed not fixed: the identity depends on the bounds being
infinite. The block's comment explains why the model has no random
effects; it does not say why it has no bounds. A later edit that gives
the fixture `lower =` or `upper =` would add a Jacobian term to
`lp_accum__` and break the identity, and the failure would look like
the defect. One sentence in the comment closes it.

## 6. Restoring `--as-cran`: my view

The worker's caution is right. The reason given for it is wrong.

`r-lib/actions/check-r-package@v2` runs

    if (Sys.getenv("_R_CHECK_CRAN_INCOMING_", "") == "")
      Sys.setenv("_R_CHECK_CRAN_INCOMING_" = "false")

so the CRAN-incoming checks are ALREADY off in this job and would stay
off with `--as-cran` restored. That is not the cost.

The real cost is that `--as-cran` changes other verdicts under this
action's `error-on: "warning"` default. A concrete one from R's own
check source: when `qpdf` is missing, "'qpdf' is needed for checks on
size reduction of PDFs" is an info line normally and a WARNING under
`--as-cran`, which `error-on: "warning"` turns into a failed job. It
also sets `_R_CHECK_FF_AS_CRAN_` and enables example timings. None of
that can be seen without a push, which is the same objection the gates
flip carries.

**Recommendation: do not restore `--as-cran`. Add one line to the job's
`env:` instead:**

    _R_CHECK_DONTTEST_EXAMPLES_: "true"

From the check source already quoted,
`test_donttest <- !run_donttest && (if (x == "NA") as_cran else
config_val_to_logical(x))`, so this turns on the `\donttest` examples
and nothing else, with no change to any verdict's severity. It buys the
whole benefit of the discussion, which is that CI exercises the 18
example calls now that they carry the build guard, at none of the risk.
It should ride with this lane, because the guard it exercises is this
lane's work and the two land or fall together.
