# Release review: frmtmb 0.77.0 and frmtmb.sample 0.24.0, 2026-10-28

Adversarial review of the consolidation in `frmtmb-wt-rel077` (branch
`wt-rel077` at `435e7ce6`, uncommitted) and of the release library
`rellib-r15`. The record is `dev/round-20261028.md`. Everything below
was measured on this machine during the review. Scripts and logs are in
`dev/review-rel077-a-run/`, `dev/review-rel077-b-run/` and
`dev/review-rel077-c-run/` (all gitignored by `*-run/`). Seeds are in
the scripts.

## Verdict: FIX

The merge is correct: no lane hunk is lost, and every difference from a
plain merge of the four lanes is a recorded resolution or release fix.
The library matches the tree, the tests and floors reproduce the
record's numbers, and the cross-lane semantics are right. Two
exceptions:

- One major defect (finding 1). It is new in this release, and a user
  meets it in one ordinary step: `subset()` or a column selection of a
  `default_prior()` table removes the route mark that R1 and reslot's S1
  depend on. `frm_sample()` then samples `(flat)` in place of brms's
  defaults on the intercept, sigma and the standard deviations, with no
  message. The fix is a few lines.
- The record's claim that the dry run "makes no git write" is not quite
  true (finding 4).

Fix finding 1, then ship. The other findings are minor or nits; fix
them in the same pass or file them.

## Findings

### 1. MAJOR: `subset()` and a column selection drop the route mark, so a fit-route table's `(flat)` rows replace brms's defaults in silence

The mark is the `route` attribute of a `frmtmb_prior_rows` table.
`[.data.frame` keeps that attribute on a row subset. It drops the
attribute when the call gives `j`, and `subset()` always gives `j`. No
`[.frmtmb_prior_rows` method exists (`R/priors.R` defines only `print`
and `as.data.frame` for the class). So the result is still a
`frmtmb_prior_rows` table but has no route. `as_priorlist()` then
reads it as written: each `(flat)` row becomes brms's `(flat)`.

The R1 heuristic does not catch this, because it applies only to a
plain data frame read by `as.brmsprior()`.

Evidence (`dev/review-rel077-c-run/route.R`, `route.txt`, seed 11):
- Model: `y ~ x + (1 + x | g)` with `pf <- default_prior(f, data = d)`.
- Edit: one row set to `normal(0, 1)` on `b`/`x`.
- The table is passed to `frmtmb.sample:::sample_resolve_priors()`.

| prior = | route | effective prior |
|---|---|---|
| `pf` (edited) | fit | refused (correct) |
| `pf[pf$prior != "", ]` | fit | refused (correct) |
| `subset(pf, class != "cor")` | NULL | `beta[1]`, `theta[1]`, `theta[2]`, `betad[1]` **flat**; `beta[2]` normal; `theta[3]` lkj |
| `pf[, c("prior", "class", "coef", "group")]` | NULL | the same flat rows, and the LKJ **flat on L** |
| no prior (the defaults) | | `beta[1]`, `betad[1]`, `theta[1]`, `theta[2]` student_t; `theta[3]` lkj(1) |

Fork B's run sampled `frm_sample(fit, prior = pf[, cols])` for 200
iterations. Its `prior_summary()` is `(flat)` on all 10 rows
(`dev/review-rel077-b-run/r1b.R`, `r1b.txt`).

The same log shows which operations keep the mark:
- Kept: row subsetting, `head()`, `rbind()`, `unique()` and `$<-`.
- Lost: `pf[cols]`, `pf[, cols]` and `subset()`.

So the claims below hold only in part:
- The record says the mark "travels through `+`, `c()` and a column
  edit".
- frmtmb.sample's NEWS says a fit-route table is refused "edited or
  not".
- reslot's review S1 listed the forms it tried. None of them was a
  column selection or `subset()`.

Two related gaps are smaller, because each needs
`as.data.frame()` first. In each, a coerced fit-route table passes in
silence (`r1-route.txt`, lines 30 and 34):
- the `source` column is dropped;
- `source` is set to `"user"`.

Required fix:
- Add `[.frmtmb_prior_rows`, which keeps `route` (and the class) on
  every subset. `subset()` dispatches through it.
- Add tests to frmtmb.sample's `test-flat-prior.R`: `subset(pf, ...)`,
  `pf[, cols]` and `pf[cols]` are refused. Also add the case where the
  guard's condition is absent: `subset()` of a `route = "sample"` table
  resolves to brms's defaults.
- Correct the record's sentence on where the mark survives.
- File the two coerced-table gaps, or close them the same way.

### 2. MINOR: `?frmtmb-marginaleffects` and NEWS omit that the sandwich spellings are refused under a residual correlation term

On `y ~ x + ar(time = t, gr = h, cov = TRUE)`, `vcov = "HC0"`,
`"HC1"`, `"stata"` and `~ h` are all refused
(`dev/review-rel077-b-run/x3.R`, `x3.txt`). The refusal is
`vcov_cluster()`'s: "does not support the residual correlation term
... Use frm_bootstrap()".

The refusal is correct, and `vcov = TRUE` equals `frm_linpred()`'s
standard errors there. But the help page and the NEWS bullet list only
crossed random effects and the leverage, time-order and
degrees-of-freedom strings as reasons for a refusal.

`~ h` clusters on the series itself, where the scores do factor by
group. So that refusal is wider than it needs to be. That is a parity
gap to file, not a defect.

Required fix: one sentence in the help topic and in the NEWS bullet,
and a backlog line for `~ <ar group>`.

### 3. MINOR: `c(set_prior(...), default_prior(...))` is refused as "a plain data frame"

The argument is a `default_prior()` table, not a plain data frame, so
the message is wrong. 0.76.0 accepted the call
(`dev/review-rel077-b-run/r1c.R`: `r1c-rellib-r14.txt` "OK",
`r1c-rellib-r15.txt` the refusal). brms's `c()` of a `brmsprior` and a
prior table combines them.

`default_prior() + set_prior()` fails in R's `Ops` dispatch
("Incompatible methods") on both builds. That is pre-existing.

Required fix: take the table in `c()`, with its route carried through
`combined_prior_route()`, or refuse it with a message that names a
`default_prior()` table. Add a NEWS line if it stays refused.

### 4. MINOR: the commit script's dry run writes the git index, in the lanes and in main

Measured on a scratch repository (`git init`, commit one file, `touch`
it):
- `git add -A -n` left `.git/index` unchanged.
- `git status --porcelain` rewrote it (the stat refresh git does when
  it can take the lock).
- `GIT_OPTIONAL_LOCKS=0 git status --porcelain` did not rewrite it.

`dev/rel077-commit.sh` runs `git status --porcelain` in each lane tree,
and `git -C <main> status --porcelain` in the main checkout, before
its `--dry-run` branch. So the dry run, and the record's "makes no git
write", is not strictly read-only. It refreshes the stat data of the
index of each tree. No content changes.

Because of this, I did not run the dry run. I reproduced its counts
read-only instead (finding 9).

Required fix: `export GIT_OPTIONAL_LOCKS=0` at the top of the script
(the real run's `git add` and `commit` are unaffected), and correct the
record's wording.
