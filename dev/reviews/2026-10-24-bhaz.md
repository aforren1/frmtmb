## Findings

### 1. major: partial argument names fit a different basis from brms, silently

`cox_bhaz_option()` matches the call with `match.call(sig, call)`, and
R partially matches the names. brms does not partially match the same
names, because `bhaz_basis_matrix()` and `resp_bhaz()` fill
`Boundary.knots` and `intercept` by exact name before splines2 sees
the call. `dev/review-bhaz-partial.R` (`partial.txt`), seed 11, n =
200:

| spelling | brms 2.23.0 | frmtmb lane | max abs dZbhaz |
|---|---|---|---|
| `bhaz(int = FALSE)`, `bhaz(inter = FALSE)` | intercept TRUE (ignored) | intercept FALSE | 5.17 |
| `bhaz(Boundary = c(0, 30))`, `bhaz(Bound = c(0, 30))` | boundary 0, 8.929 (ignored) | boundary 0, 30 | 0.457 |
| `bhaz(kn = c(0.5, 1.1))`, `bhaz(deg = 2)` | knots, degree taken | taken | 8.9e-16, 1.8e-15 |
| `bhaz(d = 6)` | df 6 | refused: "argument 1 matches multiple formal arguments" | |

The first two rows fit a different model from the same brms formula,
with no message. That is the one outcome that is worse than a refusal.
The lane refuses `bhaz(foo = 1)` because brms drops it silently. The
partial names are the same kind of input, and here frmtmb guesses
instead.

Fix: before `match.call()`, refuse any argument name that is not one
of `gr, df, degree, intercept, knots, Boundary.knots` exactly, and name
the full argument ("bhaz(int =) is not an argument; write intercept
="). Add the four spellings above to `test-cox-bhaz.R`. A refusal of
`kn`, `deg` and `d`, which brms takes, is acceptable; a silently
different model is not.

### 2. minor: the refusals of models brms fits, judged one by one

The rule is to match brms unless brms is clearly wrong. My evidence
for each refusal:

- **Boundary knots inside the data: brms is clearly wrong. Keep the
  refusal.** `dev/review-bhaz-bnd.R` (`bnd.txt`) uses the lane's probe
  data. With `Boundary.knots = c(0.5, 10)`, 62 rows lie below the
  lower knot and 1 above. With equal simplex weights, brms's
  cumulative baseline hazard reaches -1.082, so S(t) > 1. With `c(0.01,
  14.71)`, 1 row lies outside, and the same cumulative hazard is
  -0.0053. With the upper knot alone inside the data (`c(0, 12)`), 1
  row has a negative M-spline entry, so some simplexes give a
  negative hazard. frmtmb's own basis is zero outside the knots, so
  the alternative to the refusal is log(0) for an event, not brms's
  fit.
  The NEWS sentence and the comment in `bhaz_spec()` overstate the
  case: "63 of 200 rows of brms's `Zbhaz` had a negative entry, which
  is a negative baseline hazard". No row is negative for EVERY simplex
  (0 of 63, `bnd.txt`). The negative cumulative hazard is the
  stronger fact. Fix: say "the cumulative baseline hazard is negative
  below the lower knot (-1.08 at equal weights), and the hazard can be
  negative", and do the same in the `bhaz_spec()` comment.
- **`df` with `knots` that disagree: brms silently drops what the user
  wrote. The refusal is defensible.** brms fits the knots model
  correctly, but it ignores an explicit `df`. This is a documented
  deviation, and NEWS and `?cox` record it. Keep it.
- **Unknown arguments: defensible, with one false refusal.**
  `periodic`, `derivs` and `integral` reach splines2 in brms and change
  the basis (`bhaz(periodic = TRUE)` moves the knots; `brms.txt`), so
  frmtmb cannot fit them, and refusal is right. `foo = 1` and
  `Knots =` are typos that brms drops silently, so refusal is
  defensible. `bhaz(warn.outside = FALSE)` is a splines2 argument that
  changes nothing, and brms takes it. frmtmb refuses it
  (`partial.txt`). Fix (nit): accept `warn.outside` and ignore it.
- **Fractional `df`: fine.** `cox(df = 4.5)` was already refused at
  0.74.0 by `sv_check_count()`, and brms's truncation to 4 is not what
  the user wrote.
- **`bhaz(6)`: the refusal is right, and its message is not.** brms
  reads `6` as `gr` and fits ONE group named "6" with df 5 (Kbhaz 5,
  ngrbhaz 1). That is almost surely not what the user meant. frmtmb
  says "gives each level of 6 a baseline hazard of its own ... or add
  6 to the formula" (`compose.txt`). Fix (nit): when `gr` is a
  constant, say that the first argument of `bhaz()` is `gr` and
  suggest `bhaz(df = 6)`.

### 3. minor: the help example of `option =` cannot work as written

`?frmtmb_register_aterm` gives `bw(5)`, which sets `family$width` and
returns the family. A third party who copies it fails twice
(`dev/review-bhaz-toy.R`, `toy.txt`):

1. On `gaussian()` it is refused ("Addition term `bw()` is not
   supported for family 'gaussian'"), because every built-in family
   declares `accepts_aterms`.
2. Assigning a slot changes nothing that the likelihood reads. The
   lpdf closure does not see `family$width`.

When I wrote the toy from the prose of the help page instead, it
worked. A family that lists `sdk` in `accepts_aterms` and an option
that REBUILDS the family gave logLik -211.15526367 against an
independent -211.15526367. The option ran once per `frm()`, once per
`update()` and once per `get_prior()`, and 0 times for
`frm_linpred(newdata =)`. A deliberately non-idempotent option
(`sd * value`) gave sd 2 after the fit, after `update(. ~ . +
I(x^2))` and after `update(newdata =)`. So the help is right that
`update()` parses from the family as written. Fix: replace the
example with one that rebuilds a family which declares the term, and
say in one sentence that the returned family must be rebuilt, because
closures do not read new slots.

### 5. minor: `cox(df = 3) + bhaz(intercept = FALSE)` is refused, though the merged basis is valid

The BREAKING change (`cox(df = 3)` stops when `cox()` runs) is right
for `cox()` alone, because the check needs no data. Note that
`bhaz(df = 3, intercept = FALSE)` works and equals `cox(df = 3,
intercept = FALSE)`. But `cox()` now stops before `bhaz()` can supply
`intercept = FALSE` or `degree = 2`. The result is "cox(): df must be
at least degree + 1 (4)" (`compose.txt`), although df 3 with no
intercept is a valid basis. Only frmtmb can write this combination,
because brms has no `cox(df =)`. Fix: either defer the check until
the options are applied (for example, check in `cox_build()` only
when no `bhaz()` will follow, and again after the merge), or say in
`?cox` that `bhaz()` cannot repair `cox()`'s own `df`. I accept either.

## Outside this lane

brms 2.23.0's Stan code for an interval-censored `cox()`
(`dev/review-bhaz-icens.R`) evaluates `cox_log_lcdf(rcens[n] | ...,
cbhaz[n])` with `cbhaz` at `Y`, not at `rcens`. So the interval term
is `log(0)`, and brms cannot fit interval-censored Cox models. frmtmb
evaluates its own basis at the bound. File this as a brms difference
where brms is wrong. It is not a defect of this lane.
