## 1. HIGH, FIXED: a link object was taken on trust

`robust_link()` was

```r
robust_link <- function(link, dpar) {
  if (is.list(link)) return(link)
  get_link(link, dpar = dpar)
}
```

Any list bypassed `get_link()`. `robust_logit()` then finds no
`logit_eta` on it, returns `NULL`, and the accessor falls back to the
plain arithmetic. Measured on the delivered build, at
`list(zi = plogis(40), .eta_zi = 40)`:

| `link` argument | `dpar_log1m()` |
| --- | --- |
| `"logit"` | -40 |
| `get_link("logit")` | -40 |
| `stats::make.link("logit")` | **-Inf** |
| `list(name = "logit")` | **-Inf** |

`stats::make.link("logit")` is the most likely object a family author
outside frmtmb reaches for, and it spells the derivative `mu.eta` where
this package's contract spells it `mu_eta`. Core's own resolver already
refuses it:

```
get_link(stats::make.link("logit"), dpar = "zi")
# Error: The custom link of dpar 'zi' has no `mu_eta`. ...
```

So the new public accessor was LESS strict than the private resolver it
wraps, and the consequence was silence in exactly the regime the whole
topic exists for.

**Fixed** in `R/families.R`: `robust_link()` now routes every link
through `get_link()`. The obvious objection is cost, and the objection
does not survive measurement. `get_link()` on a list costs 26 us, and
the R-level density runs ONCE per fit, not once per iteration:
counted through real `frm()` fits, the lpdf runs in R **once**.
`cross_wishart()` on 30 units: 1 call for a fixed-effect fit, 1 for a
fit with `coh ~ 1 + (1 | id)`. A custom binomial family on 600 rows
and 30 groups: 1 for `y ~ x`, 1 for `y ~ x + (1 | g)` through the
Laplace approximation, then 0 for `fitted()`, `residuals()`,
`logLik()` and `predict()`, and 1 for `summary()` where the report is
taped again. The validation is therefore paid once per tape build.

Tests added in `tests/testthat/test-dpar-eta-api.R`
("a link object is held to the same contract as a link name"). Against
the pre-fix build they fail on BEHAVIOR:

```
Expected `frmtmb::dpar_log1m(d40, "zi",
  stats::make.link("logit"))` to throw a error.
Expected `frmtmb::dpar_complement(d40, "zi",
  list(name = "logit"))` to throw a error.
```


| --- | --- |

## 5. MEDIUM, NOT FIXED: the published timing is the wrong quantity

The lane's decision to export four rather than three rests on a
measurement of R-level lpdf call time, and that number is now printed in
`?"frmtmb-robust-dpars"`, in `NEWS.md`, and in the coupling's Rd:

> the pair costs a second `RTMB::logspace_add()` over the whole
> response, which measured 1.9 ms against 1.2 ms per call at 1000 rows

The R-level density call happens once per fit (finding 1). What repeats
is the tape sweep. Measured here, interleaved in one process, 5 blocks,
medians:

Full `cross_wishart()` density at n = 1000, R-level call:

| build | blocks (us/call) | median |
| --- | --- | --- |
| base `a2deb65` arithmetic | 704 744 802 774 1648 | 774 |
| pair accessor | 1330 1172 1270 1976 2906 | 1330 |
| one-sided (shipped) | 732 756 702 1812 754 | 754 |

Same density, taped, us per GRADIENT SWEEP, 5 blocks of 2000:

| build | blocks | median |
| --- | --- | --- |
| base | 310 325 410 320 350 | 325 |
| pair | 445 460 480 460 460 | 460 |
| one-sided | 340 415 330 320 340 | 340 |

The accessor alone at n = 1000, 5 blocks of 3000 sweeps: one-sided
median 240 us, pair median 413 us, ratio 1.72.

So the lane's CONCLUSION is right and is better supported than its own
evidence: the pair costs 1.35 to 1.72 times the one-sided per gradient
sweep, and the gap is outside the run-to-run spread (the pair's minimum
block, 445 us, is above the maximum block of both other builds). Four
exports, not three, is justified. What should change is the number in
the public documentation, which currently describes a cost paid once per
fit as though it were paid per iteration.

I did NOT edit that text: replacing a published measurement is the
lane's to re-run, and the sentence is not wrong, only mis-framed.

Two sub-questions answered while measuring this:

* **Is `dpar_log1m()` redundant with `dpar_log_complement()`?** No. R's
  `list()` forces both arguments: a counter placed in both components
  fires twice, so laziness cannot skip the unused half. Neither does the
  tape: RTMB exposes no `simplify`/`optimize` method on a `Tape` object
  (the object's environment holds only `Dim, eval, evalAD, mod, output,
  Pattern`), and the measured sweep cost above is the dead
  `logspace_add` being replayed.
* **Does the name path really cost 0.8 us?** `get_link("logit")` is
  0.600 us/call over 50000 replicates, twice. The end-to-end
  name-versus-object difference in `dpar_log_complement()` came out
  +1.0 us at n = 1 and +6.0 us at n = 500, against an accessor cost of
  41 and 419 us. The lane reported the difference as negative; it is
  positive and small. Same conclusion. Note that after fix 1 the object
  path is no longer free: it costs the same 26 us validation, paid once
  per fit.

## 7. MEDIUM, NOT FIXED: `dpar_` now names two different things

The lane's vocabulary claim checks out against NAMESPACE (133 exports):

* `frmtmb_*` is constructors and registries: `frmtmb_family`,
  `frmtmb_structure`, `frmtmb_control`, `frmtmb_ad_overload`,
  `frmtmb_register_aterm`, `frmtmb_register_compat`,
  `frmtmb_register_frame_check`.
* `frm_*` is verbs on a fit: `frm_allfit`, `frm_bootstrap`,
  `frm_compat`, `frm_joint_cov`, `frm_lp_basis`, and eight more.
* Unprefixed noun phrases opening with the object read is the extension
  vocabulary: `dpar_linpred`, `frame_block_of`, `fit_extras`,
  `response_mean`, `eval_dpars`, `single_response`.

The four new names fit that pattern. The cost is that `dpar_` now spans
two unrelated call shapes:

```r
dpar_linpred(frame, params, resp, dpar)   # post-fit, extension API
dpar_log(dpars, dpar, link)               # inside a density, while taping
```

Different first argument, different lifecycle phase, different reference
topic. `dpar_linpred()` is NOT the natural home for the new four: it
takes a frame and a parameter list and returns the fixed-effect part of
a linear predictor at the estimates, which is a different quantity
computed at a different time. But a reader who learns one `dpar_`
convention will guess the other wrong. Worth one sentence of
cross-reference in each topic, which the new topic half has already
(`@seealso [frmtmb-extension-api] for the accessors a family uses AFTER
a fit`) and `frmtmb-extension-api` does not.

## 9. LOW: the Sterbenz claim, stated precisely and checked

The hypothesis the lane leans on, stated: for floating-point `x` and
`y` with `y/2 <= x <= 2y`, `x - y` is exactly representable and the
subtraction is exact. With `x = 1` that is `p` in `[0.5, 2]`;
restricted to `(0, 1)`, `1 - p` is exact for `p` in `[0.5, 1)`.

Checked over 940 points (logarithmic toward both ends plus 200 uniform),
442 of them with `p >= 0.5`:

* round trip `1 - (1 - p) == p` exact at **442 of 442**, zero
  counterexamples;
* `log(1 - p)` and `log1p(-p)` **bitwise identical at all 442**;
* below 0.5, the round trip is exact at only 101 of 498.

The two spellings differ at **397 of 940** points. The lane says every
differing point has `p < 0.1`; on my grid the largest is exactly
`p = 0.1`, so the claim holds as `p <= 0.1`. Largest relative difference
**1**, at `p = 1e-18`, where `log(1 - p)` returns exactly 0 for a value
of -1e-18. Against a series reference over `p` from 1e-18 to 1e-6,
`log1p(-p)` has relative error 0 to 2.1e-16 and `log(1 - p)` has up to
1. `log1p` is never worse and is the right choice.

## 19. Suspicions chased and disproved

* **"The `log(1 - p)` to `log1p(-p)` change moves a shipped family's
  density silently."** It is reachable on the tape: `identity` carries
  neither `logit_eta` nor `log_eta` and is in the allowed link set for
  `zi`, `hu` and `quantile`, so the fallback branch is differentiated
  there. Measured on `zero_inflated_poisson(link_zi = "identity")`,
  summed log density over `y = c(0,0,1,3,7)` at zi in
  {1e-18, 1e-12, 1e-8, 0.01}: **bit-identical** between the base and the
  lane build at all four. The gate term's improvement is below the last
  bit of the total. No NEWS bullet is owed for it.
* **"`get_link(name, dpar =)` restricts the link set per dpar, so an
  accessor called with a dpar core does not know, such as `coh`, will
  refuse."** It does not. `dpar` only decorates the error message when a
  list is passed; the per-dpar restriction lives in `dpar_link()`, which
  the accessors never call. `dpar_log1m(d, "coh", "logit")` works, which
  is what the coupling package needs.
* **"The tape optimizer removes the pair's unused half, so the fourth
  export is unnecessary."** It does not. RTMB exposes no simplify or
  optimize method on a `Tape`, and the measured gradient sweep at
  n = 1000 is 413 us for the pair against 240 us for the one-sided.
* **"A wrong-but-known link name is caught."** It is not, and cannot be:
  `dpar_log1m(d, "zi", "probit")` on a logit-scale predictor returns
  -3.78 where the truth is -2.13, in silence. That is inherent to
  passing the link as an argument and is documented ("That dpar's OWN
  link"). Not a finding, recorded so the next reader does not chase it.

### Does `bcm_contaminant()` need its own NEWS bullet?

`link_phi = "logit"` the density is bit-identical (15 of 15 etas, max
