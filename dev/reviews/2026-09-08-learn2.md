## Verdict at first review: PUNCH

The mathematics is right and the measurement is honest. Two mechanical
defects block the merge, and both are in the same place: the new
`rlddm()` family's dependency on `frmtmb.eam`. The first makes the
family unusable on a user's own data, and every test and example in the
package masks it. Neither is deep; both are a few lines.

The factorization work, which was the item most likely to be silently
wrong, verifies exactly. See "The ruling on `loglik_row`" below.

## Findings, ranked

### 1. HIGH. `rlddm()` fails from a clean session: `dec()` is never registered

`library(frmtmb.learn)` does not load the `frmtmb.eam` namespace, so
`frmtmb.eam`'s `.onLoad` never runs, so the `dec()` addition term
`rlddm()` requires is not in the registry when `frm()` parses the
formula. A user who loads the package and fits their own data gets:

    Addition term `dec()` is not supported (supported: weights(),
    trials(), cens(), trunc(), se(), vint(), vreal(), mi(), reward(),
    payoff(), stage2()). ...

`extensions/frmtmb.learn/NAMESPACE` carries `importFrom(frmtmb, ...)`
and `importFrom(stats, setNames)` and nothing from `frmtmb.eam`. A
package listed only in DESCRIPTION `Imports:` is required to be present
at install time; it is not loaded at package load time. `rlddm.R` reaches
the density through `frmtmb.eam::wiener_lpdf()`, and `::` loads the
namespace when it is *called*, which is long after the frame is built.

The false premise is written down at
`extensions/frmtmb.learn/R/zzz.R:61-62`:

> This package Imports frmtmb.eam, so the term is always already
> registered by the time this call runs; expects = tolerates that.

It is not already registered. `expects = "dec()"` correctly stops
`.onLoad` from failing, which is why nothing complains at load.

**Why no test caught it, and the pattern to recognize next time.** THE
MASK IS A NAMESPACE LOAD HAPPENING AS A SIDE EFFECT OF SOMETHING ELSE.
Every route in this package that fits an `rlddm()` model calls
`frm_task_simulate()` first. That reaches `frmtmb.eam::ddm_simulate()`,
and evaluating `::` LOADS the `frmtmb.eam` namespace, which runs its
`.onLoad`, which registers `dec()`. The registration is nobody's
intention; it is a by-product of having drawn some data a moment
earlier. Every later fit in the same session then works, so the suite
and the examples all pass.

It is true of `?rlddm`'s example (`R/rlddm.R`, `@examples`), of
`test-factorization.R`'s rlddm block, and of all four new `rlddm` blocks
in `test-families.R`. The one thing no test does is the one thing a real
user does: fit data they already have, without simulating any.

The general shape, worth carrying to the next package that reaches
across an extension boundary: **if package A's behavior depends on
package B's `.onLoad` registering something, and A only ever touches B
through `::` inside a function, then any test that happens to call that
function first will hide the fact that A never loads B.** A test whose
setup uses the same package it is testing against cannot detect a
missing load. The check is a session that does the minimum: attach, fit,
nothing else.

Reproduction (`scratchpad/rvl3-dec.R`), against the correct
`frmtmb.eam` 0.4.1 in the private library:

    eam namespace loaded after library(frmtmb.learn)? FALSE
    registered aterms: payoff reward stage2
    A. clean session, user's own data: FAILS

    B. now load the eam namespace, as any frmtmb.eam:: call would
    registered aterms: dec payoff reward stage2
    B. same fit: works

Fix: `@importFrom frmtmb.eam wiener_lpdf` on `rlddm()` (or an explicit
`requireNamespace("frmtmb.eam")` in `.onLoad`), then re-roxygenise. Add
a test that fits `rlddm()` on a data frame built without
`frm_task_simulate()`, in its own file so no earlier block in the same
file has loaded the namespace for it.

### 3. MEDIUM. The package doc denies a capability the lane actually delivered

`extensions/frmtmb.learn/R/frmtmb.learn-package.R:115` (rendered at
`man/frmtmb.learn-package.Rd:132`):

> The same slots do NOT deliver `loo()` or `waic()`: those refuse for
> every frmtmb fit ... That refusal is core-wide and unrelated.

That is true of a `frmtmb_fit` and false of the route the core's own
`?loo` page sends users to. `frmtmb.sample/R/loo.R:74-85` admits any
structure that declares `loglik` together with either factorization
slot, and `loo.R:157` picks `loglik_group %||% loglik_row`. So the
lane's change flips `loo()` from refused to admitted.

Reproduction (`scratchpad/rvl3-loo.R`), `frmtmb.sample` installed
unmodified from the worktree:

    === WITH the new slots (this lane) ===
    draws_loglik_factors: ADMITTED (no refusal)
    pointwise columns = 6   rows in data = 180   subjects = 6
    attr unit = one subject's trial sequence
    sum = -82.4852596519   logLik = -82.4852596519

    === WITHOUT them (what main does today) ===
    draws_loglik_factors: REFUSED: loo() needs a likelihood that factors
    into one term per observation, and the response 'choice' does not:
    its smallest independent unit is one subject's trial sequence ...

The behavior is correct and is the honest one: a column is a subject,
not a trial, and the matrix carries `attr(x, "unit")` so `loo()` and
`psis()` name the unit at use time. The documentation is what is wrong.
It should say that with `frmtmb.sample` a `loo()` column is one
subject's whole trial sequence, which is also the answer to "what does
`loo()` on this mean", and it should not tell a reader the slots deliver
nothing.

### 4. MEDIUM. The row-scaling argument for rlddm's identity residual is not supported by its own table

`dev/learn2-findings.md` argues the 3.176e-09 residual is a per-row
implementation difference rather than accumulated rounding because "the
residual GROWS with the row count while the per-row figure stays flat".
Its own table says otherwise:

| rows | difference | per row |
|---|---|---|
| 120 | 1.188e-09 | 9.90e-12 |
| 240 | 2.500e-10 | 1.04e-12 |
| 720 | 3.176e-09 | 4.41e-12 |
| 1440 | 5.837e-09 | 4.05e-12 |

240 rows has a residual five times *smaller* than 120 rows, so the
residual does not grow with the row count, and the per-row column spans
a factor of 9.5, so it is not flat. Four points of a signed difference
between two totals cannot separate a per-row bias from cancellation.

**The conclusion is right and there is a much better argument for it,
which the lane already half has.** I measured `frmtmb.eam`'s density
against RWiener directly over 4000 rows spanning dt in (0.05, 3), drift
in (-4, 4), boundary in (0.6, 2.5) and bias in (0.2, 0.8)
(`scratchpad/rvl3-dens.R`):

    eam vs RWiener, per-row |difference| in the LOG density:
      median 5.55e-17   mean 3.86e-16   max 1.78e-14
      quantiles .9/.99/1: 8.88e-16  3.55e-15  1.78e-14

eam's density is accurate to about 1e-15 per row against a third
implementation. A per-row difference of 4e-12 against Stan therefore
sits on **Stan's** side of the comparison, not on a symmetric "the two
series agree to eleven significant figures". That is a stronger claim
than the one made and it is one measurement away. Replace the scaling
table with this.

## The ruling on `loglik_row`: honestly declared

Yes. Verified rather than accepted, and it holds at a level the lane did
not claim.

**On the tape, five families.** `scratchpad/rvl3-fact.R` builds one
`RTMB::MakeTape()` per family returning
`c(loglik, sum(loglik_row), sum(loglik_group))` as a function of a
perturbation of every distributional parameter plus a per-subject
offset, then compares values and Jacobians at four parameter vectors
(the estimates and three random draws). For `bandit2arm_delta`,
`prl_fictitious`, `bandit4arm2_kalman_filter`, `igt_orl` and `ts_par7`:

* values agree to 3.4e-13 or better at every point,
* **Jacobians agree to exactly 0** at every point, in all 20 comparisons,
* the gradient itself is non-trivial (0.46 to 3.0), so the check is not
  vacuous.

Exact gradient equality is what "one recursion, three slots" is supposed
to mean, and it is what the tape shows.

**Alignment, which sum-to-total cannot check.** `scratchpad/rvl3-fact2.R`
adds the two cases the lane's `test-factorization.R` does not cover.

* *Padding.* Unequal trial counts (11, 20, 24, 20, 18, 30), so the block
  really is padded. Every row equals an independent longhand delta-rule
  reference written subject by subject, to 4.4e-16, and no row is left
  at exactly zero. This is the case `ln_loglik_row()`'s `keep` mask
  exists for, and the lane's own tests all use equal trial counts.
* *Permuted layout.* `levels(id)` reversed to 6,5,4,3,2,1 and the rows
  shuffled so the data order is 2,6,4,1,4,5,3,6. Rows still match the
  longhand reference to 8.9e-16, and `loglik_group` follows
  `levels(group)` rather than order of appearance: the two orderings
  differ by 12.8 log units here, so the test is not vacuous.
* *Stacking on a padded block.* `nrep = 3` gives `rep(row, 3)` and
  `rep(grp, 3)` exactly, at length `n * nrep`.

**End to end through the correction.** `scratchpad/rvl3-impperm.R` fits
with `importance = 24` on the natural and the reversed-level layouts.
Both complete, which means core's `imp_verify()` per-group check passed
on the permuted one, and the two log-likelihoods agree to ten digits
(-166.9791473).

**Is a row's value the conditional contribution, and does `loo()` mean
what a user assumes?** It is the conditional contribution, given that
subject's own earlier trials, and that is exactly what the core contract
asks for (`R/structure.R:132`: "the conditional log-density of that row
given whatever the family's factorization conditions on"). The family
keeps `unit = "one subject's trial sequence"` separate and says why,
both in `R/family.R` and in `NEWS.md`. `frmtmb.sample` then picks the
*coarsest* slot, so a `loo()` column is a subject, not a trial, and
leaving one out drops the whole sequence. That is the honest answer, and
core anticipated this family by name in `loo.R`'s own comment. The one
gap is documentation, finding 3: the package tells the reader `loo()`
still refuses, so a reader is never told what a column is.

## The `frmtmb.eam` export

Sound. `wiener_lpdf()` is a sensible public surface: one function, the
density and nothing else, with the truncations, the blend, the
variability integrals and the CDF explicitly kept private and the reason
written at the top of `R/extension-api.R`. It is fully documented
(parameters, tape safety, what a non-positive decision time gives,
Navarro and Fuss reference, two runnable examples) and it validates the
one argument that is data rather than a parameter.

`frmtmb.learn` reaches it through `::` and there is **no `:::` anywhere**
in `extensions/frmtmb.learn/R/` (`grep -rn ":::"` returns nothing).

`tests/testthat/test-extension-api.R` checks it five ways: against
`wiener()`'s own `lpdf` through the family, against the closed-form exit
probability by quadrature, against RWiener on both boundaries, against a
finite difference through an RTMB tape jacobian, and the two guards. For
a seam another package depends on, that is the right amount.

## The simulator defect

Reproduced, and the fix is right.

An RWiener-free library was built as junctions to the user library minus
`RWiener` (374 entries), which is the faithful "user without RWiener"
case rather than a simulation of it.

* The **fallback really does error**, verbatim
  (`scratchpad/rvl3-sim2.R`). At drift 2.7, boundary 1.6, 300 rows:

      wiener: the fallback simulator could not produce a draw at the
      requested boundary for 2 of 300 rows in 50 passes. Install
      RWiener for exact conditional draws.

  Drift 1.5 and drift 4.0 both draw fine, which sharpens the lane's
  diagnosis: the failure needs a boundary favored strongly enough that
  rejection cannot reach the other one, but not so strongly that the
  other one is never requested.
* The **refusal fires first and is useful** (`scratchpad/rvl3-sim.R`).
  `frm_task_simulate()` on `rlddm()` stops with a message that names the
  package, says what it is needed for, and says fitting does not need it.
  `R/task.R:241-249`.
* The **flaky test was flaky, not load-bearing.** The old assertion
  compared a pooled choice share at two drift scalings, and the lane's
  own table shows the pooled statistic ranges 0.020 to 0.313 at drift 3
  and 0.027 to 0.340 at drift 12, so it never separated the conditions.
  The replacement in `test-families.R` asserts two anchored thresholds on
  a per-subject statistic (below 0.15 at drift 0, above 0.25 at drift
  12) with measured margins on both sides. That is a stronger test, not
  a weaker one, and it still asserts the load-bearing claim that the
  value store reaches the drift rate.
