## 1. The breaking change refuses a model 0.54.0 fitted CORRECTLY

**Severity: MEDIUM (a decision to ratify, not a defect).** No change
made.

The lane's own report frames this as a trade. It is worth stating in
the sharpest form, because the project's standing rule is that "a check
that fires on a correct model is worse than no check", and this check
does fire on one.

The family: `skew_se`, dpars `c("mu", "alpha")`, `accepts_aterms`
including `"se"`, whose density reads BOTH `aterms[["se"]]` (as the
scale) and `alpha` (as the skew). No `se_dpar` declaration, because in
0.54.0 there was none to write. 400 rows, `alpha` drawn at 3.

| model | MAIN (0.54.0) | LANE |
| --- | --- | --- |
| `bf(y \| se(sev) ~ x)` | refused | refused |
| `bf(y \| se(sev) ~ x, alpha ~ 1)` | **fits** | **refused** |

The MAIN fit is not a broken fit. Measured: logLik -285.4588975,
`alpha` 2.955556 with a standard error of 0.351892, every standard
error finite. It is the same model the LANE reaches by declaring
`se_dpar = NA`, to the digit. So an out-of-tree family author who wrote
a formula for their shape parameter, which is the natural spelling,
had a working model in 0.54.0 and gets a refusal in 0.55.

Against that, the same spelling on a family whose extra dpar is a
second SCALE fitted at logLik -62.49777177 with `NaN NaN NaN` for the
standard errors, and the core cannot see which of the two it has. The
argument for keeping the error rather than downgrading to a warning:

* A warning leaves the NaN case fitted-and-wrong, which is the exact
  failure mode 0.54.0's `se()` allow-list exists to close. The
  refusal's authority comes from the same premise as that allow-list:
  "did not say" cannot mean yes.
* 0.54.0's behavior was internally inconsistent, not conservative. The
  bare case was refused and the formula case fitted, for the same
  family. Whatever the default should be, it should be one default.
* The cost is one argument, and the refusal names it in both spellings
  (`se_dpar = "alpha"` and `se_dpar = NA`).
* The blast radius is zero shipped families. Verified independently
  across all SEVEN extensions, not the five the lane checked:
  `frmtmb.coupling`, `frmtmb.eam`, `frmtmb.latent`, `frmtmb.learn`,
  `frmtmb.ode`, `frmtmb.sample`, `frmtmb.spline`. No family in any of
  them lists `"se"` in `accepts_aterms` or `required_aterms`. The only
  `se()` addition term anywhere in the extensions is an
  `expect_error()` at `extensions/frmtmb.latent/tests/testthat/`
  `test-hmm.R:609`, which asserts a refusal and still gets one.

**Recommendation: keep the error.** But the NEWS entry should not read
as if only the broken case changes; it currently names the built-in
gaussian and the second-scale family and says "the refusal names the
one-argument fix", without saying that a CORRECT model is among the
casualties. That sentence is worth one more clause before release.

> alongside the known standard error. Four ways out: ...

Every substring the lane's tests and the pre-existing tests match on is

`se_dpar = "alpha"`, `se_dpar = NA`, ``name the scale `sigma` ``,

## 3. "A call that is refused does not spend the notice" is false

**Severity: LOW. Prose FIXED** in `NEWS.md` and `R/frame.R`; behavior
left alone.

The notice sits after every CENSORING guard, which is what the code
comment claims and what the lane's test pins. The NEWS entry
generalized that to "A call that is refused does not spend it", which
is not true. Two counterexamples, one fresh R process each, using the
same 150 poisson draws right censored at 6:

| call | notices | outcome |
| --- | --- | --- |
| half-integer interval bound | 0 | refused by a censoring guard |
| then a good fit | 1 | notice arrives |
| `y \| cens(cc) + se(s) ~ 1`, poisson | **1** | refused by the `se()` guard, 15 lines LATER in the same frame loop |
| then a good fit | 0 | notice already spent |
| `prior(normal(0,1), class = "nonesuch")` | **1** | refused after frame assembly entirely |
| then a good fit | 0 | notice already spent |

The behavior is acceptable: the notice belongs to frame assembly, and
frame assembly is where the convention is applied. Closing it fully
would mean deferring the notice past the optimizer, which is worse. So
only the claim moved. NEWS now says a call a censoring guard refuses
does not spend it, and a call refused later does; the code comment says
the same and names the two measured routes.

## 5. `tests/testthat/setup.R`: what the suite-wide silencer costs

**Severity: MEDIUM, no change recommended.** The measurement is the
point of this finding.

The task named this the highest-risk change in the lane. I removed
`setup.R` from a scratch copy of `tests/testthat` and reran, one file
per R process against the LANE library, every core test file that
writes `cens(`: 23 files.

**Result: 23 files, 2148 passing assertions, 0 failures, 0 errors, and
exactly ONE file fires the notice** (`test-bcm-data-analysis.R`, which
right-censors a count in a case study). That file still passes.

So, concretely:

* No assertion anywhere in the suite currently depends on the
  silencer. It is insurance against order dependence, not a patch over
  a present breakage. That is a reasonable thing to buy, and it is the
  standard testthat idiom.
* It masks exactly one firing today, and that firing is correct
  behavior.
* **Does any test still prove the notice FIRES?** Yes. Two tests in
  `test-cens-trunc.R` re-arm the option, clear the state environment
  and assert the notice arrives (right censoring, interval censoring).
  A third asserts it does NOT arrive for left censoring, a continuous
  response, or truncation alone, and then that it is still unspent. So
  both directions are pinned for the cases that matter.
* **Does the silencer leak?** No. `options()` is process-local;
  `R CMD check` runs the suite in one process and that is the process
  the file is meant to configure. Examples and vignettes run in their
  own processes and do NOT get it, so a notice there would be visible:
  measured, `frmtmb-Ex.Rout` from the lane's own check contains zero
  notice emissions, and no built vignette contains the notice text.
  Extensions run their own suites in their own processes, and none of
  them can fire the notice at all: of the ten extension test files
  that write `cens(`, every one censors a CONTINUOUS response
  (survival times, reaction times, gaussian) or asserts a refusal.
* **Would a notice fired at the wrong time now be invisible to CI?**
  For any case other than the three negative assertions above, yes.
  That is the residual risk and it is inherent to a once-per-session
  notice: a per-file assertion cannot exist for a thing that fires
  once per process. The mitigation the lane chose, three explicit
  negative assertions on the cases that actually differ, is the right
  one. Recorded so the next person who adds a notice adds a negative
  assertion with it.

## 6. The guard reads `default_forms` but not `fixed_dpars`

**Severity: MEDIUM. Pre-existing on both builds; NOT fixed.**

`parse_one_response()` merges two family-supplied defaults after the
`se()` guard runs: `default_forms` (a formula, `R/parse.R:1681`) and
`fixed_dpars` (a CONSTANT, `R/parse.R:1696`). The lane went to the
trouble of reading `default_forms` at guard time, correctly, because a
default formula still estimates. It did not do the symmetric thing for
`fixed_dpars`, so a family that pins its own scale at a constant, which
is precisely the escape the refusal message recommends, is still
refused.

Measured, on the family with dpars `c("mu", "tau")` declaring `se()`:

| family | LANE | MAIN |
| --- | --- | --- |
| `fixed_dpars = list(tau = 1)`, no `se_dpar` | refused | refused |
| user writes `bf(y \| se(sev) ~ x, tau = 1)` | fits, -62.4977718 | fits |

The two rows are the same model. The first is refused because
`names(pfix)` at guard time does not yet contain the family's own
fixed dpar. This is not a lane regression, and no shipped family is
affected (`fixed_dpars` is used by `whittle(tapers =)`, which does not
declare `se()`), but it is an inconsistency the lane's own rewrite
introduced the asymmetry of. The fix is one expression, used in both
places the guard currently reads `names(pfix)`:

```r
pinned <- c(names(pfix),
            intersect(names(fam[["fixed_dpars"]] %||% list()),
                      fam[["dpars"]]))
```

Left for the lane rather than applied here, because it changes a
refusal and therefore needs its own test, which is more than a
reviewer's small-and-clearly-right budget.

## 7. `sigma()` is one of THREE reporting sites, not one

**Severity: MEDIUM. Pre-existing on both builds; NOT fixed.** This
extends the defect the lane recorded and did not fix.

The lane's record is correct as far as it goes: `sigma.frmtmb_fit()`
returns 1 for a family with no dpar called `sigma`, including one whose
scale is mapped out through `se_dpar = "tau"`, while
`predict(dpar = "tau")` correctly reports 0. Reproduced:

| fit | `sigma()` | `predict(dpar = <scale>)` | `hypothesis("sigma = 0")` |
| --- | --- | --- | --- |
| built-in gaussian, `se()` | 0 | 0 | **1** |
| custom, scale named `sigma`, `se()` | 0 | 0 | **1** |
| custom, `se_dpar = "tau"`, `se()` | **1** | 0 | errors |

The third column is new information and it is the reason the lane was
right to leave this alone: `sigma()` and `hypothesis()` already
disagree with each other, on the BUILT-IN gaussian, on both builds.
`R/sugar.R:53` gates on `"sigma" %in% dpars` and then returns 0 for
`se()`; `R/confint.R:2022` gates on `lp[["dpar"]] != "sigma"` and
reports the mapped-out constant 1. Settling "what does `sigma()` report
for a family that does not have one" therefore means settling both
sites plus `predict()`'s report hook at the same time, with one answer
for the mapped-out case. Doing it inside this lane would have been the
wrong scope. Recorded here so it is one ticket rather than three.

## 10. `se_dpar = NA` versus omitted: the four cases, plus four more

**Severity: none. Verification.** All eight behave.

| spelling | LANE result |
| --- | --- |
| absent, family has a second dpar | refused (message names `se_dpar`) |
| `NA` (logical) | accepted; NO dpar mapped out |
| `NA_character_` | accepted, identical to bare `NA` |
| `"tau"` (a real dpar) | `tau` mapped out; logLik -62.4977718, SEs finite |
| `"phi"` (not a dpar) | construction error naming the dpars it has |
| `"mu"` (a primary) | construction error naming it a LOCATION parameter |
| `NA_integer_` | construction error, `got integer NA` |
| `c(NA, NA)`, `character(0)`, `TRUE` | construction errors naming the contract |

`NA` and `NA_character_` both normalize to `NA_character_`. Absent and
`NA` are indistinguishable on a model with NO `se()` term, which is
right: both fit at -90.32662078 with `tau` estimated.

`se_dpar = NA` is a promise, and a family that makes it falsely gets
what it asked for: declaring `NA` on the second-SCALE family produces
logLik -62.49777177 with `NaN NaN NaN` and the flat-direction warning
naming `tau_(Intercept)`. That is the documented contract, not a
defect, but it is worth knowing that `NA` disarms the guard completely
rather than weakening it.

**A family that declares `se_dpar` but does NOT list `"se"` in
`accepts_aterms`**: the parse guard pins the named dpar before frame
assembly gets to refuse the term, so the pin happens and is then thrown
away with the whole call. The user-visible outcome is the 0.54.0
refusal, verbatim ("... does not declare that it does"), for both
`se_dpar = "tau"` and `se_dpar = NA`. Not a hole. Without an `se()`
term the declaration is inert: -90.32662078 either way.

Two of these deserve a note.

* **The multivariate case cannot double-fire by construction**, not by
  placement: `notify_once()` is keyed by tag and the tag is marked
  spent before `message()` runs. The measurement confirms it; the
  design guarantees it.
* **The one-point interval fires, and it should.** I suspected it
  should not, since a one-point interval on a count is exactly
  `P(Y = y)` and reads like an ordinary observation. It is not: brms
  reads an interval as `P(y < Y <= y2)`, which at `y2 == y` is zero,
  so the two packages diverge there as sharply as anywhere. frmtmb
  explicitly allows `y2 == y` (`R/frame.R:1428`) as the exact
  observation. Firing is correct. Suspicion disproved.
* The only structured family that refuses `cens()` by name, `hmm()`,
  refuses it in `hmm_check_aterms()`, which runs EARLY in the frame
  loop, before the notice. It also has no dpar named `sigma` and does
  not declare `se()`, so the `se()` guard is inert on it in both
  builds. Its `default_forms`, the only ones shipped anywhere, are
  transition cells, not scales.
