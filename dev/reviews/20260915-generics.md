## 1. `unlockBinding()`

### What I could not break

`registerS3methods()` runs at line 345 of `base::loadNamespace` and
`.onLoad` at line 367, so every `S3method()` directive is resolved
BEFORE `frm_adopt_generics()` switches any binding. That closes the
worst case I went looking for: frmtmb's `posterior_summary.default`
and `loo_compare.default` land in frmtmb's OWN method table and cannot
overwrite brms's or loo's. Measured as well as read:
`posterior_summary()` on a 500 x 2 matrix before and after
`loadNamespace("brms")` is `identical()`, plain and robust, max
absolute difference `0.000e+00` (`genrev-patho.R defaultswap`).

Orders that all give 0 of 27 dispatch and 0 of 27 `getS3method`
damage against the brms-alone control (`genrev-probe.R`,
`genrev-summary.R`, one process per row):

| order | result |
|---|---|
| `library(brms); library(frmtmb)` | 0/27 |
| `library(frmtmb); library(brms)` | 0/27 |
| `library(frmtmb); loadNamespace("brms")` | 0/27 |
| `library(lme4); library(frmtmb)` | 0/5 |
| brms attached, then a third package that imports frmtmb | 0/27 |
| both attached, brms detached, unloaded, reloaded | 0/27 |
| frmtmb attached, detached, brms ns loaded, reattached | 0/27 |
| frmtmb ns loaded, unloaded, then brms and frmtmb attached | 0/27 |

`pkgload::load_all()` three times over with brms attached: the
adoption is correct each time (`loo` from loo with `loo.brmsfit`
reachable, `posterior_summary` from brms) and the lane's OWN hook does
NOT stack. The hook counts that DO grow, lme4 0-4-7-10, posterior
0-7-14-21, bayesplot 0-1-2-3, are R's delayed S3 registrations: the
per-load increments are 3, 7 and 1, which are exactly frmtmb's counts
of `S3method(lme4::...)`, `S3method(posterior::...)` and
`S3method(bayesplot::...)`. Pre-existing, not this lane's, and
`pkgload::unload()` takes frmtmb's own hook back off
(`genrev-hooks.R`).

### The construction that does break it: a stale owner namespace

`frm_adopt_generics()` sets a load hook only for an owner that is NOT
loaded yet:

```r
for (own in owners) {
  if (isNamespaceLoaded(own)) next
```

So an owner present at frmtmb's load leaves NO hook behind, and
frmtmb's binding is a hard reference to that particular namespace
instance. Nothing ever re-validates it:

```
library(loo); library(frmtmb)
detach("package:loo"); unloadNamespace("loo")
loadNamespace("brms")            # loads a FRESH loo
```

Measured (`genrev-patho2.R stale`):

```
frmtmb ns loo -> loo
unload loo: ok
loo re-loaded fresh: TRUE
  loo          generic=loo  method=<none>  STALE=TRUE
  waic         generic=loo  method=<none>  STALE=TRUE
  loo_compare  generic=loo  method=<none>  STALE=TRUE
frmtmb ns loo identical to live loo::loo: FALSE
```

frmtmb's `loo` now dispatches into a dead namespace's method table.
`loo(brmsfit)` fails. The defect this lane exists to close is back for
those names, silently, and no order the lane measured can see it,
because the lane's load orders never unload an owner.

**Fix, measured.** Delete the `if (isNamespaceLoaded(own)) next` line
so the hook is set for every owner unconditionally. Repeating the same
construction with that hook present (`genrev-hookfix.R`):

```
loo generic from loo, STALE=FALSE, loo.brmsfit reachable=TRUE
identical to live loo::loo: TRUE
```

Cost: six extra `setHook()` calls at load. A hook for an owner that is
already there never fires unless the owner is loaded again, which is
the case being repaired.

### Is the one load order worth a permanent NOTE?

Yes, and the price of dropping it is measurable. `BASE brms loaded
only` is 25 of 27 lost dispatch and 27 of 27 lost `getS3method`.
Dropping the hook path gives that whole order back. Do not drop it.

But the trade the findings put to the user is a false dichotomy: there
is a third design that keeps the repair, removes the NOTE, removes the
hooks and removes the stale-namespace failure. **Install an ACTIVE
binding in `.onLoad`, while the namespace is still unsealed**, whose
function returns the owner's generic if the owner is loaded and
frmtmb's own otherwise. `makeActiveBinding()` in an unsealed namespace
needs no `unlockBinding()` at all.

I built it on three throwaway packages (`genrev-ab.R`, one process per
mode) rather than arguing it:

| mode | generic resolves to | owner method | own method | getS3method both |
|---|---|---|---|---|
| adopter, then owner loaded | owner | yes | n/a | yes |
| RE-EXPORTER, then owner loaded | owner | yes | n/a | yes |
| adopter alone | adopter | n/a | yes | yes |
| owner attached, then adopter | owner | yes | n/a | yes |
| owner loaded, UNLOADED, reloaded | owner | yes | n/a | yes |

Two things to note. The active-ness PROPAGATES through
`importIntoEnv()`: `bindingIsActive()` is TRUE in the adopter's
attached environment AND in the re-exporting package's attached
environment. That repairs the residue the lane files as defect 5, for
free, which the binding-swap cannot do. And `getS3method()` still
works, which a call-time forwarding generic would have broken, because
a forwarder's `environment()` is still frmtmb's namespace.

Costs to weigh before adopting it: one closure call per generic ACCESS
rather than per session; `bindingIsLocked()` and `ls()` still behave,
but an active binding in a namespace is unusual and some tooling may
not expect it; and the whole thing needs re-running against the 27-name
table rather than the two-name toy. It is a follow-up, not a merge
gate, but it should be on the record as the option the findings did not
price.

## 5. The scale contract

### The identity is an identity, and the lane says so

`fitted()` is `response_mean()`, which is the family's own `mean_fn`,
which for lognormal is literally `exp(dpars$mu + dpars$sigma^2/2)`
(`R/families.R:1378`). So `fitted() / exp(mu)` IS `exp(sigma^2/2)` by
construction. Measured at full precision rather than at `%.6f`
(`genrev-scale.R`):

```
max |fitted - exp(mu + s^2/2)| in ulps: 0.000
identical(fitted, exp(mu + s^2/2)):     TRUE
median(fitted/exp(mu)) = 1.083917735481314
exp(sigma^2/2)         = 1.083917735481315
difference in ulps     = 3.690      (one division apart)
```

No falsification. The findings label it correctly and give the residual
at full precision. This is the one number this round that was presented
as an identity and IS one.

### The contract is NOT complete

Three holes, each measured on the same fit the test uses.

1. **`conditional_effects()` is not on the table at all**, and it is
   the one method whose scale is the opposite of `predict()`'s.
   Measured: `estimate__` ranges 1274.05 to 9689.08, the RESPONSE
   scale, where `predict()` on the same fit is about 8.73. A porter
   reading `?frmtmb-scales` to understand why two methods differ by
   three orders of magnitude will not find the one they plotted.

2. **The stated lognormal identity has two unstated conditions.** The
   page says flatly that `fitted()` is `exp(mu + sigma^2/2)`.
   * With a distributional sigma (`lf(sigma ~ x)`), `sigma()` returns
     `NA` with a warning and the formula as written gives `NA`. The
     identity holds to 0 ulps only with `predict(dpar = "sigma",
     type = "response")` in place of `sigma()`.
   * Under truncation, `response_mean()` switches to `trunc_mean_fn`
     and the formula is simply wrong: on a `y | trunc(lb = 2000)`
     lognormal the relative difference is **0.4548**.
   `sigma()`'s own row in the table should also say it is `NA` when
   sigma varies by observation.

3. **Methods stated nowhere:** `posterior_summary()`, `pp_check()`,
   `bayes_R2()`, `hypothesis()`, `dharma_residuals()`, `profile()`,
   `influence()` and `cooks.distance()`. `predict(dpar = "sigma")` is
   listed as "link, or response", which is the one row that does not
   answer the question the page exists to answer.

### The page is hidden

`R/scales.R` carries `@keywords internal`, and `frmtmb-scales` is not
in `_pkgdown.yml`. Of the twelve `frmtmb-*` concept pages in core,
exactly three are internal: `frmtmb-package` (auto-generated),
`frmtmb-shared-generics` (plumbing, correctly internal) and this one.
The other nine are all indexed. Item 2.5d's whole deliverable is a page
the user is told to read, and it is the only one of its kind they
cannot find.

The Rd itself renders correctly. `Rd2txt` on `man/frmtmb-scales.Rd`
shows the three-column table intact; no `%` hazard in this page.

**One assertion is weaker than the page says it is.** In "fitted() on a
lognormal is the MEAN, not the median":

```r
ratio    <- median(fitted(f) / exp(mu))       # == exp(s^2/2), an identity
se_ratio <- exp(sg^2/2) * sg^2 * se_ls
expect_gt((ratio - 1) / se_ratio, 5)
```

The delta method is correct. But substitute the identity and expand:
`ratio - 1` is about `sigma^2/2` and `se_ratio` is about
`sigma^2 * se(log sigma)`, so the statistic reduces to
`1 / (2 * se(log sigma))`, which is about `sqrt(n/2)`. Measured:
statistic 13.2433, `1/(2*se_ls)` 13.7840, `sqrt(n/2)` 14.1421. So
`> 5` is, to first order, an assertion that n > 50; it does not depend
on sigma and therefore not on the size of the discrepancy it is meant
to detect. It still kills M1, where the ratio is exactly 1 and the
statistic is 0, so it discriminates. The page should not describe it as
measuring the separation.

**The test covers 9 of about 15 contract rows.** `predict(dpar =)`,
`residuals(type = "deviance")`, `residuals(type = "osa")`, `coef()`,
`ranef()`, `confint()`, `vcov()` and `logLik()` are stated on the page
and asserted nowhere.

### The replaced yardstick: confirmed

Both halves reproduce (`genrev-scale.R`):

```
mean-minus-median on the link scale (s^2/2): 0.080582
predict() own se.fit: min 0.086664 median 0.088222 max 0.104725
separation / median se.fit = 0.9134
se of log(sigma) from summary(): 0.036274
ratio 1.083918, its se 0.006337, t = 13.2433
```

The prediction's own standard error cannot separate the lognormal mean
from its median: they sit 0.9134 of one apart, and 0.9298 of one even
at the smallest `se.fit` on the design. The ratio's own standard error
can. The delta-method derivation is right:
`d/dl exp(exp(2l)/2) = ratio * sigma^2` with `l = log(sigma)`.
Keeping the wrong first spelling on the page is the right call.

## 7. Timing: the instrument, and what it cost

**The clock.** Measured directly on this box: `proc.time()[["elapsed"]]`
advances in steps of min 0.010 s, median 0.020 s. The lane's instrument
is `system.time()[["elapsed"]]`, which is that clock. Its reported
minima of 0.220 and 0.180 differ by exactly one or two ticks, and its
CONTROL moved 0.020 s, one whole tick, which is half of the effect it
claimed. That instrument could not have resolved the effect it reported.

**The re-measurement.** 30 interleaved replicates, one fresh process per
replicate, timing the same `library()` call with BOTH clocks
(`genrev-loadcost.R`):

```
arm                               min(st)  med(st) |    min(hr)    med(hr)
frmtmb FIX                          0.200    0.250 |     0.2158     0.2683
frmtmb BASE                         0.180    0.240 |     0.1990     0.2508
frmtmb BASE + nlme + generics       0.200    0.255 |     0.2173     0.2667
control Matrix FIX                  0.440    0.550 |     0.4462     0.5634
control Matrix BASE                 0.440    0.550 |     0.4555     0.5700
control nothing FIX                 0.000    0.000 |     0.0128     0.0181
control nothing BASE                0.000    0.000 |     0.0132     0.0175
nlme alone                          0.030    0.055 |     0.0584     0.0744

FIX - BASE      minima: system.time +0.020  hi-res +0.0167
CONTROL Matrix  minima: system.time +0.000  hi-res -0.0093
CONTROL nothing minima: system.time +0.000  hi-res -0.0004
permutation p for the FIX-BASE gap on minima: 0.0043 (obs +0.0167)
```

So the true cost is **+0.0167 s**, not +0.040 s. The published figure is
2.4x too large and is an artifact of the tick. The effect itself is
real: a 20,000-relabelling permutation test on the paired minima gives
p = 0.0043.

**The attribution is right, and can be made exact.** Adding
`loadNamespace("nlme")` and `loadNamespace("generics")` to the BASE arm
costs `+0.0183 s` over BASE, and `FIX` minus that arm is **-0.0015 s**.
The two new hard Imports account for the whole of the difference and
the adoption loop is below the noise floor at the process level. That
is a stronger statement than the one the findings make, and it survives
the correction to the headline number.

**The adoption loop itself.** The lane's 1,689.5 us reproduces once the

### The per-process rule

The defect is not visible ONLY in a single process. It reproduces one
file per process as soon as the file's precondition, brms loaded, is
built. What one file per process hides is that every file runs in an
EMPTY environment, so a defect that depends on the environment stays
invisible unless the environment is built on purpose. `R CMD check` saw
this one because of file order. The release harness is not blind to the
class: `dev/release/run-check.ps1` runs `--as-cran` with `NOT_CRAN=true`
and runs the tests in one process, and that is what caught it.

So no exception to the rule. State two things instead. The `R CMD
check` test run is a CORRECTNESS gate, not only a NOTE counter. And a
file that exercises a borrowed generic is also run per process with
each optional owner preloaded, which is deterministic where file order
is not. Neither would have caught BLOCKER E, which needs a test.
