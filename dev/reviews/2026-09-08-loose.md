## F1. BLOCKING. The deleted span refusal was reachable, and the deletion is a silent behavior regression

`extensions/frmtmb.spline/R/curve-feature.R:225-234` (the comment that
replaced the deleted block; the block itself was at `:225-230` before
the edit).

### The claim

> both refusals reduce to the same call on an `nd` fixed before either
> runs [...] a non-empty `sp_span_on_grid(nd)` always raises at 165-166
> and control never reaches 228.

The new in-source comment states the same thing:

> So a non-empty `sp_span_on_grid(nd)` always refuses at the scan, and
> control never arrives here with anything to say.

### The mechanism, stated so it is not re-derived wrongly

**The scan and the span check do not look at the same data, and the
whole argument depends on believing that they do.**

> `scan$span` and `parts$span` are computed on a ONE-ROW grid, widened
> along `var` only. `sp_span_on_grid(nd)` is computed on the USER'S
> grid, every row and every column. They can disagree.

Concretely, `frm_curve_feature()` never evaluates the user's grid as a
grid. It takes row 1 and replicates it:

- `row1 <- nd[1L, , drop = FALSE]` at `curve-feature.R:120`
- `eta_at()` at `:125-129` does `d <- row1[rep(1L, length(tv)), ]` then
  `d[[var]] <- tv`
- the stencil at `:222-223` does the same:
  `stk <- row1[rep(1L, 5L * length(roots)), ]`, then `stk[[var]] <- ...`

So every point the scan and the stencil evaluate holds **every column
except `var` frozen at row 1's value**. No other column varies in
either. `sp_span_on_grid()` (`R/curve-cov.R:90-92`) instead runs one
`predict()` on the **whole** `nd`, every row and every column as the
user passed it.

The lane's step, "a grid point outside the span puts the scan outside it
too, in the same direction and by at least as much", is a statement
about the `var` column. It is true there and **vacuous for every other
column**, because no other column varies in the scan at all. A model
with a second `ps()` term therefore breaks it: the grid can leave that
second term's span in a row the scan never evaluates. `scan$span` is
empty, the first guard is false, the first refusal never runs, and
`sp_span_on_grid(nd)` is non-empty when the second guard asks. That is
the deleted branch, live.

The trap for the next reader is that the two refusals really are
textually identical, `sp_span_stop(sp_span_on_grid(sp$fit, nd, ...))`,
and `nd` really is fixed before either runs. Both observations are
true and neither is sufficient. What differs is not the call but
**which guard lets you reach it**: `length(scan$span)` asks about the
one-row grid widened along `var`, `length(parts$span)` asks about the
stencil, and *neither asks about `nd`*. Two guards that ask different
questions can gate the same call to different effect. Any future
argument that one of these branches is dead has to be an argument about
the guards, not about the call they share.

### Reproduction

Needs no exotic argument: default `eps`, default everything.
`scratchpad/rvlo-reach2.R`.

```r
set.seed(4242)
n <- 220
d <- data.frame(t = sort(runif(n)), z = runif(n, 0, 1))
d$y <- 2 + sin(2 * pi * d$t) + 0.5 * d$z + rnorm(n, 0, 0.25)
fit <- frm(bf(y ~ lev + ps(t, k = 10, pad = 0.3) + ps(z, k = 8, pad = 0.02),
              lev ~ 1, nl = TRUE), family = gaussian(), data = d)
pt <- fit$frame$linpreds[["y.mu"]]$ps_terms
st <- pt[[1]]$knot_range   # t span: [-0.2969, 1.2981]
sz <- pt[[2]]$knot_range   # z span: [-0.0178, 1.0179]

# grid end just inside t's span, so the crossing scan stays clean;
# a root within e2 of that end pushes the STENCIL past it
b <- st[2] - 5e-6 * (st[2] - 0.05)
g <- data.frame(t = seq(0.05, b, length.out = 15))
g$z <- 0.5
g$z[10] <- sz[2] + 5      # one row leaves z's span; row 1 does not

# `at` chosen so the root lands 0.2 * e2 inside the grid end
frm_curve_feature(fit, var = "t", type = "crossing", at = at, newdata = g)
```

|---|---|
| main (`rvlo-main-lib`) | **ERROR**, "the search bracket leaves a ps() term's knot span" |
| branch (`rvlo-lib`) | **no error, no warning**, returns a root at 1.298035 |

The same contrast holds with an explicit `eps = 1.0`
(`scratchpad/rvlo-reach.R`), which is the easier construction.

### The sibling settles it

`frm_curve_deriv()` keeps a **structurally identical** gated re-ask at

| call | outcome |
|---|---|
| `frm_curve_deriv(fit, var = "t", newdata = g, eps = 1.0)` | **warns**, "this grid leaves a ps() term's knot span" |

`curve-deriv.R:136-141` is dead by exactly the same reasoning, and it
demonstrably is not. The lane deleted one instance of a live pattern
and left the other.

### What the deletion leaves behind

`parts$span` is now computed by `sp_curve_parts()` and **never read**
in `curve-feature.R`. Uses of `$span` in `R/`:

```
R/curve-cov.R:91,139,156     produced
R/curve-deriv.R:136          consumed, warns
R/curve.R:171                consumed, warns
R/curve-feature.R:165        consumed (the SCAN's span, not the stencil's)
```

`frm_curve_feature()` is now the only one of the three curve functions
that says nothing about a stencil excursion. That inverts the policy
`sp_span_stop()`'s own roxygen states at `R/curve-cov.R:50-56`: a
warning is the right answer for a band and the wrong one for a feature,
"a peak or a crossing located past the span [...] the search reports it
as a number with a standard error, and nothing in the output says which
curve it belongs to". The feature path is precisely the one that now
says nothing.

### In fairness: main's behavior was not obviously right either

The refusal main raises here keys on a grid row the search never
evaluates. Row 10's `z` leaves `z`'s span, but every point the scan and
the stencil touch holds `z` at row 1's value, so the number returned is
not contaminated by that row. Main refuses on evidence unrelated to the
search, and stays silent in the control case where the stencil leaves
`t`'s span with a clean grid. That is incoherent, and it is a fair
reading that the block needed to change.

What does not follow is deleting it as unreachable. The genuine defect
sitting underneath is the one both builds share: in the control case
`parts$span` is non-empty, the stencil really did leave the span, and
neither main nor the branch says anything at all. The branch had that
value in hand at `:224` and threw it away. Fixing that is the useful
version of this item; the deletion moves away from it.

`tests/testthat/test-span.R` on the instrumented build:

### Also unsupported

## The deeper incoherence: recording it is the right call

The lane recorded rather than fixed the finding that the refusal keys on
evidence the search never touches, while the case that matters, the
stencil alone leaving the span with a clean grid, stays silent in both
builds with `parts$span` discarded at `:224`. I agree with recording it,
for three reasons.

1. **The revert is provably zero-risk.** Executable code byte-identical
   to main is the strongest possible statement that nothing regressed.
   Shipping new refusal semantics in the same breath would give up that
   property in a lane whose brief is clearing recorded debt.
2. **The fix is a design decision, not debt, and a naive one is wrong.**
   The obvious move, `sp_span_stop(parts$span)`, would reintroduce
   exactly the false refusal that `sp_span_on_grid()` was added to
   prevent: `test-span.R`'s "a grid ending exactly on a knot is inside
   the span" pins that a grid laid on the knots must NOT be refused,
   and the stencil is outside it by `e1` by construction. A correct fix
   has to separate "the stencil left the span because the grid did"
   from "the stencil left it on its own fringe", which needs its own
   tests and a decision about warn-versus-refuse.
3. **The record is good enough to act on.** `dev/test-backlog.md:515-526`
   states the mechanism, names the discarded value and its line, cites
   both sibling functions and the `sp_span_stop()` roxygen policy that
   makes the feature path the one that most needs to speak, and notes
   the two-`ps()` test covers current behavior both ways. The next lane
   inherits a reproduction, not a hunch.
