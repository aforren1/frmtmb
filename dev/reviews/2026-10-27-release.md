### 2. minor: the open item's evidence is vacuous; the cause is found, and it does not block

The record says the two Stan models (defaults against the sampling
table passed back) have bitwise-equal log density and gradient at 800
points, so the cause of the different draws is unknown.
`dev/rel076-overlap-trip.R` evaluates `rstan::log_prob()` of both
stanfits only after both runs. tmbstan's `sampling()` method calls
`.Call("set_pointers", x, R_callf, R_callg, env, object@ptr, ...)`:
the objective is held in process-global pointers, so after run b,
both stanfits evaluate b's objective. That comparison cannot see a
difference.

`dev/review-rel076-trip.R` (the trip script's data, model and seeds;
`trip.txt`) evaluates each objective right after its own run, at 500
fixed points (a's 200 draws and 300 jittered points):

- `a's stanfit after b's run equals b's evaluation (global pointer):
  TRUE`.
- Each run's own objective: log density differs at 9 of 500 points,
  max abs 1.4e-14, max relative 1.8e-16 (one ulp); the gradient differs
  at 0 of 500.
- The warmup trajectories are equal through iteration 13, differ from
  iteration 14, by more than 1e-8 at 49 and more than 1e-2 at 115.
- The table's run reproduces itself (`TRUE`); the posterior means of
  the four sampled coordinates differ by at most 0.13 posterior sd
  (one chain of 200 draws each), within Monte Carlo error.

So the cause is the one acprior's test names: the two prior stacks
sum their entries in another order, one ulp apart, and HMC amplifies
the difference (an ulp in the log density flips an acceptance or a
tree decision). Not a density defect.

Fix: correct the record's paragraph in "The semantic overlaps" and the
backlog item to this cause and these numbers; add a pitfall to
`dev/rtmb-pitfalls.md`: "tmbstan holds the objective in a global
pointer; `rstan::log_prob()` of an earlier tmbstan fit evaluates the
latest one's objective, so compare objectives right after each run".
No code change.

### 3. minor: `ub = 1` on a `sar()` term is refused for a row-standardized W, by rounding

Evidence: `dev/review-rel076-cross.R x3` and `x4` (`cross-x3.txt`,
`cross-x4.txt`), a ring of 20 with chords, row-standardized,
eigenvalues -0.5789 to 1:

- frmtmb's table ends, 17 digits: `lb -1.7275567273213239 ub
  0.999999999999998` (`1 / max eigenvalue`, with the computed largest
  eigenvalue about 10 ulps above 1).
- `frm(set_prior("", class = "lagsar", ub = 1))`: `ERROR class =
  "lagsar" ub = 1 is outside the interval of sar(W, type = "lag"),
  (-1.72756, 1)`. The same for `errorsar` and for `lb = -1, ub = 1`.
  `lb = 0` alone fits.

`ac_bound_theta()` (`R/priors.R`) accepts an end only on exact
equality (`v == ends[2L]`), and the message prints the end it refuses
as 1. Whether `ub = 1` is taken depends on which side of 1 LAPACK
rounds the largest eigenvalue, so it can differ between the reference
BLAS and OpenBLAS. Core NEWS ("A bound at an end of a
residual-correlation parameter's interval is accepted") reads as if
`ub = 1` works. Not a regression: 0.75.0 refused every end. The table
passed back works, because it carries the same computed end (both
routes, both types: `frm(prior = fit table): logLik equal TRUE`;
`frm_sample(prior = sample table)` runs).

Fix (either): accept a bound within a few ulps of an end as that end,
as `autocor_bound_chart()` already snaps (`64 * .Machine$double.eps *
max(1, abs(b))`), print the ends with `digits = 15` in the refusal,
and add a test that types `ub = 1` on a row-standardized W; or file
it in the backlog and add "a bound typed at a computed end, such as
`ub = 1` for a `sar()` term, can be refused by rounding" to the NEWS
bullet.

### 4. nit: the sigma intercept under `sigma ~ x` is documented in `?set_prior` only

Release fix R1's sentence is true. Measured
(`dev/review-rel076-r1.R`, `r1.txt`): under `bf(y ~ x + ar(t, g, cov =
TRUE), sigma ~ x)`, the resolved entry of a prior on `class =
"Intercept", dpar = "sigma"` has no innovation factor (`innov no`),
and the penalty is the same at `theta_ar` -1.5, 0 and 1.5 (spread 0),
so it is read at the log marginal sd; the `b` entry likewise. Since
`log c` does not depend on `x`, the slopes are the same quantity in
both, as the sentence says. frmtmb.sample's default on that intercept
reads the same scale (`R/sample.R`: `set_prior(d, class = "Intercept",
dpar = dp)`, not natural). `?frm_sample` says "A prior on class
`"sigma"`, the default ... is read as brms reads it" and is silent on
`sigma ~ x`. The backlog has the fix. Fix: optional, one sentence in
`?frm_sample` pointing to `?set_prior`.
