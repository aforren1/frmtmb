# Lane tmbstan121: does tmbstan 1.2.1 remove the StanHeaders pin?

Worktree `frmtmb-wt-tmbstan121`, base e031e8c (frmtmb 0.59.0,
frmtmb.sample 0.7.0). Measured 2026-09-17. Nothing was committed.

## Verdict

| Reason for the pin | With tmbstan 1.2.1 |
| --- | --- |
| (1) tmbstan built against StanHeaders 2.39 samples a standard normal | **FIXED.** Gone in both configurations, from source and from the CRAN binary. The 1.2.0 control reproduces the defect. |
| (2) rstan 2.32.7 cannot compile a fresh Stan program against StanHeaders 2.39.1 | **STILL HOLDS** on a stock toolchain. tmbstan does not touch it. It goes away with one Makevars line, `CXX17FLAGS += -std=gnu++17`, measured below. |

So the pin cannot drop as the machine is configured today. It can drop
if the user's Makevars gains that line, because reason (2) is then gone
too on this machine (measured on one rstan program, one brms program,
and the two gated brms-fit test files).

## Reason (1): the sampling defect

Script `dev/tmbstan121-03-probe.R <arm>`, logs
`dev/tmbstan121-probe-<arm>.log`. Three instruments per arm.

**The shipped detector.** `frmtmb.sample:::tmbstan_build_broken()` is
FALSE and `check_tmbstan_build()` does not refuse in A, Bsrc, Bbin,
BbinA and C120A. In C120 it is TRUE and the call refuses.

**The HMC gradient, chain-free.** An RTMB objective of four independent
normals, means `c(3, -2, 10, 0.5)`, sds `c(0.5, 2, 0.1, 3)`.
`rstan::grad_log_prob()` against `-obj$gr()` at four points (origin,
mode, mode + 0.3, and `rnorm(4, 0, 2)` at `set.seed(4030)`); the stanfit
comes from a 20-iteration chain, seed 1, whose draws are not read.

| Arm | 4 of 4 gradients `identical()` | lp at origin, Stan vs objective |
| --- | --- | --- |
| A, Bsrc, Bbin, BbinA, C120A | TRUE | -5020.985670 vs -5020.985670 |
| C120 | FALSE, relative gap 0.66 to 10 | 0.000000 vs -5020.985670 |

C120's gradient equals the defect's closed form `-u` at every point:
its relative gap to the model equals the gap between `-u` and the model
at all four points.

**Chains against a known answer.** The same model, 4 chains x 4000
iterations, seed 20260917:

| Arm | th[1] mean, sd (truth 3, 0.5) | th[3] mean, sd (truth 10, 0.1) | largest abs z of mean |
| --- | --- | --- | --- |
| A, Bsrc, Bbin, BbinA, C120A | 2.9974, 0.4944 | 10.0002, 0.1001 | 0.55 |
| C120 | -0.0245, 1.0136 | 0.0266, 0.9912 | 972.54 |

z is (mean minus truth) over rstan's `se_mean`. The five healthy arms
print the same draws summary to four decimals.

kaskr/tmbstan#33's own reproduction, TMB's `simple` example (data at
`set.seed(123)`, the example's own), copied out of the TMB installation
before compiling so nothing is written into the user library. One chain
of 4000, seed 1:

| Arm | beta[1] draws mean, sd | beta[2] draws mean, sd |
| --- | --- | --- |
| ML estimate, se (all arms) | 52.0137, 0.2017 | 30.2406, 0.2018 |
| A, Bsrc, Bbin, BbinA, C120A | 52.0071, 0.2041 | 30.2308, 0.2050 |

One number worth naming so nobody rediscovers it: th[2] in the healthy
arms has sd/truth 0.9700 at an n_eff of 9963 for the mean. If that
n_eff also held for the squared draws, 0.97 would sit about 4 standard
errors low, but n_eff for the mean says little about the variance, and
this was not measured further. It does not bear on the verdict: all
five healthy arms print the same value, and the defect gives 0.4985.

**Answer: tmbstan 1.2.1 fixes reason (1).** It holds from source against
2.32.10 and against 2.39.1, and from the CRAN binary under either
runtime StanHeaders. The control built the same way from 1.2.0 samples
N(0, 1) on both models.

## Reason (2): rstan compiling a fresh program

Script `dev/tmbstan121-04-compile.R <A|B> <rstan|brms>`. The program
text carries a per-run timestamp so no cache can serve it.
`rstan_options(auto_write = FALSE)`.

| Arm | Makevars | rstan `stan_model()` | `brms::brm()` |
| --- | --- | --- | --- |
| A (2.32.10) | user's | OK, y mean 1.4696 sd 0.2375 (truth 1.5, 0.25) | OK |
| B (2.39.1) | user's | `compileCode()` ERROR, `make: *** [...Makeconf:304: ...o] Error 1` | same ERROR |
| B (2.39.1) | user's plus `CXX17FLAGS += -std=gnu++17` | OK, y mean 1.4696 sd 0.2375 | OK |

The B failure is the one `dev/machine-library.md` records. rstan
truncates the compiler output, so the first compiler error was not
captured here; the verbose log shows `-std=c++1y` after `-std=gnu++17`
on the compile line. The override is the lever
`brms-likelihood.yaml` already uses on CI, where its comment records
the first error as `'void_t' is not a member of 'std'`: rstan's
generated code asks for the cpp14 plugin, its `-std=c++1y` lands last,
and StanHeaders 2.39 needs C++17. The override file is
`tmbstan121-lib/makevars/Makevars.win`, the user's own one line plus
the `-std` line, passed through `R_MAKEVARS_USER`; the user's
`Documents/.R/Makevars.win` was not changed.

**Answer: reason (2) still holds on a stock toolchain and is
independent of tmbstan. It is a C++ standard flag ordering problem, and
one Makevars line removes it on this machine.**

## The one test change, and why the evidence demanded it

The control run showed `test-tmbstan-build-guard.R` failing TWO blocks
on a genuinely broken build, not the one canary it was designed to
fail. Block 2, "a generated model.hpp with the unpatched overload is
refused", ends by asserting `expect_false(tmbstan_build_broken())`
after the fixture restores state. On a real broken install the
restored state is TRUE, so the block fails. The earlier lane never saw
this, because its broken arm poisoned the memo instead of installing a
broken tmbstan.

Changed in
`extensions/frmtmb.sample/tests/testthat/test-tmbstan-build-guard.R`:
the block reads `before <- tmbstan_build_broken()` first and asserts
`expect_identical(tmbstan_build_broken(), before)` at the end.

`dev/tmbstan121-07-guardfix.ps1`, the file alone in each arm:

| Run | Pass | Fail | Error | Skip | Failing block |
| --- | --- | --- | --- | --- | --- |
| C, before the change | 10 | 2 | 1 | 1 | canary AND block 2 |
| C, after | 11 | 1 | 1 | 1 | canary only |
| A, after | 23 | 0 | 0 | 0 | none |
| B, after | 24 | 0 | 0 | 0 | none |
| A, mutant fixture that does NOT restore, new assertion | 22 | 1 | 0 | 0 | block 2 |
| A, same mutant, original assertion | 22 | 1 | 0 | 0 | block 2 |

The mutant rows are the absent case: a fixture that leaves the
synthesized broken state behind is still caught on a healthy machine,
exactly as the original assertion caught it. The mutants are copies of
the test directory under `tmbstan121-lib/mut` and `mut-orig`; the
worktree helper is unchanged. The full-suite runs above predate the
change; the A and B rows here re-measure the one file it touches.

## Recommendations

1. **The pin.** Do not drop it on a stock toolchain: reason (2) holds.
   It can drop once the user's `Documents/.R/Makevars.win` carries
   `CXX17FLAGS += -std=gnu++17` after its existing line, which is the
   user's file to change. Before dropping it, rerun the gated tiers
   that compile fresh programs, since only two files were measured
   here. Also, `dev/stan-cache` was compiled against 2.32.10; B served
   it without a failure in the ungated suite, but whether every cached
   DSO loads under 2.39.1 was not audited, so clearing the cache after
   the switch is the safe order.
2. **The DESCRIPTION floor.** Yes, `tmbstan (>= 1.2.1)` in
   frmtmb.sample's Suggests, and in the root DESCRIPTION's Suggests too,
   since `tests/testthat/test-lkj.R` samples through tmbstan. It must
   land TOGETHER with removing the CI pin step (item 4): that step
   installs tmbstan 1.2.0 from the 2026-09-01 snapshot, and with
   `_R_CHECK_FORCE_SUGGESTS_` at its default the check would stop on an
   unsatisfied Suggests. Reinstall tmbstan from CRAN in the user library
   first, because its GitHub build reports 1.2.0.
3. **`check_tmbstan_build()`.** Keep the detector exactly as it is: it
   is correct on all six arms, costs one file read, and still catches a
   1.2.0 build. Change only the refusal's remedy text, which says
   "Until an upstream fix, install a binary tmbstan build, or reinstall
   tmbstan with StanHeaders 2.32.10". The upstream fix exists, and
   "install a binary" is now wrong advice for a stale RSPM or mirror
   binary. Suggested remedy: "reinstall tmbstan (>= 1.2.1)". Keep the
   substrings `StanHeaders` and `samples a standard normal`, which the
   guard tests match. Not changed here, because the message is advice,
   not a verdict.
4. **CI.**
   - `check-frmtmb-sample.yaml`: delete the step "Pin a tmbstan whose
     generated model.hpp is patched", together with item 2. Its
     obsolescence probe will now warn on every run, because the
     unpinned noble binary is patched. The job does not set
     `FRMTMB_BRMS_FIT_TESTS`, so no fresh compile runs there and
     StanHeaders 2.39.1 is safe for it; the canary block in
     `test-tmbstan-build-guard.R` still turns the job red if a broken
     build ever returns. If the brms-fit tier is ever enabled in this
     job, add the `CXX17FLAGS` step from `brms-likelihood.yaml`.
   - `R-CMD-check.yaml` and `test-coverage.yaml` install tmbstan through
     the root DESCRIPTION and get 1.2.1 from RSPM now, so the LKJ
     sampling block in `test-lkj.R` should stop skipping silently on
     Ubuntu. Nothing to change beyond the floor. The macOS binary was
     not inspected.
   - `brms-likelihood.yaml`: no change. It does not install tmbstan,
     and its C++17 step is the reason (2) remedy measured above.

## What was not done

- No workflow, DESCRIPTION or `R/` source was edited, per the brief.
- tmbstan 1.2.1's own tinytest suite was not run; tinytest is not
  installed and the probes cover the same property directly.
- The macOS CRAN binary and a Linux source build were not checked.
- `R CMD check` was not run: the only change is two assertion lines in
  one test file, rerun in every arm above.
